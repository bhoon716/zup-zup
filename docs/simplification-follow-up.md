# 단순화 후속 작업

기준 브랜치는 `codex/simplify-existing-20261026`이다. 단일 Spring 앱을 유지한다. 로컬 수정·검증·커밋만 진행하며 push·브랜치 병합·배포·운영 DB 변경·실제 발송은 하지 않는다. 아래 구현·검토·계획의 범위를 서로 확대하지 않는다.

## 완료

- `2814d9c79`: 리뷰 공유 캐시에 세 통계 필드만 반영, 타학기·분반 정보 보존, 미사용 기기 훅 두 개와 자체 테스트 3개 제거. 웹 275건·타입 검사·lint·build·브라우저 4건 통과.
- `254de92bf`: 서버 리뷰 대상 강의 선택을 기존 카탈로그 중심으로 통합. 기존 단위 테스트 보존·H2 서비스 계약 7건 보강. 서버 530건, PMD·Checkstyle 위반 0, clean check bootJar 통과.

## 승인된 구현

### 정상 응답과 결과 DTO

- DTO 역할 분류는 구현·컴파일·정적 검사·관련 20건 검증 완료. 정상 응답 전환도 구현·서버 536건·웹 279건·정적 검사·양쪽 빌드·브라우저 4건 검증을 완료했다.

- 정상 JSON은 DTO·목록·페이지 객체 등 실제 결과를 반환한다. `CommonResponse`와 성공용 code/message/data 중첩을 제거한다. 새 정상 응답 래퍼를 만들지 않는다.
- 현재 공통 `ErrorResponse`·오류 상태/안내/상관 ID는 유지한다. 성공 구조 변경에 오류 계약 변경·로그 정책 변경을 끼워 넣지 않는다.
- ResponseEntity는 상태·헤더가 필요한 곳에 유지한다. 기존 200/201/204·302/쿠키·Location·첨부 Content-Disposition·페이지 메타데이터를 보존한다. health 상태 조회의 503 상태 결과도 기능 DTO로 유지한다. 문자열·데이터 없음·nullable 대표 시간표의 직접 응답은 브라우저 파싱까지 확인한다.
- API 입력은 `dto/request`, API 출력은 `dto/response`, 내부 처리 결과는 `dto/result`에 정리한다. 외부 연동·이벤트·조건 모델은 별도 역할 패키지에 두며 DTO를 복제하지 않는다. 클래스명·JSON 필드는 불필요하게 바꾸지 않는다. 요청 DTO와 내부 공유 조회 타입은 목적에 맞는 현재 위치를 유지한다.
- 서버·웹 API/훅/타입·모의 응답·문서·테스트를 함께 전환한다. 정상/오류·빈 응답·페이지·파일·인증/권한 계약을 검증한다.

### 일정과 D-day

- Schedule 한 엔티티에서 일정의 대표 D-day 표시 여부를 설정한다. 기존 확정 정책에 따라 여러 일정 지정이 가능하다. 일반 일정 목록을 선택 일정만으로 축소하지 않는다.
- 이미 확정된 진행 중/예정 정렬, 종료 후 위젯 제외, soft delete·복원·원본 보존, 수집 설정과 분리를 실제 코드와 대조한다. 시간대·날짜/시각 경계는 테스트 가능한 작은 규칙으로 명시한다.
- 기존 D-day 255자 제목·목표일/시각·생성/수정 시각을 손실 없이 일정으로 복사한다. 제목만으로 자동 병합하지 않는다. 두 테이블의 독립 ID 충돌과 기존 API 식별을 고려한다. 과거 migration 수정이나 운영 DB 적용은 하지 않는다.
- **선택 확정:** 옛 일정·D-day 데이터와 ID 매핑 보존은 요구하지 않는다. 관리자·공개 소비 경로를 일정 API로 통합하고 별도 호환 계층을 만들지 않는다. 운영/공유 DB 데이터 삭제는 실행하지 않으며 자동 migration에 파괴적 정리를 넣지 않는다.
- 별도 검증·로컬 커밋으로 관리하고 마지막에 현재 HTML/다이어그램의 바뀐 부분을 맞춘다.

### API 페이지 크기 고정

- 모든 공개/관리자 페이지 API의 크기를 서버에서 30으로 고정한다. page 번호·허용된 정렬·페이지 메타데이터는 보존한다.
- 클라이언트 size=1/100/음수와 무관하게 고정 PageRequest로 전환하고 정상 페이지 이동을 검증한다. 크롤링 chunk·outbox batch·내부 bulk limit는 변경하지 않는다.

### 소스 주석 정리

- 설명 주석·Javadoc·주석 처리된 죽은 코드는 기능 변경 뒤 별도 커밋으로 제거한다. README·설계 문서·기존 DB migration·vendor/생성물/lockfile은 대상이 아니다.
- 언어 인식 방식으로 문자열·URL·정규식·템플릿 리터럴을 보존한다. 라이선스·저작권·실행/컴파일/빌드/린터/타입/커버리지 제어·생성 소스 표식 등 의미 있는 주석은 유지하고 목록/이유를 보고한다.
- 사용자 명시 요청에 따라 테스트 given/when/then 같은 설명 주석도 정리한다. 기능 변경과 주석 정리의 검증·커밋을 구분한다.

## 읽기 전용 검토

- `CrawlerRunFailure`: 저장만 하는 진단 이력인지, 로그 전환으로 잃는 조사·보존 범위를 확인한다. 삭제하지 않는다.
- `CrawlerStatus`: 마지막 성공 시각의 신선도·관리자 상태·재시작 후 유지와 나머지 진단 필드를 구분한다. 삭제하지 않는다.
- `AdminActionLog`: 실제 감사 조회 API와 업무 트랜잭션, 첨부 확인·재전송·보존 영향을 확인한다. 별도 관리자 로그 화면은 만들지 않고 Grafana 방향으로 대안을 설명한다. 엔티티·데이터·테이블은 삭제하지 않는다.
- `applicationTaskExecutor`, `MdcTaskDecorator`, Firebase와 기타 설정·빈·의존성: 명시적 호출뿐 아니라 이름 기반 Spring MVC/자동 구성 사용을 확인해 제거 추천·추가 확인·유지로 분류한다. 민감한 설정 값은 출력하지 않는다.
- `SensitiveDataRedactor`: 실제 다섯 보호 기능과 사용처를 확인한다. 불필요함이 확실할 때만 조건부 제거 대상이며 로그·오류·발송 경로의 민감정보 보호를 약화시키지 않는다.
- 구현 완료 뒤 추가 단순화 후보는 최대 3~5개만 근거·효과·위험·최소 변경으로 보고하고 새 구현 승인을 기다린다.

## 계획만 정리

- 사용자 영구 알림함: 사용자별 알림 항목·읽음 상태·목록/권한·보존을 기존 알림 이력과 구분하는 짧은 설계를 준비한다. 이번에 엔티티·API·화면을 구현하지 않는다.
- 공지의 영구 알림함·채널 전달: 발행/수정 중 어느 시점에 누구에게 전달할지, 중복 방지와 재시도·취소 경계를 기존 공지/outbox와 대조한다. 대상 범위·읽음/삭제/보존·수정 시 재알림은 후속 선택 사항이다. 아직 실제 발송 경로에 연결하지 않는다.

## 나중에 할 로깅 점검 — 지금 구현하지 않음

- 사람이 읽는 메시지 한국어화, 레벨·기록 위치·중복·민감정보 점검.
- Grafana에서 찾을 event/runId/오류 코드·상관 ID 등 검색 키와 내부 원문 비노출 유지.
- Slack 오류 안내의 원인·영향·추적 정보 가독성 개선.
- 별도 관리자 로그 조회 기능은 추가하지 않는다. 일반 로그의 보존/압축 정책과 실제 설정 차이는 후속 점검 대상으로 남긴다.
