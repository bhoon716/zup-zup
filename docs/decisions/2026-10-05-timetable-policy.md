# 결정: 시간표의 시간 충돌은 표시하고 추가를 허용한다

- 상태: Accepted
- 결정일: 2026-10-05
- 범위: 시간이 겹치는 강의·개인 일정의 시간표 추가
- 대체 결정: 없음
- 관련 자료: [TimetableService](../../apps/server/src/main/java/bhoon/sugang_helper/planning/timetable/application/TimetableService.java), [시간표 재설계 체크리스트](../backend-redesign-checklist.md)

## 문제와 목표

시간표 계획 단계에서 시간이 겹치는 후보 강의나 개인 일정을 함께 담을 수 있도록 할지, 겹치는 항목의 추가를 차단할지 정한다.

## 선택지 비교

| 방식 | 장점 | 비용·제약 |
| --- | --- | --- |
| 충돌 표시와 추가 허용 | 후보 강의를 함께 담아 비교할 수 있음 | 실제 사용할 시간표의 충돌은 사용자가 정리해야 함 |
| 충돌 시 추가 차단 | 겹치지 않는 시간표를 유지 | 후보 조합을 자유롭게 담기 어려움 |

## 결정

1. 기존 시간표 항목과 시간이 겹치는 강의·개인 일정도 추가하고 저장할 수 있도록 한다. 시간 충돌만을 이유로 추가를 차단하지 않는다.
2. 시간이 겹친다는 사실과 충돌하는 항목을 사용자가 알 수 있도록 명확히 표시한다. 구체적인 표시 위치·표현과 API 응답의 구성은 상세 설계에서 정리한다.
3. 시간표는 후보 강의를 담아 비교하는 계획 도구로 사용할 수 있도록 한다. 실제 수강 신청을 학교 시스템에 수행하거나 시간 충돌이 없는 수강을 보장하는 기능으로 확대하지 않는다.
4. 시간 충돌 판정의 세부 기준과 개인 일정·강의 시간 데이터의 처리 방식은 상세 설계에서 정리한다.

## 근거와 결과

- 시간표를 계획하는 과정에서 후보를 함께 담고 충돌을 명확히 표시하는 방식을 제안했고, 사용자가 추가를 허용하는 1번을 선택했다.

## 기록과 구현 상태

- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기록하고 결정 목록에 추가했다.
- 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 수집된 최신 강의 정보를 저장된 시간표 조회에 반영한다

- 상태: Accepted
- 결정일: 2026-10-05
- 범위: 시간표에 담긴 강의의 시간·강의실 등 학교 정보 변경 반영
- 관련 자료: [TimetableService의 강의 정보 조회](../../apps/server/src/main/java/bhoon/sugang_helper/planning/timetable/application/TimetableService.java), [강의 수집 정책](2026-10-04-course-collection-policy.md)

### 비교와 결정

| 방식 | 장점 | 비용·제약 |
| --- | --- | --- |
| 수집된 최신 정보 반영 | 학교에서 변경한 강의 정보와 시간표가 맞춰짐 | 변경으로 기존에 없던 시간 충돌이 생길 수 있음 |
| 강의를 담은 시점의 정보 유지 | 계획한 당시 모습이 유지됨 | 실제 강의 정보와 달라질 수 있고 별도 갱신 방식 필요 |

1. 학교의 강의 시간·강의실 등 변경 정보를 정상적으로 수집해 DB에 반영하면, 다음 시간표 조회부터 해당 강의의 갱신된 정보를 사용한다.
2. 시간표를 위한 별도의 강의 정보 사본을 강의 추가 시점에 고정해 유지하는 방식을 기본으로 도입하지 않는다. 담은 강의의 식별자로 저장된 강의 정보를 조회하는 구조를 기준으로 한다.
3. 정보 갱신으로 시간이 겹치면 앞서 선택한 충돌 표시 정책을 적용한다. 그 이유만으로 사용자 시간표의 항목을 자동 삭제하지 않는다.
4. 수집 실패 시 마지막 정상 정보를 유지하는 기존 결정을 적용한다. 학교 변경 즉시 실시간 반영이나 이미 열린 화면의 실시간 자동 갱신을 이번 결정으로 확정하지 않는다.
5. 강의 폐강·카탈로그 삭제·조회 시 강의 정보 누락의 처리와 별도 변경 안내 필요성은 후속 논의 또는 상세 설계에서 정리한다.

### 근거와 기록 상태

- 학교 정보 변경을 수집 후 시간표 조회에 반영하는 방식과 추가 당시 정보를 유지하는 방식을 비교했다. 현재 코드가 저장된 강의 키로 강의 정보를 조회함을 확인하고 갱신 반영 방식을 제안했고, 사용자가 1번을 선택했다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 가입 처리에서 기본 시간표 생성을 직접 호출한다

- 상태: Accepted
- 결정일: 2026-10-05
- 범위: 신규 사용자와 기본 시간표의 생성 흐름
- 관련 자료: [UserOAuthAccountService](../../apps/server/src/main/java/bhoon/sugang_helper/identity/user/application/UserOAuthAccountService.java), [TimetableService](../../apps/server/src/main/java/bhoon/sugang_helper/planning/timetable/application/TimetableService.java)

### 결정

1. 신규 사용자 가입 처리에서 기본 시간표 생성 기능을 직접 호출한다. 현재 `UserRegisteredEvent`를 발행하고 시간표의 이벤트 리스너가 생성하는 흐름은 이 작업에 대해 직접 호출 방식으로 대체한다.
2. 사용자 저장과 기본 시간표 저장은 같은 DB 트랜잭션으로 처리한다. 둘 다 성공하면 커밋하고, 어느 하나라도 실패하면 함께 롤백한다.
3. 기존 사용자 로그인마다 기본 시간표를 새로 생성하는 방식으로 확대하지 않는다. 신규 사용자 생성 시 기본 시간표를 함께 만드는 흐름을 기준으로 한다.
4. 직접 호출을 위한 서비스·포트 구성과 의존성 배치, 중복 생성 방지 등은 상세 설계에서 정리한다. 다른 이벤트 사용과 여석 알림의 outbox는 각각의 기존 결정에 따른다.

### 근거와 기록 상태

- 가입과 기본 시간표 생성의 연결을 코드에서 바로 따라갈 수 있는 방식을 제안했고, 사용자가 직접 호출하는 1번을 선택했다.
- 현재 기본 시간표 생성 리스너에는 `@Async`가 없고 일반 `@EventListener`를 사용한다. 이번 선택은 이벤트가 반드시 비동기이거나 별도 트랜잭션이라는 전제에 근거하지 않으며, 필요한 처리 흐름을 명시적으로 드러내기 위한 결정이다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 한 시간표에 같은 과목의 여러 분반을 허용한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 같은 과목의 서로 다른 분반을 시간표에 함께 추가하는 경우

### 비교와 결정

여러 분반 허용, 같은 과목의 한 분반만 허용, 여러 분반을 허용하되 중복 과목 안내를 추가하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 같은 과목의 서로 다른 분반을 한 시간표에 함께 담을 수 있도록 한다. 같은 과목코드라는 이유만으로 추가를 차단하지 않는다.
2. 동일한 개설 강의를 같은 시간표에 반복 추가하는 것은 기존처럼 허용하지 않는다. 현재 코드는 시간표 식별자와 `courseKey`로 중복을 확인한다.
3. 서로 다른 분반의 시간이 겹치면 기존 시간 충돌 표시 정책을 적용하고 추가는 허용한다. 이번 선택으로 별도의 중복 과목 안내 기능을 추가하지 않는다.
4. 실제 수강할 분반의 최종 선택과 후보 정리는 사용자가 수행한다. 시간표가 학교 수강 신청을 대신하거나 같은 과목의 중복 수강 가능 여부를 보장하지 않는다.

### 근거와 기록 상태

시간표를 후보 강의를 비교하는 계획 도구로 사용하는 기존 방향과 일치하며, 과목별 추가 제한과 별도 안내 규칙을 줄인다. 사용자가 후보 분반을 직접 정리해야 하는 비용을 수용한다.

이번 추가는 의사결정 기록이며 실제 시간표 코드 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 시간표를 특정 학기에 제한하지 않는다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 시간표의 개설 연도·학기 구분과 강의 추가 제한

### 비교와 결정

학기 제한 없이 구성하는 방식, 시간표에 연도·학기를 지정하고 해당 학기 강의만 허용하는 방식, 학기를 지정하되 다른 학기 강의도 안내와 함께 허용하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 시간표를 특정 개설 연도·학기에 묶지 않는다. 이름은 기존 입력 제약 안에서 사용자가 자유롭게 정하고, 서로 다른 학기의 강의도 한 시간표에 담을 수 있도록 한다.
2. 시간표의 학기 제한을 위한 연도·학기 필드나 다른 학기 강의 추가 차단·안내 규칙을 이번 범위에 추가하지 않는다. 강의 자체의 개설 연도·학기와 식별 기준은 유지한다.
3. 동일 개설 강의 중복 추가 금지, 같은 과목의 여러 분반 허용, 시간 충돌 표시와 추가 허용 등 기존 정책을 유지한다.

### 근거와 수용한 비용

현재 시간표 엔티티는 이름과 대표 여부를 관리하고 별도 연도·학기 필드를 두지 않는다. 자유로운 계획 도구라는 방향에 맞춰 현재 구조를 유지하며 학기 지정·전환·검증 부담을 줄인다. 사용자가 이전 학기 강의를 잘못 담을 수 있는 제약을 수용하고, 학기 혼합 방지의 필요성이 확인되면 재검토한다.

이번 추가는 의사결정 기록이며 실제 시간표 코드 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 대표 시간표는 삭제할 수 없다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 사용자의 시간표 개별 삭제

### 결정

대표 시간표 삭제 후 자동 지정, 대표 없음 유지, 삭제 시 대체 시간표 선택을 비교했으나, 사용자는 별도로 대표 시간표 자체의 삭제를 금지하도록 결정했다.

1. 현재 대표로 지정된 시간표의 삭제 요청은 서버에서 거부한다. 화면에서도 삭제할 수 없음을 안내한다.
2. 해당 시간표를 삭제하려면 다른 시간표를 먼저 대표로 지정해야 한다. 기존 대표는 대표가 아닌 상태가 된 뒤 일반 삭제 정책에 따라 삭제할 수 있다.
3. 대표 시간표 삭제를 허용한 뒤 다른 시간표를 자동 승격시키는 현행 동작은 재설계에서 사용하지 않는다. 삭제 요청 자체가 대표 지정을 자동 변경하지 않는다.
4. 대표 변경과 삭제가 동시에 요청되더라도 대표인 시간표가 삭제되지 않도록 서버의 상태 확인과 저장 경계를 설계한다. 구체적인 오류 응답과 경합 처리는 상세 설계에서 정한다.
5. 이번 결정은 사용자의 시간표 개별 삭제에 관한 규칙이다. 계정 탈퇴에 따른 시간표 소프트 삭제·보존 정책은 유지한다.

### 근거와 후속 논의

대표 시간표의 삭제를 금지한다는 사용자의 명시적인 요구를 반영한다. 삭제하려는 시간표가 대표라면 대표 변경을 먼저 수행해야 하는 비용을 수용한다. 시간표가 하나만 남은 경우의 최소 보유·대표 해제 허용 여부는 다음 논의로 남긴다.

이번 추가는 의사결정 기록이며 실제 시간표 코드 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 대표 해제와 시간표가 없는 상태를 허용한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 대표 시간표 해제 및 마지막 시간표 삭제

### 비교와 결정

대표 시간표 하나를 포함해 최소 한 개의 시간표를 유지하는 방식과 대표 해제 후 마지막 시간표도 삭제할 수 있게 하는 방식을 비교했다. 사용자는 두 번째 방식을 선택했다.

1. 대표 시간표의 지정을 해제할 수 있도록 한다. 시간표가 남아 있어도 대표가 없는 상태를 허용한다.
2. 대표가 아닌 시간표는 마지막 한 개라도 삭제할 수 있다. 사용자의 활성 시간표가 하나도 없는 상태를 허용하며, 삭제 후 기본 시간표를 자동 생성하지 않는다.
3. 현재 대표인 시간표를 바로 삭제할 수 없다는 직전 결정은 유지한다. 다른 시간표를 대표로 지정하는 방법 외에도, 해당 시간표의 대표 지정을 먼저 해제한 뒤 삭제할 수 있다.
4. 시간표 삭제 후 다른 시간표를 자동으로 대표 지정하지 않는다. 대표가 없는 경우와 시간표가 없는 경우를 조회·화면에서 정상 상태로 처리한다.
5. 신규 가입 시 기본 시간표를 생성하는 기존 결정은 유지한다. 기존 사용자의 로그인마다 기본 시간표를 다시 생성하지 않는 기존 규칙도 유지한다.

### 근거와 후속 논의

시간표를 반드시 보유하거나 대표로 지정해야 하는 제약 없이 사용할 수 있다는 사용자의 선택을 반영한다. 대표 없음·시간표 없음 상태를 조회와 화면에서 처리해야 하는 비용을 수용한다. 이번 추가는 직전 기록의 ‘삭제하려면 다른 시간표를 먼저 대표로 지정해야 한다’는 절차에 대표 해제 경로를 추가한다.

시간표가 없는 상태에서 새 시간표를 만들 때 대표로 자동 지정할지는 다음 논의로 남긴다. 이번 추가는 의사결정 기록이며 실제 시간표 코드 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 시간표가 없는 상태에서 생성해도 대표는 직접 지정한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 기존 사용자가 시간표가 없는 상태에서 새 시간표를 생성하는 경우

### 비교와 결정

새 시간표를 대표로 자동 지정하는 방식과 대표 없이 생성하고 사용자가 직접 지정하는 방식을 비교했다. 사용자는 두 번째 방식을 선택했다.

1. 사용자의 활성 시간표가 하나도 없는 상태에서 새 시간표를 만들어도 대표로 자동 지정하지 않는다. 대표 없이 생성한 뒤 사용자가 명시적으로 대표를 지정할 수 있도록 한다.
2. 대표 없음 상태를 유지할 수 있으며, 첫 시간표라는 이유로 대표 지정을 강제하지 않는다.
3. 신규 가입 시 기본 시간표를 생성하는 기존 결정은 유지한다. 이번 선택은 기존 사용자의 시간표 재생성 시 대표 자동 지정 여부에 관한 결정이며 가입 시 기본 시간표의 정책까지 변경하지 않는다.

### 근거와 기록 상태

대표가 없는 상태를 허용한다는 직전 결정에 맞춰, 시간표 재생성과 대표 지정을 별도 사용자 선택으로 다룬다. 대표 시간표를 사용하려면 직접 지정해야 하는 비용을 수용한다.

이번 추가는 의사결정 기록이며 실제 시간표 코드 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 기본 시간표 생성의 직접 호출과 원자성을 안쪽 흐름에서 유지한다

- 상태: Accepted
- 결정일: 2026-10-13
- 기준: [클린 아키텍처 적용 결정](2026-10-13-clean-architecture-policy.md)

가입 시 기본 시간표를 동기적으로 직접 생성하고 사용자 저장과 같은 DB 트랜잭션으로 처리하는 기존 결정을 유지한다. 안쪽 가입 처리 흐름에서 시간표 생성 기능을 호출하고 필요한 저장 계약을 사용한다. Spring 빈·구체 JPA 어댑터 의존성과 트랜잭션 실행은 바깥 구성·실행 영역에서 연결한다. 같은 안쪽 애플리케이션 계층의 직접 호출을 이유로 이벤트 방식으로 되돌리지 않는다.

분반·학기 제한 없음, 대표 삭제 금지·대표 해제 허용, 시간표 없음 허용, 기존 사용자의 재생성 시 대표 직접 지정 등 지금까지 정한 시간표 동작은 유지한다. 이번 추가는 기술 배치 보완이며 실제 코드 변경이나 테스트 실행은 하지 않았다.
