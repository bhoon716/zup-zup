# 줍줍 통합 운영 대시보드

## 요구와 선택

사용자는 기존 Grafana 대시보드를 하나의 진입점으로 정리하고 실제 화면까지 검증하도록 요청했다. 지표 생산·API·인증 설정은 유지하며 기존 쿼리·변수·링크·알림 참조의 보존을 우선한다.

운영에서 받은 클래식 JSON 3개(사용자 운영판 v21/30패널, 메트릭 v5/33패널, Loki v4/7패널)를 해시와 함께 로컬 작업 산출물에 백업했다. 저장소 Grafana JSON·프로비저닝 5개도 별도 백업했다. 사용자 운영판의 `zup-zup-operations` UID와 기존 데이터 패널 ID 23개를 유지하고 이 판을 파일 프로비저닝의 원본으로 추가한다. 다른 두 판은 삭제하지 않고 `[이전 보기]` 제목과 통합판 링크로 보존한다.

새 UID로 또 다른 주 대시보드를 만드는 대안은 기존 링크와 패널 참조를 나누고 진입점 수를 늘린다. 기존 운영판을 유지하는 선택은 해당 판을 이제 저장소에서 관리한다는 비용이 있다. UI에서 수정한 내용을 다음 CD에서도 보존하려면 저장소 JSON에도 반영해야 한다.

## 구성과 보존 경계

서비스 요약, HTTP, 서버/JVM, DB/Redis, 강의 수집, 알림 전달, Loki 로그의 7개 행을 둔다. 요약·HTTP는 기본 펼침, 나머지는 접힌 상태다. 기존 판에서 동일한 유형·조회·시간 모드·변환을 가진 20개 중복 패널은 운영판 하나로 대표한다. 다른 시간 범위나 누적/비율 의미를 가진 패널은 유지한다. 운영판 23개, 다른 판의 고유 10개, 설명/기존 scrape 상태 2개로 표시 패널은 35개다.

- 지연 6개 패널은 평균/min/max/p50/p95/p99 조회를 그대로 유지한다. min은 미계측 `NaN`/N/A, max는 수집된 계측 창의 최대이며 정확한 모든 개별 요청 극값이 아니다.
- `up`은 기존 Prometheus 앱 scrape 상태를 표시하며 DB·Redis readiness를 뜻하지 않는다.
- Redis의 상세 지표는 이 대시보드에 미구성이라고 명시한다. 0값·추정값·새 exporter는 추가하지 않는다. 앱 `/health`의 DB·Redis 의존성 검사와 구분한다.
- 운영 로그의 범위/레벨, 전체 로그의 서비스/검색, 요청 추적의 Correlation ID 등 기존 변수 5개를 모두 유지한다. 각 필터가 적용되는 패널은 제목에 표시한다.
- 원래 UID/패널 ID를 참조하는 기존 링크·주석·알림의 대상은 삭제하지 않는다. datasource·alert rule·알림 전송 설정은 수정하지 않는다.

Grafana 기본 홈 경로는 새 원본 파일로 지정한다. 기존 사용자/조직의 별도 홈 선택은 임의로 덮어쓰지 않는다. 공급자의 `disableDeletion=true`로 파일 제거가 DB 대시보드 삭제로 이어지지 않게 한다. 이미지·보안·자격 증명·접근 권한은 유지한다.

## 검증과 배포

기존 observability 계약에서 UID·패널 ID 중복·원래 ID 보존·이전 패널 쿼리 포함·변수·지연 통계·홈 경로·삭제 방지를 확인한다. 실제 운영 버전이 백업 이후 바뀌지 않았는지 배포 전 읽기 대조한다. 정상 CI/CD 후 접힘/펼침·표시·로그 검색을 브라우저에서 확인한다. 유효한 쿼리의 빈 결과와 쿼리 오류를 구분한다.

사용자 요청으로 SSH 원인과 OCI IP 확인은 중단했다. 대시보드 정리와 무관한 네트워크 조사는 재개하지 않는다.

## 복구

구현 전 백업 위치는 작업 산출물 `grafana-unified-20261028/backups/`이며 `manifest.json`에 원본 해시가 있다. 운영판 백업은 `operating/zup-zup-operations.classic.json`이다. 정의만 포함하며 실제 로그 행·자격 증명은 저장소에 넣지 않는다.

통합 화면을 되돌릴 때는 새 원본 파일을 단순 삭제하기보다 같은 경로/UID에 백업 운영판 정의를 복원하고 `disableDeletion=true`를 유지한다. 과거 release의 `disableDeletion=false`로 함께 되돌리면 이제 관리 대상으로 등록한 운영판의 삭제 위험이 있으므로 전체 소스 rollback 전에 확인한다. 이전 두 대시보드는 계속 조회 가능하며 DB 복원은 정상적인 화면 복구에 필요하지 않다.

## 구현 전 검증 기록

서버 `check bootJar`(Java 21)는 단위 테스트 559개와 Checkstyle/PMD를 포함해 통과했다. observability 계약과 나머지 infra 계약도 로컬에서 검증한다. 배포 직전 브라우저의 읽기 API에서 운영 정의 버전이 백업과 동일한 v21/v5/v4임을 확인했다. 실제 배포·화면 결과는 작업 산출물에 별도로 기록하며, 이 기록만으로 미실행 검증을 통과로 간주하지 않는다.

## 사용자 정정: JSON import와 DB 관리로 전환

사용자는 저장소의 파일 프로비저닝 방식에 반대하고, JSON 파일을 작성한 뒤 Grafana에서 import하여 직접 편집하도록 명시했다. 위 파일 관리 선택은 더 이상 현재 정책이 아니다. Clarity 검색 응답 보완과 이전 도메인 네 설정은 유지하며 PR 전체를 되돌리지 않는다.

통합 정의는 작업 산출물 `grafana-db-import-20261028/zup-zup-operations.import.json`으로 보관한다. 활성 `infra/grafana/dashboards`에서는 통합판 JSON을 제거하고 파일 기반 홈 경로도 제거한다. 이전 메트릭·Loki 파일의 제목/링크 변경과 통합판 파일 검사를 되돌린다. 기존 두 파일의 unrelated 프로비저닝은 삭제하지 않는다.

`disableDeletion=true`는 DB 정의·UID·이력 보존을 위해 유지한다. Grafana 13.1.0의 `handleMissingDashboardFiles`는 이 설정에서 사라진 파일의 DB 대시보드를 삭제하지 않고 `UnprovisionDashboard`로 관리 기록만 제거한다. 이것은 `editable=true`로 파일 재동기화를 숨기는 방식이 아니다. 다음 CD에도 동일 UID가 활성 JSON에 없어야 하며 계약 검사에서 이를 보호한다.

운영 전환 전 서버의 비공개 `/var/backups/zup-zup-grafana-db-import-20261028T073318Z`에 SQLite backup API로 만든 DB 사본과 Compose·공급자·원본 JSON 및 해시를 보관했다. API 기반 백업 읽기는 401로 중단했고 그 요청을 재시도하지 않았다. 비밀번호 재설정이나 토큰·권한 변경은 하지 않는다.

정상 후속 배포로 파일 관리를 해제한 다음 같은 UID로 import한다. 브라우저 UI에서 소규모 설명 수정·저장·새로고침과 프로비저닝 재읽기 이후에도 저장 내용이 유지되는지 확인한다. 홈 진입점은 필요 시 Grafana DB의 기존 사용자/조직 환경설정으로 선택하며 파일 경로를 다시 추가하지 않는다. 대시보드 삭제·DB 전체 복원은 정상 전환에 사용하지 않는다.
