# 결정: 공지는 운영자가 수동으로 공개·비공개를 변경한다

- 상태: Accepted
- 결정일: 2026-10-08
- 범위: 공지의 게시 방식
- 관련 코드: `apps/server/src/main/java/bhoon/sugang_helper/campus/announcement/`

## 문제와 확인한 사실

백엔드 재설계에서 공지의 공개 시점을 운영자가 직접 변경할지, 예약 게시 기능을 추가할지 결정한다. 인지 부채와 근거 없는 기술 도입을 줄이기 위해 실제 요구가 확인되지 않은 기능은 추가하지 않는다.

현재 코드의 공지 엔티티와 등록·수정 요청에는 `published` 공개 여부가 있으며, 예약 게시 시각은 없다. 서비스는 등록·수정 요청의 공개 여부를 저장하고 공개 조회에서는 공개된 공지만 반환한다. 이는 저장소 코드에서 확인한 사실이며 운영 환경의 동작을 별도로 검증한 것은 아니다.

## 검토한 대안

| 대안 | 장점 | 부담 |
| --- | --- | --- |
| 운영자가 수동으로 공개·비공개 변경 | 현재 방식이 단순하고 공개 시점을 직접 통제할 수 있음 | 원하는 시각에 운영자가 직접 변경해야 함 |
| 예약 게시 추가 | 미리 지정한 시각에 공개할 수 있음 | 예약 시각, 예약 변경·취소, 실행 실패 처리를 설계하고 운영해야 함 |

## 결정

- 운영자가 직접 공개·비공개를 변경하는 현재 방식을 유지한다.
- 공개하면 게시되고, 비공개하면 공개 조회에서 숨긴다.
- 이번 재설계에서는 예약 게시 기능을 추가하지 않는다.
- 원하는 시각의 자동 게시가 실제로 필요해지면 예약 기능을 다시 검토한다.

## 영향과 후속 논의

게시 방식의 선택으로 예약 실행 작업과 관련 상태를 추가할 필요가 없다. 운영자는 게시 시점에 직접 공개 여부를 변경해야 한다.

공개 공지의 익명 조회 허용 여부, 정렬, 보존, 공지 알림, 첨부 지원은 이번 결정으로 확정하지 않는다. 공개 여부를 생략한 등록 요청의 기본값도 별도 검토 사항이다.

이번 기록에서는 코드·설정을 변경하거나 테스트를 실행하지 않았다.

## 추가 결정: 공개 공지는 로그인 없이 조회한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 공지 목록·상세의 조회 권한

### 검토와 결정

공개 공지를 누구나 조회하는 방식과 로그인 사용자만 조회하는 방식을 비교했다. 로그인 제한은 조회 대상을 줄일 수 있지만, 가입 전 서비스 안내나 점검 공지를 확인하려는 사용자도 로그인해야 한다.

사용자는 현재 방식인 로그인 없는 공개 공지 조회를 선택했다.

- 공개된 공지의 목록과 본문은 로그인 없이 조회할 수 있다.
- 비공개 공지는 운영자만 조회할 수 있다. 일반 사용자는 로그인 여부와 관계없이 조회할 수 없다.
- 비공개 공지는 공개 목록에서 제외하며, ID로 직접 상세 조회를 요청해도 공개하지 않는다.
- 공지의 작성·수정·공개 여부 변경 등 관리 기능은 운영자 권한으로 유지한다.

### 근거와 영향

서비스 안내 성격의 공개 공지는 가입·로그인 전에도 확인할 수 있게 한다. 공개 내용은 누구나 조회할 수 있다는 전제로 운영자가 게시한다.

저장소 코드의 `SecurityConfig`는 공지 GET 경로를 인증 없이 허용하고, `AnnouncementService`는 공개 목록과 상세 조회를 공개 상태로 제한한다. 관리자 컨트롤러는 ADMIN 권한을 요구한다. 운영 환경의 실제 동작은 별도로 검증하지 않았다.

이 추가 결정은 앞서 후속 논의로 남긴 익명 조회 여부를 확정한다. 공지 등록 시 기본 공개 상태 등 나머지 미정 사항은 별도로 논의한다. 이번 변경은 문서 기록이며 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 새 공지는 기본 공개로 등록한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 새 공지 등록 시 기본 공개 상태

### 검토와 결정

기본 비공개로 저장한 뒤 별도로 공개하는 방식과 등록 시 기본 공개하는 방식을 비교했다. 기본 비공개는 초안의 실수 노출을 줄이지만 게시를 위한 추가 변경이 필요하다. 기본 공개는 바로 게시할 수 있지만 비공개로 저장하려는 운영자가 공개 설정을 직접 변경해야 한다.

사용자는 기본 공개를 선택했다.

- 새 공지 등록 시 공개 상태를 기본으로 한다.
- 운영자가 비공개를 명시하면 비공개로 저장한다.
- 등록 요청에서 공개 여부를 생략하면 공개로 처리하는 현재 방식을 유지한다.
- 기본 공개로 등록된 공지는 앞서 결정한 조회 정책에 따라 로그인 없이 조회할 수 있다.

### 근거와 영향

등록 후 바로 게시하는 흐름을 유지한다. 비공개 초안을 저장하려는 운영자는 등록 전에 비공개를 선택해야 한다.

현재 `AnnouncementRequest.isPublishedOrDefault()`는 공개 여부가 없거나 참이면 공개로 처리한다. 이번 결정은 새 공지 등록의 기본값에 한정하며, 수정 요청에서 공개 여부를 생략했을 때의 처리와 공지 알림 발송 여부까지 확정하지 않는다.

이 추가 결정으로 앞서 미정으로 남긴 새 공지 등록 시 기본 공개 상태를 확정한다. 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 운영자가 선택한 공지는 영구 알림으로 안내한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 공지 알림의 제공 여부와 전달 수단
- 관련 결정: [영구 알림함 정책](2026-10-01-persistent-notification-inbox.md)

### 검토와 결정

공지를 화면에서만 제공하는 방식과 운영자가 선택한 공지만 알림으로 안내하는 방식을 비교했다. 사용자는 선택한 공지를 알리는 방식을 택하되, 전달 수단을 외부 채널이 아닌 영구 알림으로 지정했다.

- 운영자가 알림을 보내기로 선택한 공지만 사용자의 영구 알림함에 저장한다.
- 공지 알림은 이메일·Discord·웹 푸시 등 외부 채널로 발송하지 않는다.
- 공지가 기본 공개로 등록된다는 이유만으로 모든 공지의 알림을 자동 생성하지 않는다. 공지 공개 여부와 알림 생성 여부는 별도로 취급한다.
- 영구 알림에는 기존 알림함의 읽음·안읽음, 모두 읽음, 소프트 삭제·보존 정책을 적용한다.

### 영향과 후속 논의

사용자는 알림함에서 운영자가 안내하기로 선택한 공지를 확인할 수 있다. 외부 채널을 통한 능동적인 전달은 제공하지 않는다.

수신 사용자 범위, 알림 내용과 공지 연결 방식, 최초 게시·수정·재공개 시 생성 규칙, 비공개 전환·삭제 시 기존 알림 처리, 알림 생성 기본 선택값은 후속 논의로 남긴다. 비공개 공지는 운영자만 조회한다는 앞선 권한 정책을 유지한다.

이번 결정은 공지 알림에 한정한다. 여석 알림과 문의 답변의 기존 외부 채널 정책을 변경하지 않는다. 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 공지 영구 알림의 수신 대상은 전체 미탈퇴 회원으로 한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 공지 영구 알림의 수신 사용자 범위

### 검토와 결정

전체 회원에게 공지 알림을 남기는 방식과 운영자가 특정 회원·조건을 선택하는 방식을 비교했다. 전체 회원 대상은 규칙이 단순하고 서비스 공통 안내에 적합하다. 대상 선택 방식은 관련 사용자에게만 안내할 수 있지만 선택 기능과 조건 관리가 필요하다.

사용자는 전체 회원 대상을 선택했다.

- 운영자가 알림을 보내기로 선택한 공지의 영구 알림은 탈퇴하지 않은 전체 회원을 대상으로 한다.
- 공지 알림의 수신 대상을 운영자가 특정 회원이나 조건으로 제한하는 기능은 이번 범위에 추가하지 않는다.
- 외부 알림 채널의 연결·활성화 여부를 수신 조건으로 요구하지 않는다. 공지 알림은 앞서 결정한 대로 영구 알림함에만 저장한다.
- 탈퇴한 계정과 비회원에게 개인 영구 알림을 생성하지 않는다. 비회원도 공개 공지는 기존 공개 조회 정책에 따라 볼 수 있다.

### 영향과 후속 논의

서비스 공통 공지를 동일한 기준으로 안내할 수 있지만, 일부 회원은 자신과 관련 없는 공지도 받을 수 있다.

이후 가입한 회원에게 과거 공지 알림을 추가할지와 수신 대상 확정 시점·저장 처리 방식은 후속 논의로 남긴다. 이번 결정은 수신 범위만 확정하며 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 신규 가입자에게 과거 공지 알림을 소급 생성하지 않는다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 가입 이전 공지 알림의 소급 제공 여부

### 검토와 결정

가입 이후의 공지 알림부터 제공하는 방식과 현재 유효한 과거 중요 공지까지 가입 시 알림함에 추가하는 방식을 비교했다. 과거 공지를 포함하면 신규 회원에게도 이전 안내를 전달할 수 있지만, 포함할 공지와 유효 기간 기준이 필요하다.

사용자는 과거 알림을 추가하지 않는 방식을 선택했다.

- 신규 가입자에게 가입 이전의 공지 알림을 소급 생성하지 않는다.
- 신규 가입자는 가입 이후 생성되는 공지 알림부터 수신 대상에 포함된다. 알림 생성 시점의 전체 미탈퇴 회원을 대상으로 한다는 범위를 적용한다.
- 과거 공개 공지는 공지 목록·상세에서 기존 조회 정책에 따라 확인할 수 있다.
- 신규 가입을 계기로 과거 공지를 선별하거나 개인 알림을 채워 넣는 절차는 추가하지 않는다.

### 영향과 후속 논의

가입 직후 과거 알림이 쌓이지 않고 수신 규칙이 단순해진다. 신규 회원이 이전의 중요한 공지를 확인하려면 공지 목록을 이용해야 한다.

이미 게시된 공지를 나중에 처음 알림으로 안내하거나 수정·재공개 시 다시 안내할 수 있는지는 별도 논의 사항이다. 수신 대상 선정과 알림 저장의 구체적인 처리 방식도 이번 결정으로 확정하지 않는다. 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 공지당 한 번만 영구 알림을 생성한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 같은 공지의 수정·재공개에 따른 재알림 여부

### 검토와 결정

공지당 한 번만 알림으로 안내하는 방식과 운영자가 수정·재공개 시 재알림을 선택할 수 있는 방식을 비교했다. 재알림을 허용하면 같은 공지의 중요한 변경을 다시 전달할 수 있지만, 반복 안내와 실수로 재알림할 가능성이 생긴다.

사용자는 공지당 한 번만 알림을 생성하는 방식을 선택했다.

- 운영자가 알림을 보내기로 선택한 공지는 한 번만 영구 알림으로 안내한다. 대상 회원마다 해당 공지의 알림을 한 건 생성하는 의미다.
- 이미 알림으로 안내한 공지의 내용을 수정하거나 비공개 후 다시 공개해도 새 알림을 생성하지 않는다.
- 같은 공지에 대해 운영자가 재알림을 보내는 기능은 추가하지 않는다.
- 중요한 정정·추가 안내를 다시 알릴 필요가 있으면 새 공지를 작성하고 해당 공지의 알림 생성을 선택한다.

### 영향과 후속 논의

같은 공지의 수정·재공개로 알림이 반복되지 않는다. 기존 알림을 읽음 상태에서 안읽음 상태로 되돌려 재알림하는 동작도 추가하지 않는다.

아직 알림을 생성하지 않은 기존 공지에서 최초 알림 생성을 언제 허용할지, 공지 수정 시 기존 알림에 표시되는 내용, 비공개 전환·삭제 시 기존 알림 처리는 후속 논의로 남긴다. 알림 저장 작업의 재시도·중복 방지 방식은 상세 설계에서 정하며, 작업 재시도를 사용자에게 새 알림을 제공하는 근거로 삼지 않는다. 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 공지 비공개 전환·삭제 시 관련 영구 알림도 숨긴다

- 상태: Accepted
- 결정일: 2026-10-10
