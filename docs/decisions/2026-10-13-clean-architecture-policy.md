## 사용자 요구와 적용 기준

사용자는 ‘클린아키텍처 사용할게. 지금까지 클린아키텍처에서 벗어나는 결정 있으면 수정해’라고 요청했다. 기존의 인지 부채 감소 목표와 함께, 업무 규칙을 외부 구현으로부터 분리하는 의존성 방향을 재설계의 기준으로 확정한다.

원문에서 확인한 핵심 기준은 소스 의존성이 안쪽의 정책을 향하며, 안쪽의 업무 코드가 바깥의 DB·웹·프레임워크 구현과 그 데이터 형식을 알지 않도록 하는 것이다. 아래의 구체적인 배치는 이 기준을 이 프로젝트에 적용한 결정이다. 모든 클래스에 인터페이스를 만드는 것이 원문의 필수 조건이라고 해석하지 않는다.

## 경계와 의존성

| 영역 | 책임 | 의존성 기준 |
| --- | --- | --- |
| 도메인 | 강의·평가·구독 등 업무 상태와 규칙 | Spring·JPA·HTTP·Redis·메일·로깅 프레임워크 구현을 참조하지 않음 |
| 애플리케이션 | 유스케이스, 처리 순서, 재시도·취소·보존 정책, 필요한 입출력 계약 | 도메인과 안쪽에서 정의한 계약·데이터에 의존 |
| 어댑터 | HTTP 변환, DB 영속화, 학교 요청, 메일·Discord·웹 푸시, Redis·파일 처리 | 안쪽 계약을 구현하거나 호출하며 기술별 형식을 변환 |
| 실행·구성 | Spring 빈 조립, 트랜잭션 실행, 스케줄·worker 실행과 종료, 기술 설정 | 어댑터와 유스케이스를 연결하고 운영 기술을 관리 |

```text
소스 의존성:
웹·스케줄 어댑터 → 유스케이스 → 도메인
                         ↓
                   안쪽의 출력 계약
                         ↑ 구현
                  DB·외부 연동 어댑터

실행 시에는 유스케이스가 출력 계약을 통해 바깥 어댑터를 호출할 수 있다.
```

패키지명·빌드 모듈 수·서비스 분할 수를 이번 결정으로 고정하지 않는다. 기존 단일 배포·단일 발송 worker 운영을 유지하며, 이를 위해 새 프레임워크나 MQ를 도입하지 않는다.

## 변경·정정할 결정

### 1. 저장소 인터페이스 통합을 철회하고 안쪽 계약을 유지한다

1. 업무 서비스가 `JpaRepository`를 직접 사용하는 이전 통합 결정을 대체한다. 안쪽의 저장소 계약과 바깥의 Spring Data 저장소를 구분한다.
2. 영속성 어댑터가 안쪽 계약을 구현하고 Spring Data 저장소를 사용한다. 안쪽 계약은 업무에 필요한 작업만 표현하며 Spring Data를 상속하지 않는다.
3. 현행 `RepositoryContract`의 `Page`·`Pageable`, JPA의 영속성 처리 방식을 드러내는 계약도 정리한다. 업무상 필요한 원자성·경합 보장은 계약에 표현하되 구체적인 SQL·잠금·flush 구현은 어댑터에서 담당한다.
4. 현재처럼 JPA 애너테이션이 있는 객체를 그대로 순수 도메인으로 삼는 구조도 전환 대상이다. 도메인 모델과 JPA 영속성 모델을 구분하고 필요한 변환을 어댑터가 담당한다. 조회 전용 경로는 안쪽에서 정의한 조회 DTO로 직접 매핑할 수 있다.
5. 기존 DB 제약·쿼리·잠금·트랜잭션 의미와 데이터 보존 정책은 유지해야 한다. 분리를 이유로 원자성이나 동시성 보장을 낮추지 않는다.

### 2. 강의 조회 계약 제거 제안은 채택하지 않는다

직전에 설명한 ‘`CourseCatalogQuery`를 제거하고 구체 조회 서비스를 직접 주입’하는 안은 아직 사용자에게 확정받지 않은 제안이었다. 확정된 과거 결정의 철회로 기록하지 않는다.

이 프로젝트의 기능 간 강의 조회에는 안쪽의 `CourseCatalogQuery` 계약과 순수 조회 DTO를 유지한다. 조회 유스케이스는 안쪽 저장소·검색 계약을 사용하며 JPA 구현을 직접 참조하지 않는다. 같은 애플리케이션 계층 안에서 구체 클래스를 직접 호출하는 것 자체가 항상 위반인 것은 아니며, 모든 서비스에 대응 인터페이스를 일괄 추가하지 않는다.

### 3. 업무 오류와 HTTP 응답을 분리한다

업무 오류 종류와 필요한 데이터를 안쪽에서 정의하고, HTTP 상태·오류 JSON·요청별 오류 ID 및 표시 문구와의 연결은 웹 어댑터에서 처리한다. 서버가 안내 문구를 관리하는 기존 요구는 유지한다. 현재 `ErrorCode`가 `HttpStatus`를 포함한 채 업무 코드에 사용되는 구조는 전환 대상이다.

### 4. 업무 코드에 Spring·영속성·통신·로깅 구현을 배치하지 않는다

`@Service`, `@Transactional`, Spring Security·Servlet 객체, JPA 애너테이션, QueryDSL 타입, `RestClient`, `JavaMailSender`, Redis 클라이언트, `MultipartFile`, Jackson의 외부 JSON 표현과 로거·지표 구현을 업무 코어의 의존성으로 사용하지 않는다. 구성·웹·영속성·외부 연동 어댑터에서 연결한다. Lombok의 getter·생성자·빌더는 기존에 허용한 컴파일 보조 기능으로 유지하고, 로거 생성은 바깥 영역에 한정한다.

## 동작을 유지하면서 기술 배치를 보완할 결정

### 같은 DB 트랜잭션과 직접 호출

- 강의 갱신+여석 outbox, 사용자 가입+기본 시간표, 문의·답변+영구 알림+outbox, 최종 실패+실패 안내의 원자적 저장을 유지한다.
- 트랜잭션은 바깥 실행 어댑터·데코레이터에서 시작해 관련 유스케이스와 같은 DB의 영속성 어댑터가 참여하도록 구성한다. 유스케이스에 Spring 트랜잭션 구현을 주입하는 대신 필요한 원자적 처리 범위를 명확히 둔다.
- 여석 감지 후 outbox 기록은 동기적인 직접 호출을 유지하고, 안쪽의 기록 계약을 통해 저장한다. 가입 시 기본 시간표 생성도 같은 안쪽 처리 흐름에서 직접 호출할 수 있다. 클린 아키텍처를 이유로 Spring 이벤트·비동기 처리로 되돌리지 않는다.
- 학교 HTTP 요청·외부 발송·파일 처리의 기존 DB 트랜잭션 밖 실행 경계를 유지한다. 어댑터 분리를 이유로 외부 호출 전체를 DB 트랜잭션으로 감싸지 않는다.

### 외부 채널 발송

- `NotificationSender`, 채널별 대상 타입, 명시적인 발송 결과는 안쪽에서 정의하는 출력 계약과 순수 데이터로 유지한다.
- 이메일·Discord·웹 푸시 발송기는 바깥 어댑터로 배치한다. `JavaMailSender` 유지와 채널별 실제 발송 코드 공유를 유지하되 코어가 구체 발송기를 직접 참조하는 형태는 사용하지 않는다.
- 외부 예외·응답은 어댑터에서 기존 정책에 필요한 성공·일시적 실패·설정 오류·불확실 결과 및 대기시간 요구로 변환한다. 원인 미확정 시 책임을 임의로 단정하지 않는다.
- 스케줄·스레드·메모리 작업 확보·종료 제어는 바깥 실행 영역에, 시도 횟수·다음 시각·완료·취소·재등록 대기 등의 판단은 안쪽 유스케이스·도메인에 둔다. 총 10회·고정 1분·10초 호출 제한·5초 poll·100개 확보·한 번에 하나 발송은 유지한다.

### 검색·수집·인증·파일

- QueryDSL은 검색 어댑터 내부에서 사용한다. 코어의 조회 계약은 자체 검색 조건·조회 결과·페이지 요청을 사용하며 Spring `Page`·`Slice`·`Pageable`이나 JPA 엔티티를 경계 데이터로 전달하지 않는다. 검색 캐시 없이 DB 조회·무한 스크롤 정책은 유지한다.
- 학교 요청의 RestClient·쿠키·압축·JSON 파싱은 외부 수집 어댑터에서 담당한다. 코어에는 정규화한 강의 데이터와 필요한 실패 정보가 전달된다. Jsoup 제거와 이미 확인한 전환 결과를 취소하지 않는다.
- Google OAuth·Spring Security·HTTP 세션·CSRF·쿠키·리다이렉트 처리는 웹·인증 어댑터에서 담당한다. Redis 세션 및 코드 저장은 바깥 구현에 두고, 업무 코어에는 필요한 사용자·권한·코드 검증 데이터와 계약을 제공한다. 소유권·구독 제한 같은 업무 권한 검사는 코어에서도 수행한다.
- 인증 이메일은 기존대로 요청 처리에서 동기적으로 보내고 DB 트랜잭션 밖에서 호출한다. 코드 생성·만료·검증은 유스케이스가 정책을 관리하고, Redis 저장과 실제 메일 발송은 출력 계약으로 연결한다.
- 첨부의 HTTP 업로드 객체·파일 경로·이미지 디코더는 바깥에서 처리한다. 크기·형식·소유권·등록 성공 조건은 기존 요구대로 검증하고, 코어는 필요한 파일 저장·조회·정리 계약과 중립적인 첨부 정보를 사용한다.
- 변경 로그·진단·지표는 실행·어댑터에서 출력한다. 코어의 업무 결과나 필요한 기록 계약으로 정보를 제공하고 SLF4J·Micrometer를 코어에 직접 연결하지 않는다. 기존 로그만 기록·보관 기간 정책은 유지하며 DB와 로그의 원자적 보존을 새로 보장하지 않는다.

## 비용과 상세 설계 범위

순수 도메인과 영속성 모델의 변환, 출력 계약·어댑터, Spring 조립·트랜잭션 실행 코드가 필요하다. 이 비용을 아키텍처 선택에 따른 비용으로 수용한다. 실제 외부 경계를 보호하는 계약과 단순한 같은 계층의 호출을 구분하고, 구현이 하나라는 이유만으로 계약을 제거하거나 클래스마다 일률적으로 인터페이스를 추가하지 않는다.

구체적인 패키지 구성, 전환 순서와 기존 데이터·성능에 영향을 주는 매핑·쿼리 변경은 상세 설계에서 정한다. 원자성·기존 정책을 바꾸어야 하는 문제가 발견되면 별도 의사결정으로 남긴다.

## 기록과 구현 상태

과거 문서는 수정·삭제하지 않고 관련 문서 끝에 변경·보완 결정을 추가한다. 같은 범위에서 과거의 직접 프레임워크 의존 허용과 충돌하면 이번 결정과 관련 문서의 최신 추가 내용을 우선 적용한다.

이번 작업은 의사결정과 계획의 정정이다. 실제 서버·프론트 코드·DB·실행 설정의 클린 아키텍처 전환을 완료한 것은 아니다. 테스트를 추가하거나 실행하지 않았다. 기존 사용자 지침의 단위 테스트·최종 E2E만 수행하는 원칙을 유지한다.

기능별로 묶고 내부에서 계층을 구분하는 방식과 계층별로 묶고 내부에서 기능을 구분하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 강의·평가·시간표·구독·알림 등 기능을 중심으로 패키지를 묶고, 각 기능 내부에서 도메인·애플리케이션·어댑터의 책임을 구분한다.
2. 도메인에는 업무 상태와 규칙, 애플리케이션에는 유스케이스와 안쪽의 입출력 계약을 둔다. 웹·영속성·외부 연동 어댑터는 필요한 기능 내부에서 구분한다.
3. Spring 조립과 실행 설정은 바깥 구성 영역에서 연결한다. 예시의 `domain`, `application`, `adapter`, `bootstrap` 이름은 책임을 설명하는 것이며 세부 명칭·하위 폴더 수를 일괄 고정하지 않는다.
4. 기존 `academic/course`, `planning/timetable` 같은 기능 중심 구분을 전환의 출발점으로 활용한다. 기존 모든 패키지를 그대로 유지하거나 실제 책임과 무관하게 이름만 옮기는 결정으로 해석하지 않는다.
5. 기능 간 의존성도 안쪽 계약을 기준으로 관리하며 도메인·유스케이스가 바깥 어댑터를 참조하지 않도록 한다. 기능별 패키지 배치만으로 의존성 규칙이 자동 강제된다고 간주하지 않는다.
6. 단일 앱 배포와 기존 worker 운영 정책은 유지한다. 빌드 모듈 분리 여부는 이번 선택에 포함하지 않으며 별도로 비교한다.

### 근거와 수용한 비용

한 기능을 이해하고 수정할 때 관련 코드를 가까이 두고 현재 기능 구분을 활용한다. 같은 계층 전체를 확인할 때 기능별 패키지를 살펴야 하고, 기능 간 참조 경계를 관리해야 하는 비용을 수용한다.

이번 추가는 의사결정 기록이며 실제 패키지 이동·빌드 설정 변경이나 테스트 실행은 하지 않았다.

이번 추가는 의사결정 기록이며 실제 Gradle 설정·패키지·서버 코드 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 현재 서버에서 기능별로 클린 아키텍처로 전환한다

- 상태: Accepted
- 결정일: 2026-10-13
- 범위: 백엔드 재설계 코드의 전환 방식

### 비교와 결정

현재 서버 안에서 기능별로 전환하는 방식과 별도 위치에서 새 백엔드를 작성한 뒤 운영 서버를 교체하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 현재 서버에서 한 기능 흐름의 도메인·유스케이스·계약·어댑터를 함께 전환하고 다음 기능으로 진행한다. 서버의 단일 Gradle 모듈과 기능별 패키지 구성 결정을 적용한다.
2. 기존 클래스 보존을 전환의 목표로 삼지 않는다. 합의한 기능 동작과 의존성 경계를 기준으로 필요한 코드는 새로 작성하고 적합한 코드는 활용할 수 있다.
3. 전환 중 기존 구조와 새 구조가 함께 존재하는 비용을 수용한다. 접점은 안쪽 계약과 바깥 구현의 연결로 관리하고, 새 업무 코어가 기존 Spring·JPA 구현에 직접 의존하도록 타협하지 않는다.
4. 기능 전환 시 기존 사용자 데이터·대기 알림·API와 프론트 사용처의 전환을 함께 설계한다. 기존 데이터나 발송 작업을 초기화하는 방식으로 전환 부담을 피하지 않는다.
5. 교체한 경로와 남은 사용처를 확인한 뒤 불필요해진 이전 코드·연결을 정리한다. 두 구현이 같은 업무를 중복 실행하지 않도록 전환하며, 단일 발송 worker 운영과 기존 트랜잭션·복구 정책을 유지한다.
6. 첫 번째 전환 기능과 이후 순서는 이번 선택으로 확정하지 않는다. 앞서 예시로 제시한 수집·강의 갱신·outbox 기록은 가능한 전환 단위를 설명한 것이다.

### 근거와 수용한 비용

한 기능의 전체 흐름을 이해하고 변경 범위를 작게 확인하면서 진행한다. 기존 구조와 새 구조의 접점·호환성과 정리를 관리해야 하는 비용을 수용한다. 이 선택은 현재 합의한 요구·클린 아키텍처에 따른 새 결정이며, 과거 철회된 최초 계획의 구조·CRUD 우선 순서를 재채택하는 뜻이 아니다.

이번 추가는 의사결정 기록이며 실제 기능 교체·코드 작성·DB 전환이나 테스트 실행은 하지 않았다.

## 추가 결정: 첫 전환은 수집·강의 갱신·outbox 기록으로 한다

- 상태: Accepted
- 결정일: 2026-10-13
- 범위: 클린 아키텍처로 전환할 첫 기능 흐름
- 구현 계획: [첫 전환 구현 계획](../backend-redesign-first-slice-plan.md)

수집·강의 갱신·outbox 기록, 인증·계정, 문의·첨부·답변 중에서 사용자는 첫 번째 흐름을 선택했다.

1. 학교 수집 → 전체 결과 검증 → 강의 갱신·좌석 이력·여석 발생 outbox 기록을 첫 전환 범위로 정한다.
2. 순수 모델·유스케이스·저장소 계약·외부 수집 어댑터·영속성 어댑터·바깥 트랜잭션 실행을 이 흐름에서 구체화한다. 수집 전부 검증 후 같은 DB 트랜잭션으로 반영하고, outbox는 안쪽 계약으로 동기 직접 기록한다.
3. 첫 단위의 끝은 outbox 기록이다. 기존 발송 worker가 새 기록과 기존 대기 작업을 이어받도록 호환 접점을 설계한다. 발송 worker·수신자 선정·채널 처리의 전체 재설계 완료까지 첫 범위에 포함하지 않는다.
4. 기존 검색·평가·찜·시간표 등 강의 사용처의 기능 정책을 유지하도록 접점을 확인한다. 첫 전환에 필요한 연결 변경과 이후 기능의 전체 전환을 구분한다.
5. 인증·계정·문의 및 발송 worker 등의 나머지 전체 구현 순서는 이번 선택으로 확정하지 않는다.

기존에 가장 많이 논의한 핵심 흐름에서 외부 호출 분리와 DB 원자적 저장 경계를 구체적으로 확인한다. 이번 추가는 범위 확정과 계획 기록이며 실제 서버 코드·DB 변경이나 테스트 실행은 하지 않았다.
