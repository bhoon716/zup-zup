# 결정: 기능별 MVC 레이어드 구조로 정리한 뒤 기능 코드를 전환한다

- 상태: Accepted
- 결정일: 2026-10-13
- 범위: 백엔드 아키텍처, 현재 변경 취소, 폴더 정리와 기능 재설계의 실행 순서
- 대체 결정: [클린 아키텍처의 강제 경계](2026-10-13-clean-architecture-policy.md)
- 관련 자료: [MVC 패키지 이동 목록](../backend-mvc-package-moves.md), [재설계 계획](../backend-redesign-plan.md)

## 사용자 요구

사용자는 클린 아키텍처 전환이 너무 복잡하다고 설명하고, 기능별로 묶은 뒤 내부를 `entity/`, `controller/`, `repository/`, `service/` 등으로 나누는 MVC 레이어드 구조를 요청했다. 이어 현재 변경 사항을 취소하고 폴더 구조부터 정리한 다음, 합의한 기능 설계대로 코드를 변경하도록 순서를 명시했다.

## 결정

1. 직전에 진행한 미커밋 클린 아키텍처 구현은 취소한다. 작업 전 커밋 `7149c32b`를 동작의 기준으로 삼으며, 그 전에 커밋한 RestClient 전환과 재설계 의사결정은 보존한다.
2. 전체 백엔드의 기능별 패키지를 유지하고 그 안을 MVC 레이어드 역할로 정리한다. 먼저 파일·package·import·관련 QueryDSL 및 테스트 참조 경로를 옮긴다.
3. 현재 단계에서는 업무 로직·메서드·API·테이블·트랜잭션·이벤트 흐름을 변경하지 않는다. 최초 구현 중 추가했던 순수 모델·출력 계약·트랜잭션 실행기·수집 모드 UI·신규 migration은 취소 대상이다.
4. 폴더 정리 후 기존 기능 결정을 기준으로 코드 전환을 진행한다. 첫 기능 전환 대상인 수집 → 강의 갱신 → outbox 기록은 유지한다. 현재 이벤트 기반 기록을 직접 호출로 바꾸는 기능 변경도 후속 구현에서 진행한다.

## 역할별 배치

| 폴더 | 책임 |
| --- | --- |
| `entity/` | JPA 엔티티와 영속성 모델. 필요한 업무 상태·동작을 함께 둘 수 있음 |
| `controller/` | HTTP 요청 처리와 응답 연결 |
| `repository/` | 저장소 인터페이스, Spring Data JPA·QueryDSL·JDBC 조회 구현 |
| `service/` | 업무 처리, 기능 간 호출, 트랜잭션 조합 |
| `dto/` | 요청·응답·조건·명령·조회 데이터 |
| `client/` | 학교 API·이메일·Discord·웹 푸시 등 외부 연동 |
| `enums/` | 기능에서 사용하는 열거형 |
| `scheduler/` | 예약 실행·worker 진입점 |
| `event/`, `exception/`, `handler/` | 기존 이벤트·예외·웹 인증 핸들러 등 필요한 역할 |

공통 설정·보안·웹 필터·도구는 공통 역할 폴더에서 관리한다. 비공개 서비스 내부 보조 타입은 접근 범위를 유지하도록 관련 서비스와 함께 둔다. 별도 `readmodel/course`의 강의 검색 저장소는 강의 기능의 `repository/`로 모은다. 빈 역할 폴더를 일괄 만들지 않는다.

예시:

```text
academic/course/
  entity/
  controller/
  repository/
  service/
  dto/
  enums/

academic/crawling/
  entity/
  controller/
  repository/
  service/
  dto/
  client/
  scheduler/
```

## 이전 아키텍처 결정과의 관계

- 업무 코어의 완전한 프레임워크 독립을 위해 JPA 모델을 별도로 복제하거나 입출력 포트·어댑터를 강제하는 클린 아키텍처 기준은 철회한다.
- 서비스의 Spring·Spring Data 사용, 서비스의 `@Transactional`·로거 사용, JPA 엔티티의 직접 사용을 허용한다. 기존 기술 선택과 실제 책임을 기준으로 단순한 흐름을 구성한다.
- 계약과 구현이 나뉜 기존 저장소·조회·발송 인터페이스는 이번 폴더 정리에서 통합·삭제하지 않는다. 기능 코드를 바꿀 때 실제 역할을 보고 정리한다. 클린 아키텍처를 위한 분리 자체를 유지 조건으로 삼지 않는다.
- 단일 Gradle 모듈, 기능별 구성, 단일 앱·발송 worker, 기능별 전환 방향은 유지한다.
- 여석 알림 조건·채널·재시도·구독·보존·계정·평가·문의 등 사용자 동작에 관한 결정은 유지한다. 아키텍처 변경을 기능 정책 변경으로 확대하지 않는다.
- 기존 테이블 구조를 고정할 필요가 없다는 추가 허용도 유지한다. 필요한 스키마 변경은 후속 구현에서 신규 Flyway migration과 데이터 이전으로 관리한다. 현재 폴더 정리에서는 스키마를 변경하지 않는다.

## 이유와 실행 순서

사용자가 이해하고 수정하기 어려워진 추상화·계약·모델 변환 부담을 줄이기 위해 MVC 레이어드 구조를 선택했다. Spring·영속성 기술에 대한 의존성을 수용한다. 먼저 위치를 정리하여 폴더 변경과 업무 동작 변경의 영향을 나누어 확인하고 이후 실제 기능을 전환한다.

과거 의사결정은 수정·삭제하지 않고 이 변경 결정을 우선 적용한다. 관련 문서에도 최신 아키텍처의 적용 범위를 추가한다. 폴더 정리의 검증은 소스 본문 보존과 컴파일 확인이며, 이번 요청에서 테스트를 추가하거나 실행하지 않는다.

## 추가 결정: 요청·응답 DTO 분리와 빈 폴더 정리

- 결정일: 2026-10-13
- 상태: Accepted

사용자 요청에 따라 기능별 `dto/` 안에서 요청 DTO는 `request/`, 응답 DTO는 `response/`로 구분한다. 기존 `*Request` 24개와 `*Response` 38개의 package·import 및 해당 기존 테스트 경로를 함께 변경한다. 명령·조건·공유 조회 데이터 등 요청·응답 전용이 아닌 내부 데이터 타입은 `dto/`에 유지한다.

이동과 이전 구현 취소 뒤 남은 빈 프로젝트 폴더도 삭제한다. Git 내부 및 무시된 빌드·도구·의존성 폴더는 정리 대상에서 제외한다.

## 추가 범위: Swagger 전체 제거

사용자는 폴더 정리 중 코드의 Swagger 관련 요소도 모두 제거하도록 요청했다. [기존 Springdoc 전체 제거 결정](2026-10-11-api-documentation-policy.md#추가-결정-springdoc-전체를-제거한다)을 이번 작업에서 구현한다. 앞선 폴더 정리 범위에 이 제거 작업을 추가하며, 실제 기능 API의 요청 검증·인증·응답 형식과 업무 처리는 유지한다.

## 추가 범위: 중복 저장소 통합

사용자는 폴더 정리 후 합칠 수 있는 저장소도 합치도록 요청했다. 앞서 저장소 계약 통합을 후속 작업으로 남긴 실행 순서를 변경하여, 중복 JPA 계약 25쌍과 단일 구현의 조회 계약 두 곳을 현재 단계에서 통합한다. 상세 범위는 [저장소 인터페이스 통합 결정](2026-10-13-repository-interface-policy.md#추가-결정-및-구현-중복-저장소-인터페이스를-현재-단계에서-통합한다)을 따른다. 쿼리·잠금·트랜잭션·DB 구조·업무 정책은 유지한다.


## 추가 결정: DTO를 실제 역할에 따라 request·response·result와 별도 범주로 분류한다

- 결정일: 2026-10-27
- 상태: Accepted — 현재 사용자 DTO 정리 요청 범위

사용자는 DTO를 request/response/result에 정리하고 셋에 맞지 않는 것은 의미 있는 별도 폴더에 두도록 요청했다. API 입력·출력·내부 결과를 호출부와 JSON 경계로 구분하며, 접미사만으로 이동하지 않는다. 이미 올바르게 분류된 타입과 command/criteria/external/provider/diagnostic의 구분을 유지한다.

현재 누락된 내부 결과 SeatNotificationDeliveryDispatch·SeatNotificationDeliveryFailureResult·SanitizedImage는 dto/result로, HealthCheckResponse는 common/dto/response로 이동했다. 필요한 public 접근성과 import만 조정하고 HTTP JSON·업무 동작·DB·설정을 바꾸지 않는다. 영구 알림함의 미완성 변경을 완성·삭제하지 않으며 이번 요청으로 commit/push/배포를 하지 않는다.

이동 목록·기존 미커밋과의 구분·검증 결과 및 기존 전체 테스트 컴파일 차단은 [작업 기록](../dto-package-classification-20261027.md)에 남긴다.


## 후속 승인: DTO 분류 변경만 로컬 커밋한다

- 결정일: 2026-10-27
- 상태: Accepted — DTO 변경의 선택적 로컬 커밋에 한정

사용자가 DTO 정리 변경만 커밋하도록 추가 승인했다. 영구 알림함 초안·다른 변경·기존 테스트 오류 수정은 포함하지 않는다. 혼합 파일은 DTO import만 선택적으로 스테이징하고 기존 미커밋 작업 보존을 확인한다. push·merge·배포는 하지 않는다.
