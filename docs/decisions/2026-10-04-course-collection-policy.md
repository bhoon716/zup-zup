# 결정: 수집 실패 시 마지막 정상 정보를 유지하고 다음 주기에 재시도한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 강의 수집 실패 시 데이터 보존·여석 알림 생성·재시도와 사용자 갱신 지연 표시
- 대체 결정: 없음
- 관련 자료: [재설계 논의 계획](../backend-redesign-plan.md), [여석 발생 사실 발송](2026-10-01-seat-alert-occurrence-notification.md)

## 문제와 목표

강의 수집에 실패했을 때 기존 정보를 어떻게 다루고, 사용자에게 수집 상태를 표시할지 정한다. 기능 동작과 큰 처리 흐름을 먼저 합의한다.

## 결정

1. 수집에 실패하면 마지막으로 정상 수집한 강의 정보를 유지한다. 실패 때문에 기존 정보를 지우거나 여석 상태를 바꾸지 않는다.
2. 수집 실패 자체로 여석 발생 알림을 만들지 않는다. 정상 수집에서 만석에서 여석으로 바뀐 사실을 확인했을 때 알리는 기존 조건을 적용한다.
3. 수집 실패 후 다음 수집 주기에 다시 시도한다. 구체적인 수집 주기는 별도 논의한다.
4. 수집 실패에 따른 갱신 지연을 사용자에게 별도로 표시하지 않는다. 사용자에게 갱신 지연을 표시하자는 제안은 채택하지 않았다.

## 근거와 결과

- 사용자는 마지막 정상 정보 유지와 다음 주기 재시도에 동의했고, 사용자에게 갱신 지연을 표시하는 부분은 제외하도록 요청했다.
- 마지막 정상 정보가 남아 있어 수집 실패 중에도 강의 정보를 제공할 수 있다. 수집 실패 동안 저장된 정보와 실제 상태가 달라질 수 있다는 제약을 수용한다.
- 이 결정은 수집 실패 시 표시 정책이다. 기존 여석 알림 메시지의 일반적인 수집·전달 시차 안내는 [관련 결정](2026-10-01-seat-alert-occurrence-notification.md)에 따른다.

## 기록과 구현 상태

사용자의 결정을 저장 여부를 별도로 묻지 않고 기록했다. 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다. 세부 실패 처리와 구현은 상세 설계에서 정리한다.

## 추가 결정: 강의 수집 주기는 5분으로 한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 강의 정보를 수집해 여석 변화를 확인하는 주기

### 결정

1. 강의 수집 주기를 5분으로 한다. 수집 실패 시 마지막 정상 정보를 유지하고 다음 수집 주기에 다시 시도하는 기존 정책을 적용한다.
2. 수집 실패에 따른 갱신 지연을 사용자에게 별도로 표시하지 않는 기존 결정을 적용한다.
3. 5분은 강의 수집 주기다. 발송 worker의 DB 조회 간격 5초와 외부 발송 실패 후 재시도 간격 1분은 각각의 기존 정책에 따른다.
4. 수집을 상시 운영할지 특정 기간에 운영할지는 아직 정하지 않았다. 이번 결정은 수집 주기에 대한 합의다.

### 근거와 기록 상태

- 운영 설정 파일의 수집 예약이 5분 간격임을 확인하고 이를 초기 정책값으로 제안했으며, 사용자가 5분을 선택했다. 실제 운영 서버의 실행 주기나 이 값의 적정성을 측정한 것은 아니다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 여석 감지용 수집은 수강 신청·정정 기간에만 운영한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 5분 주기의 여석 감지용 수집 운영 기간

### 비교와 결정

| 방식 | 동작 | 선택 |
| --- | --- | --- |
| 상시 5분마다 수집 | 신청 기간 밖에도 여석 감지용 수집을 계속 실행 | 채택하지 않음 |
| 수강 신청·정정 기간에만 수집 | 알림이 필요한 기간에 5분 주기로 수집 | 사용자 선택 |

1. 여석 감지용 강의 수집은 수강 신청·정정 기간에만 5분 주기로 운영한다. 기간 밖에는 해당 5분 주기 수집을 중단한다.
2. 해당 기간의 수집 실패는 기존 정책대로 마지막 정상 정보를 유지하고 다음 수집 주기에 재시도한다. 사용자에게 수집 실패에 따른 갱신 지연을 별도로 표시하지 않는다.
3. 수집 운영 기간 종료는 이미 생성된 여석 알림 작업의 취소 사유로 사용하지 않는다. 기존 대기 작업은 재시도·성공·취소·최종 실패 등 합의한 발송 정책에 따라 계속 처리한다.
4. 기간 밖에도 검색·시간표 등에 필요한 기본 강의 정보를 어떻게 갱신할지는 별도 논의한다. 수강 신청·정정 기간의 지정·관리 방식도 아직 정하지 않았다.

### 근거와 기록 상태

- 여석 감지용 수집을 수강 신청·정정 기간에 집중하는 제안과 상시 운영을 비교한 뒤 사용자가 기간 내 운영하는 2번을 선택했다.
- 실제 운영 기간의 날짜·시간이나 학교 일정의 자동 연동을 확정한 결정은 아니다. 기능 정책과 큰 흐름을 먼저 정하고 구체적인 관리·실행 방식은 이후 설계한다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 신청·정정 기간 밖에는 하루 1회 기본 강의 정보를 자동 갱신한다

- 결정일: 2026-10-04
- 범위: 여석 감지용 수집 운영 기간 밖의 기본 강의 정보 갱신

### 비교와 결정

| 방식 | 처리 | 선택 |

| 하루 1회 자동 갱신 | 기간 밖에도 검색·시간표 등에 필요한 강의 정보를 정기적으로 갱신 | 사용자 선택 |
| 필요할 때 관리자 수동 갱신 | 운영자가 필요한 시점마다 직접 수집 | 채택하지 않음 |

1. 수강 신청·정정 기간 밖에는 검색·시간표 등에 필요한 기본 강의 정보를 하루 1회 자동 갱신한다.
2. 이 기간 밖의 갱신에서는 새 여석 알림을 생성하지 않는다. 이미 생성되어 대기 중인 알림은 기존 발송 정책대로 계속 처리한다.
3. 수집에 실패하면 마지막 정상 정보를 유지하고 다음 수집 주기에 다시 시도한다. 수집 실패에 따른 사용자 갱신 지연 표시는 추가하지 않는다.
4. 수강 신청·정정 기간에는 앞서 결정한 5분 주기 여석 감지용 수집을 적용한다. 하루 1회 갱신의 구체적인 실행 시각과 대상 학기는 상세 설계에서 정한다.

### 근거와 기록 상태

- 관리자가 매번 갱신을 실행하지 않아도 기본 강의 정보에 변경을 반영하는 방향을 제안했고, 사용자가 하루 1회 자동 갱신하는 1번을 선택했다. 이 빈도의 적정성을 운영 측정으로 검증한 것은 아니다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 등록된 기간에 따른 자동 전환을 기본으로 하고 관리자 수동 전환도 지원한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 강의 수집 운영 기간 관리와 수집 모드 전환

1. 관리자가 수강 신청·정정 기간의 시작·종료 일시를 등록하면, 시스템이 등록된 기간에 따라 수집 운영을 자동 전환한다. 이 방식을 기본 운영 방식으로 한다.
2. 자동 운영 시 등록된 기간 안에서는 5분 주기의 여석 감지용 수집을 수행하고, 기간 밖에서는 하루 1회 기본 강의 정보를 갱신한다. 기간 밖의 기본 갱신에서는 새 여석 알림을 생성하지 않는다.

4. 수동 전환의 유지 기간과 자동 운영으로 돌아가는 기준은 아직 정하지 않았다. 이미 생성된 대기 알림은 수집 모드 전환과 별개로 기존 발송 정책에 따라 처리한다.

### 근거와 기록 상태

- 사용자는 기간 등록에 따른 자동 전환을 기본으로 선택하면서, 관리자 직접 전환도 가능하도록 요청했다. 자동 운영으로 반복적인 전환 작업을 줄이고 필요 시 운영자가 조정할 수 있도록 한다.
- 실제 학교 일정의 자동 수집·추출을 도입하는 결정은 아니다. 관리자가 지정한 기간을 기준으로 운영한다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

### 결정

1. 관리자가 수집 모드를 수동 전환할 때 종료 시각을 지정한다. 수동 모드는 해당 종료 시각까지 유지한다.
2. 지정한 종료 시각 이후에는 등록된 일정에 따른 자동 운영으로 복귀한다. 복귀 시점의 수강 신청·정정 기간 여부에 따라 5분 주기 여석 감지용 수집 또는 하루 1회 기본 정보 갱신을 적용한다.
3. 관리자가 해제할 때까지 종료 시각 없이 수동 모드를 유지하는 방식은 이번 결정으로 채택하지 않는다. 구체적인 입력·검증·전환 구현은 상세 설계에서 정리한다.

### 근거와 기록 상태

- 수동 설정 해제를 잊어도 자동 운영으로 돌아갈 수 있는 종료 시각 지정 방식을 제안했고, 사용자가 1번을 선택했다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 변경 결정: 설정 페이지에서 수집 운영을 직접 변경하고 즉시 반영한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 수집 모드의 관리·적용 방식
- 대체 범위: 위 '등록된 기간에 따른 자동 전환을 기본으로 하고 관리자 수동 전환도 지원한다' 및 '관리자 수동 전환은 지정한 종료 시각까지만 유지한다'의 기간 등록·자동 전환·종료 시각·자동 복귀 정책
- 관련 결정: [통합 일정 정책](2026-10-10-campus-schedule-policy.md)

### 변경 배경과 결정

사용자는 수집을 일정으로 관리하지 않고, 설정 페이지에서 필요할 때 직접 변경하며 변경 즉시 반영하도록 요청했다. 기존 내용은 이력으로 남기고 수집 모드의 관리·적용 방식에는 이번 결정을 적용한다.

1. 운영자가 설정 페이지에서 수집 운영 모드를 직접 변경한다. 표시용 일정이나 별도로 등록한 시작·종료 기간에 따라 자동 전환하지 않는다.
2. 설정 변경은 저장 성공 시 즉시 적용한다. 배포·서버 재시작이나 다음 수집 주기까지 기다렸다가 설정을 반영하는 방식으로 하지 않는다.
3. 별도의 수동 전환 종료 시각을 요구하지 않고, 운영자가 다시 변경할 때까지 선택한 모드를 유지한다. 기간 종료에 따른 자동 복귀를 추가하지 않는다.
4. 기존에 정한 모드별 동작은 유지한다. 여석 감지용 모드는 5분 주기 수집과 여석 발생 감지를 수행하고, 기본 정보 갱신 모드는 하루 1회 갱신하며 새 여석 알림을 생성하지 않는다. 신청·정정 기간에 맞춘 모드 선택은 운영자가 수행한다.
5. 수집 실패 시 마지막 정상 정보를 유지하고 다음 주기에 재시도하며, 사용자에게 갱신 지연을 별도로 표시하지 않는 정책을 유지한다.
6. 수집 설정 변경을 이유로 이미 생성된 대기 알림을 취소하지 않는다. 기존 작업은 합의된 발송 정책에 따라 처리한다.
7. 통합 일정의 등록·수정·삭제·복원이나 대표 D-Day 위젯 표시 여부는 수집 운영 모드를 변경하지 않는다.
