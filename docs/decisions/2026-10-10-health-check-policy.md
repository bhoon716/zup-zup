# 결정: 헬스체크 범위에 학교 서버와 알림 서비스를 포함한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 백엔드 상태 확인의 대상
- 대체 결정: 없음
- 관련 자료: [백엔드 재설계 체크리스트](../backend-redesign-checklist.md), [수집 실패 처리 정책](2026-10-04-course-collection-policy.md), [알림 전달 정책](2026-10-01-notification-at-least-once-delivery.md)

## 문제와 목표

서버 상태 확인에서 애플리케이션 응답만 볼지, 저장소와 외부 의존 서비스까지 확인할지 결정한다. 운영자가 서비스 구성 요소의 문제를 파악할 수 있도록 상태 확인 범위를 정한다.

## 확인된 사실과 미해결 사항

- 사용자는 앱 상태와 DB·Redis 상태를 구분하는 방식, 앱 응답만 확인하는 방식, 외부 서비스까지 확인하는 방식 중 세 번째를 선택했다.
- 전체 상태의 집계 방식, 외부 서비스별 확인 수단·주기·제한시간 및 배포·재시작과의 연결은 아직 선택하지 않았다.
- 이번 기록은 재설계 방향이며 실제 외부 서비스 상태를 확인한 결과가 아니다.

## 선택지 비교

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 앱 상태와 DB·Redis 연결 상태를 분리하여 확인 | 앱 자체 문제와 저장소 연결 문제를 구분하기 좋음 | 학교 서버·알림 서비스는 별도로 확인해야 함 |
| 앱 응답만 확인 | 상태 확인이 단순함 | 앱이 응답해도 저장소·외부 서비스 문제로 실제 기능이 실패할 수 있음 |
| 외부 서비스까지 포함하여 확인 | 학교 수집과 외부 알림에 필요한 의존 서비스까지 파악 가능 | 확인 요청·실패 처리와 전체 상태 집계 기준이 필요함 |

## 결정

1. 상태 확인 범위에 애플리케이션, DB, Redis뿐 아니라 학교 서버와 이메일·Discord·웹 푸시의 외부 알림 서비스를 포함한다.
2. 이번 선택은 확인 대상의 범위를 정한다. 하나의 외부 서비스가 실패했을 때 전체를 장애로 표시할지, 부분 장애로 구분할지 또는 구성 요소별 상태만 제공할지는 후속 논의로 정한다.
3. 외부 의존 서비스의 상태를 확인한다는 이유만으로 실제 사용자에게 테스트 알림을 보내는 동작을 승인한 것은 아니다. 서비스별 연결 확인, 인증 상태 확인, 최근 실제 호출 결과 활용 등 구체적인 확인 방법은 상세 설계에서 정한다.
4. 상태 확인 실패만으로 발송 작업을 취소·최종 실패 처리하거나 수집 데이터를 삭제하지 않는다. 수집의 마지막 정상 데이터 유지와 알림의 기존 재시도·최종 실패 정책은 유지한다.

## 근거와 결과

사용자는 확인 범위를 외부 서비스까지 넓히는 방식을 선택했다. 외부 의존성의 상태도 운영자가 확인할 수 있도록 하고, 확인 방식과 집계·운영 연결을 설계하는 비용을 수용한다.

학교 서버·알림 서비스의 문제가 전체 상태에 영향을 줄 수 있다는 비교 내용을 바탕으로 선택했으나, 이 선택만으로 모든 외부 실패를 앱 자체 장애로 처리하거나 자동 재시작하는 규칙을 확정하지 않는다.

## 구현과 후속 논의

- 구성 요소별 확인 수단, 확인 대상 웹 푸시 서비스의 범위, 실행 주기·제한시간·요청량과 최근 결과의 유효기간을 정한다.
- 상태 집계와 표시, 공개·운영 전용 경로의 노출 범위, 배포·트래픽 수신·재시작 판단과의 연결은 별도로 정한다.
- 이번 변경은 의사결정 기록이며 실제 외부 확인 요청·테스트 알림 발송, 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 재검토 조건

상태 확인 자체의 요청량이나 외부 장애로 인한 잘못된 운영 판단이 문제가 되는 경우 대상과 확인 방법을 재검토한다.

## 변경 결정: 앱 상태와 DB·Redis 연결 상태를 분리하여 확인한다

- 상태: Accepted
- 결정일: 2026-10-10
- Supersedes: 위 ‘헬스체크 범위에 학교 서버와 알림 서비스를 포함한다’ 결정의 확인 범위

### 정정과 결정

사용자는 앞선 3번 선택을 ‘아 1번’으로 정정했다. 현행 재설계 방향은 앱 상태와 DB·Redis 연결 상태를 분리하여 확인하는 첫 번째 방식이다. 앞선 선택은 이력으로 남기고 이번 변경 결정을 우선 적용한다.

1. 애플리케이션 자체가 응답할 수 있는 상태와 DB·Redis 연결 상태를 구분하여 확인한다.
2. DB·Redis 연결 문제를 앱 자체의 응답 불가와 동일한 상태로 뭉뚱그리지 않는다. 구체적인 상태 표현과 서비스 요청 처리 준비 여부의 판단은 상세 설계에서 정한다.
3. 학교 서버와 이메일·Discord·웹 푸시 외부 서비스는 헬스체크 대상에 포함하지 않는다. 해당 문제는 실제 수집·발송 결과, 운영 지표와 로그를 통해 별도로 확인한다.
4. 앞선 외부 서비스 확인 수단·주기·제한시간 및 외부 실패를 포함한 전체 상태 집계 논의는 이번 헬스체크의 후속 구현 요구로 유지하지 않는다.
5. 수집의 마지막 정상 데이터 유지와 발송 재시도·최종 실패 정책은 유지한다. 헬스체크 결과만으로 작업을 취소하거나 데이터를 삭제하지 않는다.

### 근거와 후속 논의

사용자의 정정에 따라 앱 자체 문제와 저장소 연결 문제를 구분하는 방식을 선택한다. 외부 서비스에 대한 확인 요청과 집계 규칙을 헬스체크에 추가하는 부담을 줄인다.

공개·운영 전용 경로의 노출 범위, DB·Redis 확인 방식·주기·제한시간과 배포·트래픽 수신·재시작 판단과의 연결은 별도로 정한다. 이번 선택만으로 특정 장애 시 자동 재시작하거나 모든 요청을 차단하는 규칙을 확정하지 않는다.

이번 변경은 의사결정 기록이며 실제 상태 확인 요청, 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 기본 상태 확인은 공개하고 상세 상태는 운영 환경에서만 확인한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 헬스체크 API의 접근·정보 공개 범위

### 검토와 결정

기본 응답만 공개하고 상세 상태는 운영 전용으로 제공하는 방식과 기본·상세 상태 모두 운영 전용으로 제한하는 방식을 비교했다. 사용자는 공개의 의미가 대시보드 표시가 아니라 API 주소에 접근할 수 있는 범위임을 확인한 뒤 첫 번째 방식을 선택했다.

1. 앱 자체의 응답 가능 여부를 확인하는 기본 상태 API는 인터넷에서 외부 호출할 수 있도록 공개한다. 이 API에는 최소한의 상태 확인 결과를 제공한다.
2. DB·Redis 각각의 연결 상태 등 상세 상태는 서버 내부 또는 허용된 운영·모니터링 환경에서만 확인할 수 있게 접근을 제한한다. 상세 상태 API를 인터넷에서 누구나 호출할 수 있게 공개하지 않는다.
3. 공개 기본 응답에 내부 구성 요소별 상태, 상세 오류 원인이나 비밀값을 노출하지 않는다.
4. 이번 결정은 API 접근 범위에 관한 것이다. 관리자 대시보드에 상태 표시 영역을 추가하는 결정은 아니다.
5. 앱 상태와 DB·Redis 연결 상태를 분리하는 앞선 결정을 유지한다. 학교 서버와 외부 알림 서비스는 헬스체크 대상에 포함하지 않는다.

### 근거와 후속 논의

외부에서는 앱의 응답 여부를 간단히 확인하고, 구성 요소별 연결 문제의 진단은 접근이 제한된 운영 환경에서 수행한다.

상세 경로의 접근 제한 수단, 실제 경로·포트·응답 형식, 점검 주기·제한시간과 배포·재시작 연계는 상세 설계 또는 후속 논의에서 정한다. ‘운영 전용’이라는 표현만으로 서비스의 관리자 로그인 인증을 접근 제한 수단으로 확정하지 않는다.

이번 변경은 의사결정 기록이며 실제 경로 공개·접근 설정 변경, 코드 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 앱 종료 또는 지속적인 내부 무응답 시 자동 재시작한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 앱 상태 확인과 자동 재시작의 연결
- 참고 자료: [Spring Boot의 외부 상태 확인과 liveness 구분](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.kubernetes-probes.external-state)

### 검토와 결정

앱 종료·지속적 무응답 시 자동 재시작하는 방식, 앱 종료 시에만 자동 재시작하는 방식, 자동 재시작 없이 운영자가 조치하는 방식을 비교했다. 사용자는 앱 종료·지속적 무응답 시 자동 재시작하는 방식을 선택했다.

1. 앱 프로세스가 종료되면 자동 재시작한다.
2. 앱이 실행 중이어도 서버 내부의 앱 자체 상태 확인에서 지속적으로 응답하지 않으면 자동 재시작한다. 한 번의 점검 실패나 일시적인 지연만으로 즉시 재시작하는 규칙은 채택하지 않는다.
3. DB·Redis 연결 실패는 그 자체로 앱 자동 재시작의 조건으로 삼지 않는다. 앱 자체 상태 확인과 저장소 연결 상태를 분리하는 기존 정책을 따른다.
4. 인터넷에서 앱에 접근하지 못했다는 사실만으로 앱 자체가 멈췄다고 단정하여 재시작하지 않는다. 지속적인 무응답 판단은 서버 내부 점검을 기준으로 한다.
5. 학교 서버·외부 알림 서비스는 헬스체크 및 앱 자동 재시작 판단의 대상에 포함하지 않는다.

### 근거와 후속 논의

운영자가 직접 확인할 때까지 기다리지 않고 앱 종료·멈춤에서 복구할 수 있도록 한다. 일시적 지연과 지속적인 무응답을 구분할 기준 및 자동 재시작 운영 구성이 필요하다. Spring Boot 공식 문서도 외부 저장소 등의 장애를 앱의 liveness 판단에 연결하여 반복 재시작하는 문제를 경고한다. 이 문서를 참고한다는 이유로 Kubernetes 등 특정 운영 기술을 도입하는 결정은 아니다.

점검 주기·제한시간·연속 실패 기준, 시작 중 대기시간, 재시작 간격·반복 제한과 운영자 안내는 후속 설계에서 정한다. 앱이 종료·무응답인 상황에서도 동작할 앱 외부의 재시작 수단은 실제 운영 구성을 확인해 정하며, 이번 선택만으로 새 운영 시스템을 도입하지 않는다.

재시작 후 미완료 발송 작업을 DB에서 복구하고 기존 시도 횟수를 유지하는 정책은 그대로 적용한다. 성공 여부가 불확실한 외부 발송의 중복 가능성을 이번 재시작 결정으로 제거한다고 보장하지 않는다.

이번 변경은 의사결정 기록이며 실제 앱 재시작, 코드·배포·운영 설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 장애 안내는 장애 전용 Discord 채널로 보낸다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 운영자가 받는 장애 안내의 수신 경로
- 관련 결정: [문의의 운영용 Discord 안내](2026-10-07-feedback-policy.md)

### 검토와 결정

기존 문의 안내용 Discord 채널에 함께 보내는 방식, 장애 전용 Discord 채널을 사용하는 방식, 운영자 이메일로 보내는 방식을 비교했다. 사용자는 장애 전용 Discord 채널을 선택했다.

1. 운영자 장애 안내는 문의 안내 채널과 분리된 장애 전용 Discord 채널로 보낸다.
2. 기존 문의·작성자 추가 메시지 안내는 기존에 선택한 운영용 Discord 채널을 유지한다. 이번 선택으로 두 안내를 같은 채널에 통합하지 않는다.
3. 장애 안내는 앱이 종료되거나 무응답인 상황에도 동작할 수 있도록 앱 외부에서 감지·발송할 수 있게 설계한다. 구체적인 감지·발송 도구는 아직 선택하지 않았다.
4. 이메일·관리자 개인 Discord 연결을 추가 수신 경로로 자동 등록하지 않는다. 실제 Discord 채널과 발송 연결 설정은 상세 설계에서 정한다.

3. 재시작 요청이나 프로세스 실행만으로 정상 복구라고 안내하지 않는다. 해당 장애 대상의 상태 확인 결과를 기준으로 복구를 판단한다.

2. 장애가 계속되는 동안 주기적 점검에서 같은 실패가 확인되더라도 장애 지속 안내를 반복해서 생성하지 않는다.
