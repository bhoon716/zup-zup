# 결정: 문의·피드백은 작성자와 운영자만 조회한다

- 상태: Accepted
- 결정일: 2026-10-07
- 범위: 문의·건의·버그 제보와 답변의 공개 범위
- 대체 결정: 없음
- 관련 자료: [FeedbackController](../../apps/server/src/main/java/bhoon/sugang_helper/support/feedback/presentation/FeedbackController.java), [AdminFeedbackController](../../apps/server/src/main/java/bhoon/sugang_helper/support/feedback/presentation/AdminFeedbackController.java), [FeedbackService](../../apps/server/src/main/java/bhoon/sugang_helper/support/feedback/application/FeedbackService.java), [탈퇴 시 문의·답변·첨부 보존 정책](2026-10-04-authentication-policy.md)

## 문제와 목표

문의·피드백을 작성자와 운영자 사이의 소통으로 제공할지, 사용자가 공개·비공개를 선택할 수 있는 기능으로 확대할지 정한다.

## 확인된 현재 동작

- 일반 사용자 API는 내 피드백 목록·상세·첨부 조회를 제공한다. 서비스는 상세·첨부 조회 시 작성자와 요청 사용자의 일치 여부를 검사한다.
- 관리자 조회는 별도 컨트롤러에서 제공하고 관리자 권한을 요구한다.
- 이번에 확인한 현재 동작은 코드 기준이며, 배포된 서비스의 접근 제어를 실행 검증한 것은 아니다.

## 선택지 비교

| 방식 | 동작 | 장점·제약 |
| --- | --- | --- |
| 작성자·운영자만 조회 | 문의와 답변을 당사자끼리 확인 | 권한 규칙이 단순하지만 다른 사용자가 같은 문의를 참고하기 어려움 |
| 공개·비공개 선택 | 공개한 문의는 다른 사용자도 조회 | 건의·버그와 답변을 공유할 수 있지만 공개 전환과 첨부 노출 규칙이 추가로 필요 |

## 결정

1. 문의·피드백과 답변은 해당 작성자와 권한을 가진 운영자만 조회할 수 있도록 한다. 일반 사용자에게 다른 사용자의 문의 목록·본문·답변을 공개하지 않는다.
2. 문의에 연결된 첨부도 같은 접근 범위를 적용한다. 구체적인 다운로드 경로와 운영자의 보존 자료 열람 방식은 상세 설계에서 정한다.
3. 초기 재설계에서는 작성자의 공개·비공개 선택 기능과 공개 문의 게시판을 추가하지 않는다. 공개적으로 공유할 필요가 확인되면 기능 확장을 재검토한다.
4. 탈퇴 시 문의·관리자 답변과 첨부를 소프트 삭제하고 보존하는 기존 정책을 적용한다. 보존된 기록의 일반 사용자 접근과 운영 조회의 세부 조건은 기존 계정 정책 및 후속 설계에 따른다.

## 근거와 결과

- 현재 본인·관리자 조회 흐름을 확인하고, 문의 기능과 권한 규칙을 단순하게 유지하는 1번을 제안했다. 사용자가 작성자·운영자만 조회하는 방식을 선택했다.
- 다른 사용자가 기존 문의를 참고하기 어려운 제약을 수용하며, 공개 공유 기능의 필요성이 확인되면 재검토한다.

## 기록과 구현 상태

- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기록하고 결정 목록에 추가했다.
- 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: JPEG·PNG 외의 이미지 형식도 첨부할 수 있도록 확대한다

- 상태: Accepted
- 결정일: 2026-10-07
- 범위: 문의 첨부파일에서 허용할 이미지 형식의 범위
- 관련 자료: [LocalFileUploadService](../../apps/server/src/main/java/bhoon/sugang_helper/common/util/LocalFileUploadService.java), [ImageUploadSanitizer](../../apps/server/src/main/java/bhoon/sugang_helper/common/util/ImageUploadSanitizer.java)

### 확인과 결정

1. 문의 첨부의 허용 범위를 JPEG·PNG에만 제한하지 않고 다른 이미지 형식으로도 확대한다. 허용 범위는 이미지 파일을 기준으로 한다.
2. 현재 코드의 허용 MIME 목록은 JPEG·PNG이며, 사용자 요청은 그 밖의 이미지 형식을 추가하는 방향이다. 구체적인 추가 지원 형식 목록은 이번에 확정하지 않고 상세 설계에서 정리한다.
3. 추가 형식의 검증·저장·표시 방식과 기존 이미지 처리 코드·의존성의 변경 범위를 해당 형식의 실제 요구에 맞춰 정한다. 이번 기록만으로 모든 이미지 형식이 현재 구현에서 처리 가능하다고 보장하지 않는다.
4. 문의 첨부의 작성자·운영자 접근 범위와 기존 계정 정책의 보존 규칙을 적용한다.

### 근거와 기록 상태

- 현재 JPEG·PNG만 허용함을 설명하고 범위를 비교했다. 사용자는 JPEG·PNG와 함께 다른 이미지들도 허용하도록 요청했다.
- 사용자의 요청을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 본문과 모든 첨부가 저장돼야 문의 등록을 성공으로 처리한다

- 상태: Accepted
- 결정일: 2026-10-07
- 범위: 문의 등록 중 본문·첨부 저장 실패의 사용자 결과
- 관련 자료: [FeedbackService](../../apps/server/src/main/java/bhoon/sugang_helper/support/feedback/application/FeedbackService.java), [LocalFileUploadService](../../apps/server/src/main/java/bhoon/sugang_helper/common/util/LocalFileUploadService.java)

### 비교와 결정

| 방식 | 동작 | 장점·제약 |
| --- | --- | --- |
| 문의 등록 전체 실패 | 본문과 모든 첨부가 저장돼야 등록 성공 | 성공의 의미와 흐름이 단순하지만 실패하면 다시 제출해야 함 |
| 본문과 성공한 첨부만 등록 | 실패한 첨부를 안내하고 나머지는 접수 | 본문은 먼저 접수되지만 부분 성공과 재첨부 흐름의 관리가 필요 |

1. 첨부가 있는 문의는 본문과 선택한 모든 첨부의 파일·연결 정보가 정상 저장된 경우에만 등록 성공으로 처리한다. 첨부가 없는 문의는 본문 저장을 기준으로 처리한다.
2. 등록 처리 중 본문 또는 첨부 저장에 실패하면 부분 접수 성공으로 응답하지 않는다. 본문과 일부 첨부만 등록된 상태를 사용자에게 정상 접수된 문의로 제공하지 않는다.
3. 실패한 등록에서 이미 생성한 파일과 DB 기록은 정리·롤백할 수 있도록 설계한다. DB와 파일 저장소는 별개의 저장 수단이므로 DB 롤백만으로 파일 삭제까지 함께 보장된다고 전제하지 않는다.
4. 파일 저장과 DB 트랜잭션의 순서, 정리 실패·서버 중단의 복구, 커밋 후 응답 유실과 재요청의 중복 처리, 실패 시 화면의 입력 유지 방식은 상세 설계 또는 후속 논의에서 정한다.
5. 성공적으로 접수된 문의·첨부의 소프트 삭제·보존 정책은 기존 결정을 적용한다. 실패한 등록의 미연결 파일 정리와 접수된 자료의 보존은 서로 다른 대상이다.

### 근거와 기록 상태

- 등록 성공이면 선택한 첨부까지 모두 접수됐다는 규칙을 명확하게 유지하고 부분 성공 흐름을 추가하지 않는 1번을 제안했고, 사용자가 선택했다.
- 현재 서비스는 DB 트랜잭션 중 파일 저장을 호출하고, 업로드 실패·DB 롤백 시 파일 정리를 시도하는 코드가 있다. 이번 결정은 사용자 결과를 확정한 것이며 해당 구현 전체를 그대로 유지한다는 선택은 아니다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 서버에서 파일을 먼저 처리하고 짧은 DB 트랜잭션으로 문의를 등록한다

- 상태: Accepted
- 결정일: 2026-10-07
- 범위: 문의 이미지 업로드 경로와 파일·DB 저장 순서
- 대체 범위: 앞서 미정으로 남긴 파일 저장과 문의 DB 트랜잭션의 순서
- 관련 자료: [FeedbackService](../../apps/server/src/main/java/bhoon/sugang_helper/support/feedback/application/FeedbackService.java), [LocalFileUploadService](../../apps/server/src/main/java/bhoon/sugang_helper/common/util/LocalFileUploadService.java)

### 비교와 선택

| 방식 | 동작 | 장점·제약 |
| --- | --- | --- |
| 서버 업로드·파일 처리 후 DB 저장 | 서버가 모든 이미지를 받아 검증·저장한 뒤 DB에 문의·첨부 정보를 저장 | 파일 처리 동안 긴 DB 트랜잭션을 유지하지 않지만 DB 실패 시 파일 정리가 필요 |
| DB 트랜잭션 안에서 파일 처리 | DB 트랜잭션 중 본문·파일·첨부 정보 처리 | 현재 구조와 비슷하지만 파일 처리만큼 DB 트랜잭션이 길어짐 |
| 객체 저장소의 presigned 직접 업로드 | 브라우저가 저장소에 업로드하고 서버가 검증 후 등록 확정 | 파일 전송·보관을 분리할 수 있지만 저장소와 업로드 확정 흐름의 관리가 추가됨 |

### 결정

1. 현재 로컬 파일 저장 구성을 기준으로 서버가 이미지 업로드를 직접 받아 검증·처리·저장하는 방식을 선택한다. 이번 재설계에서는 문의 업로드를 위해 presigned URL 발급·직접 업로드 흐름을 도입하지 않는다.
2. 필요한 모든 파일의 검증·처리·저장을 끝낸 뒤 문의 등록의 DB 트랜잭션을 시작한다. 본문과 첨부파일 연결 정보를 같은 짧은 DB 트랜잭션으로 저장하고, 커밋 후 등록 성공으로 처리한다.
3. 파일 처리 전체를 긴 DB 트랜잭션으로 감싸지 않도록 호출 흐름과 DB 저장 경계를 구성한다. 파일 처리에 실패하면 문의 등록 DB 저장을 진행하지 않고, 본문 또는 첨부 DB 저장에 실패하면 함께 롤백한다.
4. 실패한 등록에서 이미 생성한 파일은 정리·복구할 수 있도록 한다. DB 커밋 여부가 불확실하면 등록된 문의의 첨부를 잘못 삭제하지 않도록 연결 상태를 확인한 뒤 처리한다.
5. 파일 정리 실패·서버 중단의 복구 방식, 업로드와 정리의 경합, 실제 트랜잭션 적용 방식·등록 재요청 중복 방지는 후속 논의 또는 상세 설계에서 정한다. 접수된 문의·첨부의 소프트 삭제·보존 정책은 적용한다.

### 근거와 기록 상태

- 두 방식의 정상 흐름, 자원 점유, 파일·DB 저장 실패와 서버 중단 상황을 비교했다. 파일 정리·복구는 두 방식 모두 필요하며, 파일 먼저 처리하는 방식의 이점은 DB 트랜잭션 범위를 짧게 유지하는 데 있음을 설명했다.
- 사용자는 presigned URL을 질문한 뒤 S3를 사용하지 않는다고 설명했다. 현재 로컬 저장에서 일반 서버 업로드와 파일 처리 후 짧은 DB 저장을 제안했고, 사용자가 1번을 선택했다. 향후 모든 저장소 변경 가능성을 배제하는 결정으로 확대하지 않는다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 실패한 등록의 파일은 즉시 정리하고 주기적으로 누락을 보완한다

- 상태: Accepted
- 결정일: 2026-10-07
- 범위: 실패한 문의 등록에서 생성된 미연결 파일의 정리·복구

### 비교와 결정

| 방식 | 동작 | 장점·제약 |
| --- | --- | --- |
| 즉시 정리·주기적 보완 | 확인된 등록 실패의 파일을 바로 정리하고 누락 파일을 주기적으로 정리 | 대부분 바로 정리하면서 누락을 복구할 수 있지만 두 경로의 관리가 필요 |
| 주기적으로만 정리 | 실패 시 남겨두고 정리 작업에서 삭제 | 요청 흐름은 단순하지만 다음 정리까지 파일이 남음 |

1. 파일 처리 또는 문의 DB 저장의 실패가 확인되면, 해당 실패한 등록에서 생성한 미연결 파일의 삭제를 즉시 시도한다. DB 커밋 여부가 불확실한 경우에는 연결 상태를 확인한 뒤 처리하는 기존 정책을 적용한다.
2. 즉시 삭제 실패나 서버 중단 등으로 남은 미연결 파일은 주기적인 정리 작업으로 발견·정리한다. 즉시 삭제만으로 모든 중단 상황을 해결한다고 전제하지 않는다.
3. 진행 중인 업로드·등록의 파일과 성공적으로 접수된 문의에 연결된 파일은 보호한다. 소프트 삭제되거나 탈퇴 계정의 자료로 보존된 문의·첨부도 연결된 보존 자료로 취급한다.
4. 주기적인 정리 시 안전하게 연결 여부와 처리 상태를 확인할 수 없는 파일은 임의로 삭제하지 않는다. 조회·점검 실패를 미연결 판정으로 처리하지 않는다.

### 비교와 결정

| 방식 | 동작 | 장점·제약 |
| --- | --- | --- |
| 이미지 첨부 허용 | 답변마다 최대 3개·원본 합계 10MiB, 기존 이미지 정책 적용 | 해결 방법을 화면으로 설명할 수 있지만 답변에도 첨부 연결·정리 필요 |

1. 운영자는 문의 답변에 이미지를 첨부할 수 있도록 한다. 첨부는 선택 사항이며 텍스트만으로도 답변할 수 있다. 사용자는 첫 번째 방식을 선택했다.
2. 답변 한 건마다 이미지 최대 3개·업로드 원본 합계 10MiB(10,485,760바이트)를 적용한다. 최초 문의·작성자 메시지·모든 답변을 합친 누적 한도로 적용하지 않는다.
3. JPEG·PNG·WebP·GIF의 정지 이미지만 허용하고 움직이는 이미지는 거부한다. 검증·재인코딩한 파일만 저장하고 원본을 별도로 영구 보관하지 않는 기존 이미지 정책을 공통으로 적용한다.
4. 첨부가 있는 답변은 본문과 선택한 모든 첨부가 정상 저장돼야 등록 성공으로 처리한다. 파일 처리를 먼저 끝낸 후 답변·첨부 연결·사용자 영구 알림·외부 발송용 outbox를 같은 짧은 DB 트랜잭션으로 저장한다. 파일·DB 실패에는 기존 미연결 파일 정리 정책을 적용하며 실제 외부 호출은 커밋 후 수행한다.
5. 답변 첨부의 조회도 해당 작성자·권한 있는 운영자로 제한한다. 외부 답변 알림은 도착 안내와 문의 확인 링크로 유지하고 답변 본문이나 첨부 이미지를 외부 알림에 직접 포함하지 않는다.
6. 답변의 이미지 수정·교체·삭제와 보존 기록 접근의 세부 방식은 상세 설계에서 정한다. 운영자 답변 수정 자체에는 새 알림을 만들지 않는 결정과 답변 삭제 시 대기 알림 취소·답변 도착 영구 알림 소프트 삭제 정책은 유지한다.

### 근거와 기록 상태

- 현재 답변 생성 요청은 본문 텍스트만 받음을 확인했다. 이미지 첨부 허용과 텍스트만 유지하는 방식을 비교하고, 작성자 메시지와 이미지 정책을 공통으로 적용하는 1번을 제안했으며 사용자가 선택했다.

### 비교와 결정

Tika를 제거하고 이미지 처리 과정에서 검증하는 방식과 Tika의 사전 형식 판별·이미지 디코더를 함께 유지하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 첨부 이미지 처리에서 Tika와 그 의존성을 제거하는 방향으로 설계한다. 실제 이미지 처리 과정에서 입력 형식 확인·디코딩·검증·재인코딩을 수행한다.

4. 검증·재인코딩한 이미지만 저장하고 원본을 별도 영구 보관하지 않는 기존 정책과 이미지 최대 3개·원본 합계 10MiB 제한을 유지한다. 이미지 처리의 자원 제한도 유지할 검증 대상으로 삼되 세부 수치는 별도로 정한다.
5. 현재 Tika는 업로드 입력의 형식 판별뿐 아니라 저장 파일의 응답 MIME 판별에도 사용된다. 제거 시 응답 Content-Type은 서버가 실제로 저장한 출력 형식에 맞게 결정하도록 전환한다. 사용자 입력의 파일명만으로 응답 타입을 신뢰하지 않는다.
6. JPEG·PNG·WebP·GIF의 디코더 지원과 형식별 검증·출력 처리를 확인하여 필요한 구현을 선정한다. 이번 결정만으로 Java 기본 ImageIO가 모든 요구를 지원한다고 간주하거나 새로운 이미지 라이브러리를 확정하지 않는다.

기존 저장 파일의 조회 호환성과 출력 형식·응답 메타데이터 전환은 상세 설계에서 확인한다. 이번 변경은 의사결정 기록이며 Tika 의존성·Java 코드·설정 변경이나 테스트 실행·파일 변경은 하지 않았다.

## 추가 결정: 문의·답변 제출에 서버 멱등성 키와 제출 중 버튼 비활성화를 적용한다

### 비교와 결정

서버 멱등성 키와 제출 중 버튼 비활성화를 함께 적용하는 방식, 제출 중 버튼만 비활성화하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 문의·답변 생성 시 논리적인 제출을 구분하는 멱등성 키를 사용한다. 같은 제출을 다시 요청할 때는 같은 키를 사용하고, 서버에서 중복 처리를 막는다. 이미 성공한 동일 제출이면 새 글을 만들지 않고 기존 처리 결과를 반환한다.
2. 프론트엔드는 제출 처리 중 버튼을 비활성화한다. 화면 제어만으로 서버 중복 방지를 대신하지 않는다.
3. 중복 제어는 문의·답변 저장뿐 아니라 그에 따른 영구 알림·outbox 생성에도 적용한다. 동시에 도착한 동일 제출이 각각 글과 알림을 생성하지 않도록 DB의 원자적인 중복 제어와 기존 저장 트랜잭션을 함께 설계한다.
4. 키의 사용 범위는 요청 사용자·대상·작업과 연결하여 검증한다. 같은 키에 다른 내용이나 첨부를 보낸 요청은 동일 제출의 성공으로 취급하지 않는다. 기존 결과 반환 시에도 인증·권한 및 현재 접근 가능 여부를 확인한다.
5. 브라우저 API 실패 시 자동 재시도하지 않는 기존 정책은 유지한다. 응답을 받지 못한 사용자의 수동 재제출에서도 동일 제출 키를 재사용할 수 있도록 한다.
6. 외부 채널 발송 과정에서 성공 여부가 불확실할 때 중복 알림을 허용하는 기존 정책은 유지한다. 이번 결정은 우리 DB에 같은 문의·답변과 발송 작업이 중복 생성되는 것을 막는 범위다.

### 근거와 상세 설계 항목

서버에는 저장됐지만 응답을 받지 못한 상황에서 수동 재제출로 같은 글과 알림이 추가 생성되는 문제에 대응한다. 제출 중 버튼 비활성화는 연속 클릭을 줄이는 보조 수단으로 사용한다.

키 생성·보관·재사용 시점, 결과 보관 기간과 중복 방지 보장 범위, 처리 중·실패 요청의 응답, 요청 내용 일치 판정, 첨부 파일 중복 처리·정리 방식은 상세 설계에서 정한다. 파일 정리 시 기존에 접수된 글에 연결된 첨부를 삭제하지 않도록 기존 파일·DB 경계 정책을 적용한다. 이번 선택만으로 모든 API에 멱등성 키를 의무화하지 않는다.

이번 추가는 의사결정 기록이며 실제 DB 구조·서버·프론트 코드 변경이나 테스트 실행은 하지 않았다.
