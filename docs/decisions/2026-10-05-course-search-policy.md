# 결정: 강의 검색과 상세 조회는 로그인 없이 허용한다

- 상태: Accepted
- 결정일: 2026-10-05
- 범위: 강의 검색·상세 조회와 개인 기능의 로그인 요구
- 대체 결정: 없음
- 관련 자료: [SecurityConfig](../../apps/server/src/main/java/bhoon/sugang_helper/bootstrap/SecurityConfig.java), [강의 탐색 기능 체크리스트](../backend-redesign-checklist.md), [찜·구독 정책](2026-10-05-course-interest-policy.md)

## 문제와 목표

가입 전에 강의를 탐색할 수 있도록 할지, 검색과 상세 조회부터 로그인하도록 할지 정한다.

## 확인된 사실

- 현재 SecurityConfig는 강의 검색 POST와 강의 관련 GET 경로를 익명 접근 허용 목록에 둔다. 이번 결정은 코드에서 확인한 검색·상세의 접근 방식에 대한 재설계 정책 선택이며, 실제 배포 환경의 모든 요청을 검증한 것은 아니다.

## 선택지 비교

| 방식 | 장점 | 비용·제약 |
| --- | --- | --- |
| 로그인 없이 조회 허용 | 가입 전 서비스 탐색이 가능하고 개인 기능을 사용할 때 로그인 가능 | 익명 조회 요청도 처리해야 함 |
| 검색·상세부터 로그인 필수 | 접근 조건이 단순함 | 강의를 살펴보려는 사용자도 먼저 로그인해야 함 |

## 결정

1. 강의 검색과 공개 강의 상세 정보 조회는 로그인 없이 허용한다.
2. 찜·여석 구독·별점·이모지 평가 등 사용자 개인 상태를 생성·변경하는 기능은 로그인한 사용자에게 제공한다.
3. 익명 조회가 다른 사용자의 찜·구독·시간표 등 개인 상태를 공개하는 의미는 아니다. 개인화된 검색 조건·표시의 처리와 조회 API별 공개 필드는 상세 설계에서 정리한다.
4. 관리자 기능이나 강의 관련 모든 경로를 일괄 공개하는 결정은 아니다. 구체적인 요청별 접근 규칙은 이 요구를 기준으로 정리한다.

## 근거와 결과

- 강의를 먼저 살펴보고 개인 기능을 사용할 때 로그인하는 흐름을 제안했고, 사용자가 로그인 없이 검색·상세 조회를 허용하는 1번을 선택했다.
- 검색 구현·캐시·페이지네이션·외부 검색 엔진 등의 기술 선택은 이번 결정에 포함하지 않는다.

## 기록과 구현 상태

- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기록하고 결정 목록에 추가했다.
- 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 강의 검색은 별도 결과 캐시 없이 DB에서 직접 조회한다

- 상태: Accepted
- 결정일: 2026-10-05
- 범위: 강의 검색 결과의 기본 조회 방식과 별도 캐시 도입 여부
- 관련 자료: [CourseSearchReadRepository](../../apps/server/src/main/java/bhoon/sugang_helper/readmodel/course/infra/CourseSearchReadRepository.java), [강의 수집 정책](2026-10-04-course-collection-policy.md)

### 비교와 결정

| 방식 | 장점 | 비용·제약 |
| --- | --- | --- |
| DB에서 직접 조회 | 조회 흐름이 단순하고 별도 검색 결과 캐시의 갱신이 필요 없음 | 검색 요청마다 DB 작업이 발생 |
| Redis에 검색 결과 캐시 | 반복 검색의 DB 작업을 줄일 수 있음 | 검색 조건·개인 찜 조건·여석 변경과 캐시 만료·갱신을 관리해야 함 |

1. 강의 검색은 별도 결과 캐시 없이 DB에 저장된 강의 정보를 직접 조회하는 방식을 기본으로 한다. Redis 검색 결과 캐시를 이번 재설계의 기본 구조로 도입하지 않는다.
2. 검색 쿼리와 인덱스를 기본으로 설계하고, 검색 지연이나 DB 부하를 측정해 별도 캐시가 필요하다는 근거가 확인되면 다시 검토한다.
3. DB에서 직접 조회한다는 것은 조회마다 학교 외부 API를 호출한다는 뜻이 아니다. 기존에 선택한 수집 주기에 따라 DB에 반영된 강의 정보를 조회한다.
4. 이번 결정의 범위는 강의 검색 결과 캐시이다. QueryDSL 유지·직접 SQL 등 쿼리 구현 방식과 구체적인 인덱스는 아직 선택하지 않았다.

### 근거와 기록 상태

- 현재 검색 코드가 DB에 쿼리하는 것을 확인하고, 흐름을 단순하게 유지한 뒤 측정 근거가 생기면 검색 캐시를 검토하는 방식을 제안했다. 사용자가 DB 직접 조회인 1번을 선택했다. 특정 방식의 성능 우위를 측정한 결과는 아니다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 강의 검색의 동적 조건 조합에는 QueryDSL을 유지한다

- 상태: Accepted
- 결정일: 2026-10-05
- 범위: 강의 검색 쿼리의 구현 방식과 QueryDSL 사용 근거
- 관련 자료: [CourseSearchReadRepository](../../apps/server/src/main/java/bhoon/sugang_helper/readmodel/course/infra/CourseSearchReadRepository.java), [QueryDSL 공식 설명](https://github.com/querydsl/querydsl), [직접 SQL 실행의 Spring JDBC 대안](https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html)

### 비교와 결정

| 방식 | 장점 | 비용·제약 |
| --- | --- | --- |
| QueryDSL 유지 | 선택적 검색 조건을 Java 코드로 나눠 조합하고 필드·타입 관련 일부 오류를 컴파일 단계에서 확인 가능 | 라이브러리와 생성 코드 관리 필요 |
| 직접 SQL 작성 | 실제 실행할 쿼리를 직접 읽고 조정하기 편함 | 조건별 SQL 조합·파라미터·조회 결과 변환을 관리해야 함 |

1. 강의 검색의 동적 조건 조합에는 현재 사용하는 QueryDSL을 유지한다.
2. 강의명·교수·학점·요일·여석·찜 등 여러 선택 조건을 조합하는 실제 요구를 사용 근거로 한다. QueryDSL이 더 빠르다는 측정 결과를 선택 근거로 삼지 않는다.
3. 별도 검색 결과 캐시 없이 DB를 조회하는 기존 결정을 적용한다. QueryDSL 유지가 모든 데이터 접근을 QueryDSL로 통일하거나 새로운 검색 계층을 추가하는 결정은 아니다.
4. 조건·정렬·페이지네이션·인덱스와 기존 구현의 복잡도를 줄일 구조는 상세 설계에서 정리한다. 이번 결정은 특정 버전으로의 업그레이드를 승인하는 것이 아니다.

### 근거와 기록 상태

- 현재 검색 코드를 확인하고 선택 조건 조합이라는 사용 목적이 명확한 QueryDSL을 유지하는 방식을 제안했다. 직접 SQL과의 장단점을 설명한 뒤 사용자가 1번을 선택했다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 검색 결과는 무한 스크롤로 추가 조회한다

- 상태: Accepted
- 결정일: 2026-10-05
- 범위: 강의 검색 목록의 추가 조회 방식과 전체 건수 제공 여부
- 관련 자료: [현재 Slice 기반 검색](../../apps/server/src/main/java/bhoon/sugang_helper/readmodel/course/infra/CourseSearchReadRepository.java)

### 비교와 결정

| 방식 | 장점 | 비용·제약 |
| --- | --- | --- |
| 일부 결과와 다음 결과 여부 제공 | 전체 검색 건수를 계산하지 않아도 됨 | 전체 규모를 바로 알기 어려움 |
| 전체 건수와 페이지 번호 제공 | 결과 규모 파악과 특정 페이지 이동에 편리 | 검색 조건에 따른 전체 건수 계산 필요 |

1. 검색 결과는 일부 목록과 다음 결과의 존재 여부를 제공하고, 순서대로 추가 조회하는 방식을 채택한다. 검색 목록에 전체 건수와 전체 페이지 번호를 제공하는 방식을 기본으로 도입하지 않는다.
2. 화면에서는 무한 스크롤로 다음 결과를 자동 불러온다. ‘더 보기’ 버튼 방식도 같은 백엔드 응답으로 구현 가능하다는 설명 후 사용자가 첫 번째 화면 방식인 무한 스크롤을 선택했다.
3. 추가 조회 요청·응답과 검색 조건 변경 시 목록 처리, 정렬의 안정성, 갱신 중 데이터의 중복·누락 처리는 상세 설계에서 정리한다.
4. 무한 스크롤을 선택한 것만으로 커서 기반 페이지네이션을 확정하지 않는다. 현재 코드는 offset·limit와 Slice를 사용하며, 구체적인 페이지네이션 구현은 상세 설계에서 정리한다.

### 근거와 기록 상태

- 강의를 살펴보며 검색 조건을 바꾸는 흐름에 맞춰 일부 결과와 다음 결과 여부를 제공하는 방식을 제안했다. 사용자가 무한 스크롤인지 확인하여 무한 스크롤과 더 보기 버튼을 구분해 설명했고, 이후 1번으로 진행하도록 선택했다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 강의 조회 계약과 검색 어댑터를 클린 아키텍처 경계로 유지한다

- 상태: Accepted
- 결정일: 2026-10-13
- 기준: [클린 아키텍처 적용 결정](2026-10-13-clean-architecture-policy.md)

1. 기능 간 강의 조회에 안쪽의 `CourseCatalogQuery` 계약과 `CourseSummary` 등 순수 조회 DTO를 유지한다. 직전 대화에서 제안한 계약 제거·구체 조회 서비스 직접 주입 안은 아직 확정되지 않은 제안이며 이번 기준에서는 채택하지 않는다.
2. 조회 유스케이스는 안쪽 저장소·검색 계약을 사용한다. JPA 구현이나 엔티티를 다른 기능의 조회 계약에 직접 노출하지 않는다.
3. QueryDSL은 바깥 검색 어댑터에서 유지한다. 현재 `CourseSearchQuery`의 Spring `Pageable`·`Slice`와 JPA 엔티티 반환은 자체 페이지 요청·조회 결과로 전환할 대상으로 둔다.
4. 별도 캐시 없이 DB 조회, 무한 스크롤·다음 페이지 여부, 로그인 없이 공개 정보 조회 등의 기존 동작을 유지한다. 조회 전용 어댑터는 안쪽 조회 DTO로 직접 매핑할 수 있다.

같은 애플리케이션 계층의 구체 서비스 호출 자체를 일괄 금지하거나 모든 서비스에 인터페이스를 추가하는 결정으로 확대하지 않는다. 이번 추가는 의사결정 기록이며 실제 검색·조회 코드나 API 변경과 테스트 실행은 하지 않았다.
