- 관련 자료: [재설계 논의 계획](../backend-redesign-plan.md), [여석 발생 사실 발송](2026-10-01-seat-alert-occurrence-notification.md), [채널 정책](../../apps/server/src/main/java/bhoon/sugang_helper/seatalert/notification/application/NotificationChannelPolicy.java), [발송 작업](../../apps/server/src/main/java/bhoon/sugang_helper/seatalert/notification/domain/SeatNotificationDelivery.java), [FCM 발송기](../../apps/server/src/main/java/bhoon/sugang_helper/seatalert/notification/infra/FcmNotificationSender.java), [웹 Firebase 모듈](../../apps/web/src/shared/lib/firebase.ts)

## 문제와 목표

사용자가 여러 채널을 선택했을 때 하나만 성공해도 완료로 볼지, 선택한 채널 각각의 결과를 관리할지 정한다. 현재 제품 방향에서 필요성이 사라진 FCM의 구현·설정·의존성도 제거 대상으로 확정한다.

## 확인된 사실과 사용자 설명

- 사용자는 이메일·Discord·웹 푸시를 사용 중이라고 설명했다.
- FCM은 모바일 앱을 고려해 도입했지만 PWA로 방향을 정하면서 필요 없어졌다고 설명하고 제거를 결정했다. 해당 선택은 이 제품의 요구에 따른 판단이다.
- 코드에는 FCM 발송기, Firebase 초기화, 서버와 웹의 Firebase 의존성, 사용자 알림 설정·기기 타입·배포 설정이 존재한다. 코드 존재와 실제 운영 사용은 구분한다.
- 현재 발송 작업은 `outbox_id + user_id + channel`로 구분한다. 웹 푸시 채널 하나에도 여러 기기가 있을 수 있다.

## 선택지 비교

| 선택지 | 효과 | 비용·제약 |
| --- | --- | --- |
| 선택한 채널 각각에 전달하는 것을 목표로 함 | 각 채널의 수신 의도를 반영하고 부분 실패를 구분 | 사용자·채널별 성공/실패 상태가 필요 |
| 한 채널이라도 성공하면 목적 달성으로 봄 | 여러 채널을 대체 수신 경로로 사용할 수 있음 | 선택한 일부 채널에는 발송이 실패해도 추가 전달을 진행하지 않을 수 있음 |

## 결정

1. 사용자가 켜둔 채널 각각에 전달하는 것을 목표로 한다.
2. 이메일이 성공하고 Discord가 실패했다면 두 결과를 구분한다. 이메일 성공만으로 Discord 작업까지 완료로 판단하지 않는다.
3. 재시도를 도입하는 경우 부분 실패에 대한 재시도는 실패한 채널을 대상으로 한다. 성공이 확인되고 기록된 채널은 그 부분 실패를 이유로 다시 발송하지 않는다.
4. 지원할 채널은 이메일·Discord·웹 푸시다. FCM은 제거한다.

## 결정 근거와 영향

- 채널별 결과를 구분해야 한다는 요구가 발송 상태 분리의 근거다. 기존 delivery 테이블 구성·worker·claim·상태 전이 전체의 채택 여부는 추가 논의한다.
- 모바일 앱을 위한 FCM을 유지할 제품 요구가 사라졌다. 실제 사용 채널에 맞춰 이해해야 할 구현·설정·의존성을 줄인다.
- 제거 대상은 서버 FCM 발송기·Firebase 초기화/의존성, 웹 Firebase 모듈·초기화/의존성, FCM 활성화 필드·기기 등록 경로, Firebase 환경 변수·인증 파일 마운트·배포 및 CI 설정이다.
- 과거 FCM 이력·기기·대기 작업·사용자 설정 컬럼의 데이터와 호환성은 제거 구현 전에 확인한다. 운영에 적용된 Flyway 마이그레이션을 수정하지 않고 전환 방법을 정한다.
- [WebPushEndpointValidator](../../apps/server/src/main/java/bhoon/sugang_helper/identity/user/application/WebPushEndpointValidator.java)의 `fcm.googleapis.com`은 현재 웹 푸시 endpoint로 허용된 주소다. FCM 앱 채널 제거 범위와 구분해 웹 푸시의 연결을 보존한다.

## 미결 사항

- 채널별 성공 판정 기준, 재시도 여부·횟수·간격·기간과 실패 기록 관리
- 한 웹 푸시 채널 안에서 여러 기기 중 일부만 실패한 경우의 처리
- 수신자 선정 시점, 구독 해제·채널 비활성화 시 대기 작업 처리
- outbox와 발송 상태의 구체적인 저장 구조, 실행 방식, 중복·서버 중단 처리
- 기존 FCM 데이터의 정리와 읽기 호환성, 제거 배포 순서

## 구현과 검증 상태

사용자가 두 정책을 결정하고 PWA 전환 이유를 설명했으며, 이 기록의 작성을 요청했다. 현재는 결정과 제거 작업 범위를 문서화한 상태다. 애플리케이션 코드에서 FCM을 삭제하는 작업은 아직 수행하지 않았다.

구현 시 채널별 결과 구분과 성공이 기록된 채널의 재발송 제외를 단위 테스트로 확인할 범위를 정한다. 최종 E2E에서는 이메일·Discord·웹 푸시의 선택과 부분 실패 흐름을 다룬다. 이번 문서 작성에서는 테스트를 추가하거나 실행하지 않았다.

## 재검토 조건

별도 모바일 앱이나 새로운 전달 요구가 생기면 필요한 기능과 비용을 비교한 뒤 FCM 등 후보를 다시 논의한다. 사용자가 여러 채널을 각각 받기보다 대체 경로로 사용하려는 요구가 확인되면 성공 판단 정책을 재검토한다.

이 추가 결정은 위의 과거 기록을 보존하면서, 기존 미결 사항 중 구독 해제·채널 비활성화 시 대기 작업 처리 규칙을 구체화한다.

### 확정한 동작

| 설정 변경 | 미발송 작업 처리 |
| --- | --- |
| 과목 구독 해제 | 해당 사용자의 해당 과목 모든 채널 작업을 취소한다. 다른 과목의 작업은 유지한다. |
| 특정 채널 끄기 | 해당 사용자의 해당 채널 작업만 취소한다. 다른 채널의 작업은 유지한다. |
| 채널 다시 켜기 | 과거에 취소된 작업은 되살리지 않는다. 다시 켠 뒤 감지된 여석부터 알린다. |

1. 취소 처리는 구독 해제·채널 끄기 요청을 처리하는 시점에 수행한다.
2. 구독 해제에 대해서는 앞서 비교한 세 가지 방식 중 **해제 요청 시 대기 작업을 취소하는 3번만 적용**한다. 첫 발송·재시도 직전에 구독 상태를 다시 조회하는 2번은 추가하지 않는다.
3. 채널을 다시 켜도 기존 취소 작업을 복원하지 않는다. 작업 생성을 뒤늦게 수행하더라도 다시 켜기 전에 감지된 여석을 소급 발송하지 않는다.
4. 취소는 발송 성공과 구분한다. 취소된 작업을 외부 서비스가 성공적으로 수락·처리한 작업으로 기록하지 않는다.
5. 신청 기간 종료와 사용자의 구독 해제는 다른 사유로 다룬다. 신청 기간 종료나 단순 지연만을 이유로 대기 알림을 취소하지 않는 기존 방향을 유지한다.

### 선택 이유와 확인 범위

- 사용자는 구독을 해제한 사람에게 기존 대기 알림을 계속 보내는 방식이 더 이상 받고 싶지 않다는 의도와 맞지 않는다고 판단했다.
- 발송 때마다 구독 상태를 추가 조회하는 비용과 지연을 우려하여, 취소 요청 처리에서 대기 작업을 취소하는 방식을 선택했다.
- 구독 해제는 상대적으로 자주 일어나지 않으므로 해당 요청에서 취소 작업을 수행하는 것이 괜찮다는 사용자 판단이다.
- 추가 조회가 실제로 유의미한 지연을 만든다는 측정 결과와 구독 해제 빈도의 운영 자료는 아직 없다. 선택 근거인 사용자 판단과 측정된 사실을 구분한다.
- 사용자에게 늦게라도 발생 사실을 전달한다는 요구는 발송 대상으로 유지되는 작업에 적용한다. 사용자의 설정 변경으로 취소된 작업은 발송 대상에서 제외한다.

### 경합 경계와 남은 설계

- 해제·비활성화 전에 이미 시작한 외부 발송 요청은 설정 변경 후 도착할 수 있다. 취소가 진행 중인 모든 외부 요청의 전달까지 막는다고 보장하지 않는다.
- 취소할 작업 상태의 범위와 worker가 발송 정보를 읽은 뒤 취소되는 경합 처리는 구체적인 설계에서 정한다.
- 아직 발송 작업이 생성되지 않은 outbox, 해제 직후 재구독, 채널 재활성화와 여석 감지가 동시에 일어나는 경우에도 위 규칙을 적용할 수 있도록 수신자·채널 선정 시점과 데이터 구성을 정해야 한다.
- 과목 재구독 시 과거 발생을 어떻게 다룰지는 아직 별도로 확정하지 않았다. 채널 재활성화 규칙을 과목 재구독 규칙으로 자동 확대하지 않는다.

### 기록과 구현 상태

사용자가 세 가지 설정 변경 규칙을 결정하고 기존 문서 끝에 추가하는 것을 승인했다. 기존 내용은 수정·삭제하지 않았다. 이번에는 결정만 기록했으며 애플리케이션 코드·실행 설정 변경이나 테스트 추가·실행은 수행하지 않았다.

## 추가 결정: 웹 푸시는 모든 등록 기기의 발송 요청 성공을 목표로 한다

### 사용자 선택과 결정

사용자는 웹 푸시를 모든 등록 기기에서 받는 것을 목표로 선택했다. 이 추가 결정은 위의 기존 미결 사항 중 여러 기기에 대한 전달 목표를 확정한다.

1. 웹 푸시는 모든 등록 기기 대상의 발송 요청 성공을 목표로 한다.
2. 한 기기의 성공만으로 다른 기기의 실패까지 완료로 판단하지 않는다.
3. PC 대상 요청이 성공하고 휴대폰 대상 요청이 실패하거나 성공 여부가 불확실하다면, 휴대폰 대상 발송은 미완료로 남는다.
4. 성공 기준은 기존 결정에 따라 각 기기 대상 요청을 외부 서비스가 성공적으로 수락·처리했다는 응답이다. 사용자 기기의 실제 수신·화면 표시·읽음을 완료 조건에 추가하지 않는다.
5. 웹 푸시의 일부 기기 실패를 이유로 성공이 기록된 이메일·Discord 채널까지 다시 발송하지 않는다. 기존 채널별 결과 관리 방향을 유지한다.

### 미결 사항과 기존 결정의 적용

- 기기별 발송 결과를 저장할지, 여러 기기를 묶어 재시도할지는 아직 결정하지 않았다. 모든 기기 대상의 발송 요청 성공이라는 요구를 기기별 저장 구조의 채택으로 해석하지 않는다.
- 중복 알림을 허용한다는 기존 결정은 유지한다. 기기를 묶어 재시도할 때 이미 성공한 기기에도 다시 요청할 수 있다는 비용과, 기기별 결과 관리의 비용을 이후 비교한다.
- 발송 대상 기기 목록을 확정하는 시점, 대기·재시도 중 기기 추가·삭제, 유효하지 않은 기기의 실패 처리는 후속 논의에서 정한다.
- 과목 구독 해제·채널 끄기로 취소된 작업은 발송 대상에서 제외하며, 채널 재활성화 시 취소 작업을 복원하지 않는 기존 규칙을 유지한다.

### 기록과 구현 상태

사용자가 모든 등록 기기를 대상으로 하는 전달 목표를 선택하고 기존 문서 끝에 추가하는 것을 승인했다. 기존 내용은 수정·삭제하지 않았다. 이번에는 결정만 기록했으며 애플리케이션 코드·실행 설정 변경이나 테스트 추가·실행은 수행하지 않았다.

| 대기 중 새 기기가 등록됐을 때 | 과거 대기 알림에도 새 기기 대상 작업을 추가 | 새 기기는 등록 이후 감지한 여석만 수신 |

### 확정한 동작

1. 웹 푸시 발송 결과는 기기별로 관리한다. 성공이 확인되고 기록된 기기는 다른 기기의 실패를 이유로 다시 발송하지 않는다.
2. 실패했거나 성공 여부가 불확실한 기기는 미완료로 남겨 재시도한다. 한 기기의 실패가 다른 기기에 대한 발송 시도까지 중단시키지 않도록 한다.
3. 새 기기가 등록되면 아직 대기 중인 과거 웹 푸시 알림에도 해당 기기 대상 작업을 추가한다. 감지 당시 등록된 기기만 대상으로 고정하지 않는다.
4. 예를 들어 10:00에 감지한 알림의 PC 발송이 실패하고 10:05에 휴대폰이 등록되면, PC 재시도와 함께 휴대폰 대상 작업도 추가한다. 메시지에는 원래 감지 시각인 10:00을 유지한다.
5. 받을 수 있는 기기가 모두 만료돼도 미발송 알림을 보존하고 새 기기 등록을 기다린다. 만료된 기존 기기에 대한 재시도는 중단하되, 대상 기기가 없다는 이유로 원래 알림을 발송 성공으로 처리하거나 삭제하지 않는다.
6. 받을 기기가 없어 발송을 기다리고 있다는 안내 알림 한 건을 사용자에게 남긴다. 안내를 남겼다는 사실은 원래 여석 알림의 웹 푸시 발송 성공을 뜻하지 않는다.
7. 과목 구독 해제·채널 끄기로 취소된 작업은 새 기기 등록으로 되살리지 않는다. 채널을 다시 켠 뒤 감지된 여석부터 알리는 기존 규칙도 유지한다.

### 근거와 경계

- 모든 기기가 만료되면 수신 가능한 새 기기를 기다린다. 이 대기를 같은 만료 대상에 대한 반복 발송으로 해석하지 않는다.
- 외부 서비스가 요청을 처리했지만 응답이나 DB 성공 기록을 잃은 경우에는 재시도로 중복이 발생할 수 있다. 기존 중복 허용과 원래 감지 시각 표시 결정을 유지한다.
- 이미 완료된 과거 알림까지 새 기기에 소급 발송하는 것으로 확대하지 않는다. 대기 알림의 정확한 범위와 완료 판정 시점은 상세 설계에서 정한다.

4. 앞서 선택한 기존 시도 횟수 유지, 총 10회 제한, 성공·취소·최종 실패 작업 복원 금지 규칙을 유지한다.

### 근거와 남은 설계

- 고정 1분 재시도 규칙을 유지하며 설정 변경을 위한 별도 즉시 발송 동작을 추가하지 않는다.
- 이 결정은 이메일·Discord 경로 변경에 적용한다. 새 웹 푸시 기기 작업의 첫 시도 시각과 시도 횟수는 별도 논의한다.
- worker와 설정 변경의 경합, 요청 제한 적용 범위와 예약 시각의 저장·실행 방식은 상세 설계에서 정한다.

## 추가 결정: 새 웹 푸시 대상에 총 10회 기회를 주고 대체된 주소 작업은 중단한다

### 비교와 사용자 선택

| 질문 | 선택한 방식 | 채택하지 않은 방식 |
| --- | --- | --- |
| 새 기기 작업의 시도 횟수 | 기기별 새 작업에 최초 포함 총 10회 기회 부여 | 기존 기기의 시도 횟수를 공유 |

### 확정한 동작

1. 아직 대기 중인 웹 푸시 알림에 새 기기를 추가하면 새 대상 작업은 최초 발송 포함 총 10회 기회를 갖는다. 기존 기기는 자신의 시도 횟수를 유지한다.
2. 같은 기기라도 수신 주소가 갱신되면 갱신된 주소를 새 대상으로 처리한다. 이전 주소의 횟수를 초기화하는 대신 새 대상 작업에 별도의 최초 포함 총 10회 기회를 준다.
3. 주소 갱신으로 기존 주소 A가 새 주소 B에 대체된 것이 확인되면 A의 미완료 작업을 중단하고 B 대상 작업으로 발송을 이어간다. 이전 주소에서 이미 진행 중인 외부 요청은 회수할 수 없고 뒤늦게 도착할 수 있다.
4. 별도 기기 추가는 주소 대체와 구분한다. PC에 휴대폰을 추가한 경우 PC의 미완료 작업도 유지하며 각 대상의 결과와 횟수를 독립적으로 관리한다.
5. 기존 작업의 성공·취소·최종 실패 기록을 복원하거나 초기화하지 않는다. 성공·취소·최종 실패로 종료된 알림은 새 기기 등록이나 주소 갱신만으로 되살리지 않는다. 새 대상 추가는 아직 대기 중인 알림에 한정한다.
6. 새 대상에 발송할 때 원래 여석 감지 시각을 유지한다. 같은 발생의 전달임을 보존하되 구체적인 멱등성 키 구성은 상세 설계에서 정한다.

### 근거와 제약

- 별도 대상에 아직 발송을 시도하지 않았다는 점을 반영해 독립적인 시도 기회를 준다. 사용자는 같은 기기의 주소 갱신도 새 대상으로 취급하는 방식을 선택했다.
- 웹 푸시의 총 10회 제한은 수신 대상별 작업에 적용한다. 같은 여석 발생의 모든 대상·주소를 합친 총 시도 횟수를 10회로 제한하는 정책은 아니다.
- 예를 들어 주소 A로 7회 시도한 뒤 B로 갱신되면 A의 나머지 시도를 중단하고 B에 최대 10회 시도한다. 같은 발생에 총 17회 시도할 수 있으며, 주소 갱신이 반복되면 전체 시도 횟수는 더 늘어날 수 있다.
- 대체가 확인된 주소의 미완료 작업을 계속 시도하지 않는다. 대체 관계를 확인하지 않은 서로 다른 주소를 임의로 같은 기기로 추정해 중단하지 않는다.
- 이메일·Discord는 기존 작업의 경로 변경으로 처리하여 횟수와 예약을 유지하는 기존 결정과 구분한다.

### 남은 설계와 기록 상태

- 새 기기·갱신 주소의 첫 발송 시점은 아직 확정하지 않았다. 이후 일시적 실패에 대한 고정 1분 재시도와 외부 서비스의 대기시간 준수 정책은 유지한다.
- 주소 대체 관계 확인, 중복 등록과 동일 주소 재등록 처리, 이전 주소 중단과 새 대상 작업 생성의 경합, 알림 단위 완료·종료 판정은 상세 설계에서 정한다.
- 사용자가 위 세 가지 정책을 선택하고 기존 문서에 함께 추가하는 것을 승인했다. 기존 내용은 보존하고 끝에 추가했다. 이번에는 결정만 기록했으며 애플리케이션 코드·실행 설정 변경이나 테스트 추가·실행은 수행하지 않았다.

### 논의와 결정

| 등록 상황 | 대기 알림의 작업 처리 |
| --- | --- |
| 자동 동기화로 동일 주소·동일 암호화 정보 재전송 | 기존 작업·시도 횟수·예약 시각 유지 |

5. 명시적 재등록이나 실제 주소 갱신이 반복되면 같은 여석 발생의 총 시도 횟수가 10회를 넘을 수 있다. 총 10회 제한은 개별 대상 작업에 적용한다.

- 동일 주소에서 암호화 정보가 변경된 경우, 사용자 소유권 변경, 등록 요청 재전송과 새 명시적 재등록의 구분은 상세 설계에서 정한다. 동일한 명시적 요청의 재전송을 매번 새로운 사용자 의도로 간주하도록 확정한 것은 아니다.

## 추가 결정: 웹 푸시 종료와 부분 성공 시 재등록 대기 예외

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 사용자·여석 발생별 웹 푸시 알림의 종료 및 무효 주소 대기 판단
- 관련 자료: [최종 실패 종료와 채널별 안내](2026-10-01-notification-at-least-once-delivery.md)

### 확정한 동작

1. 남은 미완료 대상 작업과 재등록 대기가 없으면 해당 웹 푸시 알림을 종료한다. 기기별 성공·실패 결과는 보존하며, 종료 후 새 기기 등록에 해당 과거 알림을 소급 발송하지 않는다.
2. 성공이 기록된 기기가 있고 다른 기기의 수신 주소가 무효라면, 남은 정상 대상 작업을 처리한 뒤 부분 성공으로 종료한다. 무효 주소에 대해서는 해당 과거 알림을 전달하기 위한 재등록을 기다리지 않는다.
3. 예를 들어 PC에 성공하고 휴대폰 주소가 무효이며 다른 미완료 작업이 없다면 부분 성공으로 종료한다. 휴대폰을 나중에 재등록해도 이 과거 알림은 발송하지 않는다. 성공한 PC에도 다시 보내지 않는다.
4. 성공한 기기가 하나도 없고 수신 경로가 모두 사라졌다면, 기존처럼 원래 알림을 보존하고 재등록을 기다린다. 재등록 안내를 남기는 기존 방향을 유지한다.
5. 한 기기에 성공했어도 다른 유효 대상의 미완료 작업까지 성공이나 취소로 처리하지 않는다. 해당 작업에는 기존 총 10회·고정 1분 정책을 적용한다.
6. 총 10회 소진 등으로 이미 최종 실패한 대상 작업은 다른 대상의 진행·재등록으로 되살리지 않는다. 남은 작업과 대기 여부에 따른 웹 푸시 알림 전체의 종료 판단과 개별 작업의 종료를 구분한다.
7. 성공 기준은 외부 서비스 수락·처리 응답과 DB 성공 기록이다. 부분 성공은 일부 기기의 실제 수신·표시·읽음을 확인했다는 뜻이 아니다.

### 비교와 기존 정책의 적용 범위

- 사용자는 남은 작업·재등록 대기가 없으면 종료하는 방식을 선택했다. 미래의 새 기기에 전달하기 위해 종료 가능한 알림을 계속 열어두는 방식은 채택하지 않았다.
- PC 성공·휴대폰 주소 무효 사례에서는 재등록 후 휴대폰에도 과거 알림을 보내는 방식과 부분 성공으로 종료하는 방식을 비교했고, 사용자는 후자를 선택했다.
- 위의 기존 '모든 등록 기기 대상 성공 목표' 기록은 당시 선택으로 보존한다. 현재 정책은 유효 대상의 발송을 계속하되, 일부 성공이 기록된 상황의 무효 주소는 과거 알림 재등록 대기로 유지하지 않는 예외를 포함한다.
- 무효 주소 정리와 향후 새 여석 발생에 필요한 수신 경로 복구는 계속 필요하다. 과거 알림을 기다리지 않는다는 결정이 무효 주소를 유지하거나 향후 알림 등록을 막는다는 뜻은 아니다.
- 웹 푸시 외 다른 채널의 성공을 웹 푸시 성공으로 대체하지 않는다. 채널별 결과 관리와 실패 범위 안내 규칙을 유지한다.

### 남은 설계와 기록 상태

- 성공 기록·주소 무효화·새 기기 등록이 동시에 발생하는 경우의 순서 판단, 전체 상태 집계와 종료 시점은 상세 설계에서 정한다.
- 일부 성공이 발생하면 기존 무효 주소 대기를 해소하는 처리, 여러 기기의 실패 안내 단위·시점과 종료 결과 표시는 후속 논의에서 정한다.
- 사용자가 종료 규칙과 부분 성공 예외를 선택하고 함께 기록하도록 승인했다. 기존 내용은 보존하고 끝에 추가했다. 이번에는 결정만 기록했으며 애플리케이션 코드·실행 설정 변경이나 테스트 추가·실행은 수행하지 않았다.

## 추가 결정: worker 선정 시점의 구독자를 대상으로 하고 발생별로 독립 처리한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 여석 발생의 수신 사용자 선정 시점과 서로 다른 발생의 발송 순서

### 수신 사용자 선정

1. 수신 사용자는 여석 감지 시점에 확정하지 않고 worker가 수신자를 선정하는 시점에 구독 중인 사용자로 정한다.
2. 감지 이후 처음 구독한 사용자도 worker 선정 시점에 구독 중이라면 포함한다. 예를 들어 10:00 감지, 10:01 최초 구독, 10:02 수신자 선정이면 해당 사용자를 10:00 발생의 대상으로 포함한다.
3. 과목 재구독·채널 재활성화 이전 발생을 제외하는 기존 규칙은 유지한다. 최초 구독과 재구독을 동일하게 처리하여 기존 제외 규칙을 무효화하지 않는다.
4. 이 결정은 수신자 선정 기준이다. 매 재시도마다 구독자를 다시 선정하거나 발송 직전 구독 상태를 재조회하는 구조를 승인한 것은 아니다. 구독 해제 요청 시 대기 작업 취소 규칙을 유지한다.

감지 시점의 구독자로 고정하는 방식과 비교하여 사용자는 처리 시점 선정을 선택했다. 처리 지연에 따라 감지 이후의 최초 구독자가 포함될 수 있다는 결과를 수용한다.

### 서로 다른 발생의 처리

1. 서로 다른 여석 발생의 알림은 독립적으로 처리한다. 이전 발생의 재시도나 재등록 대기가 새 발생의 발송을 막지 않는다.
2. 예를 들어 10:00 발생 알림이 대기 중이어도, 다시 만석이 됐다가 10:05에 발생한 여석은 새 알림으로 발송할 수 있다.
3. 발생별 감지 시각·작업·결과를 구분한다. 도착 순서는 보장하지 않으며 늦게 도착한 알림에도 원래 감지 시각을 표시한다.
4. 독립 처리가 외부 서비스 요청 제한이나 전체 요청량 관리의 생략을 의미하지 않는다. 적용되는 요청 제한은 계속 준수한다.

이전 발생 작업이 종료될 때까지 새 알림을 기다리는 방식은 채택하지 않았다. 새로운 발생 정보를 이전 실패 때문에 지연시키지 않는 방향을 선택했다.

### 남은 설계와 기록 상태

- 최초 구독·재구독·채널 재활성화를 판별할 기록, worker 선정과 설정 변경의 경합, 수신자 작업 생성의 재실행 처리는 상세 설계에서 정한다.
- 발생별 처리량·스케줄링, 외부 요청 제한 적용과 오래된 작업 처리 방식도 상세 설계에서 정한다. 특정 큐·worker 개수나 병렬 실행 기술을 이번 결정으로 도입하지 않는다.
- 사용자가 두 정책을 선택하고 함께 기록하도록 승인했다. 기존 내용은 수정·삭제하지 않고 끝에 추가했다. 이번에는 결정만 기록했으며 애플리케이션 코드·실행 설정 변경이나 테스트 추가·실행은 수행하지 않았다.

## 추가 결정: 메모리 대기 작업은 실행 시작 시 DB 상태로 발송 가능 여부를 판단한다

### 비교와 결정

| 방식 | 동작 | 선택 |
| --- | --- | --- |
| 실행 시작 시 DB 작업 상태로 판단 | 시도 횟수 기록용 갱신에서 실행 가능한 상태인 작업만 처리하고, 취소된 작업은 건너뜀 | 사용자 선택 |
| 취소 요청에서 메모리 목록도 제거 | DB 취소에 더해 worker의 메모리 목록을 찾아 제거 | 채택하지 않음 |

1. 메모리에 가져온 작업이 실행 차례가 됐을 때, DB에 기록된 작업 상태를 기준으로 발송 가능 여부를 판단한다. 구독 해제·채널 끄기 요청에서 DB 작업을 취소하는 기존 규칙을 적용한다.
2. 이미 필요한 호출 전 시도 횟수 기록 트랜잭션에서 실행 가능한 상태인 작업만 갱신하도록 조건을 적용한다. 조건 검사와 실행 시작·시도 횟수 갱신이 별개로 일어나 그 사이의 취소를 놓치지 않도록 설계한다.
3. 작업이 취소되어 실행 시작 갱신이 성립하지 않으면 시도 횟수를 늘리지 않고 외부 요청을 보내지 않는다. 메모리 대기 목록에서는 해당 항목을 건너뛰고 다음 작업을 처리한다.
4. 구독 해제·채널 끄기 요청에서 worker의 메모리 목록까지 찾아 제거하는 처리는 이번 결정으로 추가하지 않는다. 취소된 항목은 실행 차례까지 메모리에 남을 수 있다.
5. 이 판단은 발송 작업의 상태 조건이다. 구독 정보를 발송 직전마다 별도 조회하지 않는 기존 규칙을 유지한다. 외부 요청은 시작 기록 트랜잭션이 종료된 뒤 실행한다.

### 근거와 남은 설계

- DB를 작업 상태의 기준으로 유지하고, 취소 요청 처리와 worker 메모리 목록 관리의 연결을 줄인다. 기존 시도 기록용 갱신에 상태 조건을 적용해 취소된 작업의 실행을 막는다.
- 실행 가능한 상태의 구체적인 표현, 확보·소유권 확인과 조건부 갱신 구현은 상세 설계에서 정한다.
- 취소와 실행 시작이 동시에 발생하는 경우의 우선순위와 판정 경계, 실행 시작이 기록된 뒤 외부 호출 전에 취소되는 경우, 이후 결과 저장·재시도와 취소의 관계는 아직 확정하지 않았다.
- 사용자가 실행 시작 시 DB 작업 상태로 판단하는 1번을 선택했다. 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했으며, 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았다.

## 추가 결정: 취소와 발송 시작의 경계는 DB에서 먼저 확정된 처리로 판단한다

2. 작업 취소가 먼저 확정되면 발송 시작·시도 횟수 갱신을 허용하지 않는다. worker는 횟수를 늘리거나 외부 요청을 보내지 않고 해당 작업을 건너뛴다.

5. 취소는 해당 작업의 이후 추가 재시도를 막는다. 이미 진행 중으로 인정한 시도가 실패하거나 성공 여부가 불확실해져도 취소 이후 외부 요청을 새로 재시도하지 않도록 취소 의사를 보존해야 한다.
6. 재구독·채널 재활성화로 과거 취소 작업을 되살리지 않는 기존 규칙을 유지한다. 진행 중인 결과를 저장하면서 취소된 재시도를 다시 예약하는 일이 없도록 설계한다.

### 근거와 남은 설계

- DB 상태를 기준으로 판단 경계를 명확히 하고, 외부 응답을 기다리는 동안 DB 트랜잭션·잠금을 유지하지 않는 기존 결정을 유지한다.
- DB 발송 시작과 실제 외부 호출 사이에도 설정 변경이 발생할 수 있다. 이 사이의 해제까지 현재 시도를 취소하는 추가 조율은 이번 결정으로 도입하지 않는다.

- 취소가 확정된 뒤 도착한 성공·실패·불확실 응답의 최종 상태와 사용자 안내 여부는 다음 논의에서 정한다.
- 사용자가 DB에서 먼저 확정된 처리를 기준으로 판단하는 제안을 승인했다. 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했으며, 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았다.

## 추가 결정: 온보딩 시작·저장 완료·저장 요청 실패를 GA4로 구분한다

- 결정일: 2026-11-01. 사용자가 기존에 제안한 최소 온보딩 계측의 구현과 로컬 검증을 승인했다. 앞서 별도 백로그로 남긴 온보딩 계측에 한해 진행한다.
- 기존 GA4 `page_view`는 경로 조회이며 온보딩 시작·완료나 실패를 뜻하지 않는다. `onboarding_started`는 로그인된 미완료 사용자의 프로필 로딩이 끝나 온보딩 화면이 준비됐을 때, `onboarding_completed`는 저장 API의 성공 응답을 받은 때 기록한다. 완료 버튼 클릭·입력 검증·저장 대기에는 완료를 기록하지 않는다.
- `onboarding_failed`는 저장 API 호출의 최종 오류만 시도별로 기록한다. 고정 `failure_reason`은 `network`(네트워크·시간 초과), `auth`(401/403), `rejected`(그 외 4xx), `server`(5xx), `unknown`이다. 네트워크 오류는 클라이언트가 성공 응답을 확인하지 못했다는 의미이며 서버 미반영을 보장하지 않는다. 실패 이후 재시도 성공은 완료로 별도 기록한다. 기존 전역 `exception` 이벤트는 일반 오류 진단이므로 이 이벤트와 합산해 실패 횟수를 구하지 않는다.
- 푸시 권한 거부·미지원·등록 실패, 이메일 인증 미완료, 사용자의 취소, 페이지 이탈은 저장 실패 이벤트로 세지 않는다. 웹 푸시 기본 off와 이메일·Discord 등 다른 수단으로 완료하는 기존 동작을 유지한다.
- 시작·완료는 같은 탭·계정에서 한 번 기록한다. 새 문서/뒤로가기/OAuth 복귀의 중복을 막기 위해 sessionStorage에 상태만 보관하고 계정 구분은 탭 내부 키로만 사용한다. 계정 ID·이메일·Discord 주소·기기명·토큰·원문 예외는 이벤트에 넣지 않는다. 새 이벤트의 경로는 query/hash 없는 `/onboarding`으로 고정한다. 저장소가 차단되면 현재 문서 메모리로 중복 방지를 제한한다. 탭 간 중복이나 분석 도구/네트워크 차단에서의 수집 보장은 범위 밖이다.
- 유효한 production GA4의 기존 초기화 경로와 gtag/dataLayer를 사용한다. 초기화 전에는 최대 20개 이벤트만 메모리에 대기하며 GA 미설정·비운영 환경에서는 전송하지 않는다. 기존 consent 처리와 GA 비활성 플래그를 존중하며 동의·개인정보·보안 설정과 GA4 콘솔 설정은 변경하지 않는다.
- 검증은 가짜 측정 ID, spy, 로컬 브라우저와 API 모의 응답으로 수행한다. 실제 운영 수집은 후속 배포와 사용자 확인이 필요하다. 커밋·푸시·PR·병합·배포는 이번 작업에 포함하지 않는다.
