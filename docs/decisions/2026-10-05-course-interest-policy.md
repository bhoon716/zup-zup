# 결정: 찜과 여석 구독은 별도로 유지한다

- 상태: Accepted
- 결정일: 2026-10-05
- 범위: 관심 강의 저장과 여석 알림 신청의 관계
- 대체 결정: 없음
- 관련 자료: [WishlistService](../../apps/server/src/main/java/bhoon/sugang_helper/planning/wishlist/application/WishlistService.java), [SubscriptionService](../../apps/server/src/main/java/bhoon/sugang_helper/seatalert/subscription/application/SubscriptionService.java), [채널 없는 구독의 안내 정책](2026-10-04-authentication-policy.md)

## 문제와 목표

강의를 관심 목록에 저장하려는 의도와 여석 알림을 받으려는 의도를 별도로 표현할지, 하나의 목록과 동작으로 통합할지 정한다.

## 선택지 비교

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 찜과 구독을 별도로 유지 | 관심 강의 저장만 원하는 사용자가 알림 신청 없이 이용 가능 | 사용자에게 두 상태를 구분해서 보여줘야 함 |
| 찜과 구독을 통합 | 목록과 조작이 줄어듦 | 저장만 했는데 알림 대상이 되는 동작을 설명·관리해야 함 |

## 결정

1. 찜은 관심 강의 저장, 구독은 여석 알림 신청으로 별도 유지한다.
2. 찜의 추가·제거가 구독 신청·해제로 자동 연결되지 않도록 한다. 구독 신청·해제도 찜 상태를 자동 변경하지 않는다.
3. 각 상태를 사용자가 구분할 수 있도록 한다. 구체적인 화면 배치·API·데이터 구조는 상세 설계에서 정리한다.
4. 채널 없는 사용자의 구독은 앞서 선택한 설정 확인 안내 정책을 적용한다. 찜만 추가하는 동작을 알림 구독으로 취급하지 않는다.

## 근거와 결과

- 관심 저장과 알림 수신의 의도를 각각 표현할 수 있는 별도 유지 방식을 제안했고, 사용자가 1번을 선택했다.
- 사용자 설정을 변경하는 흐름과 저장만 하는 흐름을 각각 이해할 수 있도록 하는 판단이다. 이번 선택은 찜·구독의 세부 구현이나 특정 기술을 추가하는 결정이 아니다.

## 기록과 구현 상태

- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기록하고 결정 목록에 추가했다.
- 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 재검토 조건

- 두 기능을 구분하기 어렵다는 사용자 피드백이나 별도 관리의 불편이 확인되면 화면·기능 관계를 다시 검토한다.

- 상태: Accepted
- 결정일: 2026-10-05

- 관련 자료: [기본 설정](../../apps/server/src/main/resources/application.yml), [운영 프로필 설정](../../apps/server/src/main/resources/application-prod.yml), [SubscriptionService](../../apps/server/src/main/java/bhoon/sugang_helper/seatalert/subscription/application/SubscriptionService.java)

### 비교와 결정

| 방식 | 장점 | 비용·제약 |
| --- | --- | --- |
| 최대 10개 유지 | 한 계정이 구독하는 강의 수와 그에 따른 발송량을 제한 | 여러 후보 강의를 찾는 사용자는 상한으로 불편할 수 있음 |
| 제한 제거 | 원하는 만큼 구독 가능 | 한 계정에 많은 발송 작업이 생길 수 있음 |

1. 사용자당 활성 여석 구독은 최대 10개로 유지한다. 이미 10개인 상태에서 새로운 구독을 추가하려면 기존 활성 구독을 해제하도록 한다.
2. 해제 상태로 보존한 구독 기록은 활성 구독 수에 포함하지 않는다. 여석 알림을 받았다는 이유로 구독을 자동 해제하지 않는 기존 결정은 유지한다.
3. 찜과 구독은 별도 기능이므로 이 상한을 찜 개수 제한으로 확대하지 않는다. 동시 요청에서의 상한 보장과 기존 데이터의 전환은 상세 설계에서 정리한다.
4. 부족하다는 사용자 피드백이나 운영 데이터를 바탕으로 상한을 재검토할 수 있다. 이번 선택은 10개가 최적이라는 측정 결과에 근거한 결정이 아니다.

### 근거와 기록 상태

- 현재 기본·운영 프로필 설정 파일에 최대 10개가 지정된 것을 확인하고, 기존 값을 우선 유지한 뒤 사용자 피드백·운영 데이터로 조정하는 방식을 제안했다. 사용자가 최대 10개를 유지하는 1번을 선택했다. 실제 배포 환경의 최종 적용 값까지 확인한 것은 아니다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 찜 API는 원하는 선택 상태를 명시한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 찜 추가·해제 요청의 의미와 중복 요청 처리
- 관련 결정: [이모지 선택 상태 명시](2026-10-05-course-evaluation-policy.md#추가-결정-이모지-api는-원하는-선택-상태를-명시한다)

### 비교와 결정

원하는 상태를 명시하는 방식과 서버의 현재 상태를 반전하는 토글 방식을 비교했다. 사용자는 응답 유실 후 재제출, 여러 기기의 오래된 화면, 구현 비용에 대한 설명을 확인하고 첫 번째 방식을 선택했다.

1. 찜 API는 대상을 찜 상태로 만들거나 해제 상태로 만드는 의도를 명시한다. 서버의 현재 상태를 무조건 반전하는 토글 요청은 재설계에서 사용하지 않는다.
2. 이미 찜한 대상의 추가 요청은 찜 상태를 유지하고, 이미 해제한 대상의 해제 요청은 해제 상태를 유지한다. 동일한 목표 상태의 반복 요청으로 찜을 반전하거나 활성 기록을 중복 생성하지 않는다.
3. 화면에서는 하트를 눌러 선택·해제하는 기존 조작을 유지할 수 있다. 프론트는 사용자가 요청한 목표 상태를 서버에 전달하고, 요청 결과로 화면 상태를 맞춘다.
4. 상태가 실제 변경된 경우에만 관련 집계·상태 변경 처리를 수행한다. 기존 소프트 삭제·기록 보존 정책은 유지하며 구체적인 복원·새 기록 생성 방식은 상세 설계에서 정한다.
5. 동시 추가의 중복 방지를 위한 DB 제약·트랜잭션 처리는 별도로 구현해야 한다. 이 선택만으로 반대 상태 요청의 도착 순서나 여러 기기의 최신 화면 동기화를 보장하지 않는다.
6. 기존 브라우저 API 실패 시 자동 재시도하지 않는 정책을 유지한다. PUT·DELETE는 설명에 사용한 예시이며 최종 경로·요청·응답 계약과 기존 클라이언트 전환은 상세 설계에서 정한다.

### 근거와 구현 상태

요청 자체에서 사용자의 목표를 읽을 수 있도록 하여 인지 부채를 줄인다. 응답 유실 후 같은 선택 요청을 다시 보내거나 다른 기기의 오래된 화면에서 선택해도 의도치 않게 해제되는 상황을 줄인다. 현재 토글 코드를 유지하는 방식보다 서버·프론트 변경 비용이 들지만, 동일 상태 요청 처리에 별도 제출 키·결과 보관 구조를 추가할 필요를 줄일 수 있다. DB 조회 감소나 성능 우위를 입증한 결정은 아니다.

이번 추가는 의사결정 기록이며 실제 API·서버·프론트 코드 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 이미 여석이 있는 강의의 구독 시 화면에서만 안내한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 구독 신청 시 저장된 강의 정보에 이미 여석이 있는 경우의 안내

### 비교와 결정

구독 화면에서만 안내하는 방식과 화면 안내에 더해 영구 알림·선택한 외부 채널로 즉시 알리는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 저장된 강의 정보에 이미 여석이 있어도 기존 구독 조건을 충족하면 구독을 등록한다. 구독 화면에는 `현재 수집된 정보에 여석이 있습니다`라는 취지의 안내를 표시한다.
2. 구독 순간 여석이 있다는 이유만으로 새 여석 발생 outbox·영구 알림·외부 발송 작업을 생성하지 않는다. 화면에서 안내하는 것으로 처리한다.
3. 이후 정상 수집에서 만석에서 여석으로 바뀐 사실을 확인하면 기존 여석 발생 알림 정책을 적용한다. 구독 후 알림을 받더라도 구독을 유지하는 정책도 유지한다.
4. 이번 결정은 구독 자체를 계기로 새 알림을 만들지 여부에 한정한다. 이미 감지된 발생에 대해 worker의 수신자 선정 시점에 처음 구독한 사용자를 포함하는 기존 정책을 취소하거나, 해당 사용자의 기존 대기 작업을 삭제하는 뜻이 아니다.
5. 안내는 마지막 정상 수집 정보를 기준으로 하며 학교의 실시간 신청 가능 여부를 보장하지 않는다. 이를 위해 구독 요청에서 학교 서버에 새 조회를 추가하는 방식은 이번 범위에 포함하지 않는다.

### 근거와 구현 상태

구독한 화면에서 여석 존재를 바로 알리고, 구독 시점의 상태 안내와 만석에서 여석이 생긴 발생 알림을 각각 관리하는 부담을 줄인다. 화면을 떠난 뒤 별도 알림 내역이 남지 않는 제약을 수용한다. 안내 위치·응답 필드 등 구체적인 API·화면 구성은 상세 설계에서 정한다.

이번 추가는 의사결정 기록이며 실제 구독 API·서버·프론트 코드 변경이나 테스트 실행은 하지 않았다.
