# 결정: 대시보드의 일부 조회가 실패해도 정상 영역은 표시한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 사용자 대시보드의 정보 조회 실패 처리와 화면 표시
- 관련 코드: `apps/server/src/main/java/bhoon/sugang_helper/dashboard/application/DashboardService.java`, `DashboardSnapshotResponse.java`

## 문제와 확인된 사실

대시보드는 공지·일정·사용자 정보·최근 알림·대표 시간표를 함께 제공한다. 한 영역의 조회 실패가 다른 정보의 이용까지 막아야 하는지 결정한다.

현재 `DashboardService`는 각 정보를 순서대로 조회하여 하나의 응답으로 조합하며, 메서드에 영역별 조회 실패를 구분하는 처리가 없다. 응답에도 영역별 실패 상태가 없다. 이는 저장소 코드에서 확인한 사실이며 실제 운영 장애를 재현하거나 검증한 것은 아니다.

## 선택지 비교

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 정상 영역은 표시하고 실패한 영역만 안내 | 일부 장애 중에도 다른 정보를 이용 가능 | 영역별 성공·실패 상태와 처리 경계를 설계해야 함 |
| 하나라도 실패하면 대시보드 전체 실패 | 응답 처리가 단순함 | 공지 조회 실패만으로 시간표 등 다른 정보도 이용하지 못할 수 있음 |

## 결정

- 독립적으로 처리할 수 있는 영역의 조회가 실패해도 정상적으로 조회한 다른 영역은 표시한다.
- 실패한 영역에는 '불러오지 못했습니다'와 같은 조회 실패 안내를 표시한다.
- 조회 실패를 정상적인 빈 상태와 구분한다. 예를 들어 알림 조회 실패를 '알림 없음', 시간표 조회 실패를 '시간표 미등록'으로 표시하지 않는다.
- 성공적으로 조회한 빈 목록이나 미등록 상태는 해당 영역의 정상 빈 상태로 표시한다.

## 근거와 결과

대시보드 각 영역은 서로 다른 정보를 제공하므로 일부 조회 실패 중에도 정상 정보를 사용할 수 있도록 한다. 실패를 빈 상태로 숨기지 않아 사용자가 실제로 데이터가 없는 것으로 오해하지 않게 한다.

모든 영역이 정상이라는 가정에 의존하는 응답·화면 처리를 변경해야 한다. 공통 기반 장애로 조회 자체가 불가능한 경우까지 정상 응답을 보장하는 결정은 아니며, 인증·권한 오류를 비로그인이나 빈 개인 데이터로 바꾸지 않는다.

## 구현과 후속 논의

영역별 상태의 API 표현, 조회·트랜잭션 경계, 실패 영역의 재조회 방식은 상세 설계에서 정한다. 광범위한 예외를 잡아 빈 값으로 대체하는 것으로 이 결정을 구현하지 않는다.

대시보드 최근 알림의 데이터 출처와 갱신 정책은 이번 결정으로 확정하지 않는다. 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 재검토 조건

여러 영역을 함께 성공·실패로 취급해야 하는 실제 데이터 의존성이나 사용자 요구가 확인되면 해당 범위를 다시 검토한다.

## 추가 결정: 사용자 대시보드에서 최근 알림 영역을 제거한다

- 상태: Accepted
- 결정일: 2026-10-10

- 관련 결정: [영구 알림함 정책](2026-10-01-persistent-notification-inbox.md)

### 배경과 결정

사용자 대시보드와 관리자 대시보드를 구분한 뒤, 사용자는 사용자 대시보드의 최근 알림 영역을 제거하도록 요청했다. 최근 알림을 영구 알림함 기준으로 통일하는 앞선 제안은 채택하지 않는다.

- 사용자 대시보드에서 최근 알림 목록을 표시하지 않는다.
- 해당 영역을 위한 대시보드의 최근 알림 조회와 응답 데이터도 제거하는 방향으로 재설계한다. 화면에서만 숨긴 채 불필요한 조회를 유지하지 않는다.
- 알림 확인은 기존 영구 알림함에서 제공한다. 알림의 생성·읽음·소프트 삭제·보존 및 외부 발송 정책은 변경하지 않는다.
- 최근 알림 영역의 제거는 알림 원본이나 발송 이력을 삭제한다는 의미가 아니다.
- 나머지 대시보드 영역에는 앞서 결정한 부분 조회 실패 정책을 유지한다. 이전 기록의 알림 조회 실패 예시는 제거되는 영역을 유지하라는 요구로 해석하지 않는다.

### 영향과 범위

사용자 홈과 알림함의 중복 표시 및 대시보드의 불필요한 알림 조회를 줄인다. 사용자는 최근 알림을 확인하려면 알림함으로 이동해야 한다.

이번 결정은 사용자 대시보드의 최근 알림 목록에 한정한다. 관리자 대시보드의 운영 통계나 알림함 진입 버튼·안읽음 배지의 구성까지 변경·확정하지 않는다. 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 관리자 대시보드에서 최근 시스템 로그 영역을 제외한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 관리자 대시보드의 최근 시스템 로그 표시·조회
- 관련 코드: `apps/server/src/main/java/bhoon/sugang_helper/admin/application/AdminService.java`, `AdminOverviewResponse.java`

### 검토와 확인된 사실

운영 상태를 대시보드에 표시하고 상세 진단은 서버 로그에서 확인하는 방식과, 관리자 화면에서 최근 시스템 로그도 조회하는 방식을 비교했다. 화면에서 로그를 제공하면 접근은 편하지만 로그 조회·필터·노출 범위를 관리해야 한다.

현재 코드의 `recentLogs`는 실제 서버 로그 파일을 읽는 기능이 아니다. `AdminService.buildRecentLogs()`가 최근 알림 이력과 마지막 수집 성공 시각을 기반으로 로그 형식의 항목을 구성한다. 이는 코드에서 확인한 사실이며 실제 운영 화면의 사용 빈도는 확인하지 않았다.

### 결정

- 관리자 대시보드의 최근 시스템 로그 영역을 제외한다.
- 해당 영역을 위한 로그 형식 데이터 구성·조회와 관리자 대시보드 응답의 `recentLogs`도 제거하는 방향으로 재설계한다.
- 상세 장애 진단은 서버 로그에서 확인한다. 이번 결정으로 별도 로그 검색 시스템이나 새 의존성을 도입하지 않는다.
- 대시보드에서 로그 영역을 제외한다는 이유로 서버 로그 기록, 알림 원본·발송 이력, 수집 이력이나 관리자 감사 기록을 삭제하지 않는다.

### 영향과 후속 논의

관리자 화면과 로그 형태의 데이터 구성 기능을 단순하게 한다. 상세 진단을 위해서는 서버 로그를 확인해야 한다.

시간대별 알림 트래픽 차트와 나머지 운영 상태·통계의 제공 여부 및 집계 기준은 별도 논의 사항이다. 사용자 대시보드의 부분 조회 실패 정책을 관리자 화면에도 적용할지는 이번 결정으로 확정하지 않는다. 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 관리자 대시보드의 시간대별 알림 트래픽 차트는 유지한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 관리자 대시보드의 시간대별 알림 트래픽 표시

### 검토와 결정

시간대별 집계·차트를 제외하는 방식과 최근 24시간의 시간대별 알림 건수 차트를 유지하는 방식을 비교했다. 사용자는 차트를 유지하는 방식을 선택했다.

- 관리자 대시보드에 최근 24시간의 시간대별 알림 트래픽 차트를 유지한다.
- 최근 시스템 로그 영역을 제외하는 앞선 결정과 별도로 차트의 집계·표시 기능은 유지한다.
- 차트는 시간대별 알림량의 추이를 확인하는 용도로 제공한다.

### 확인된 사실과 후속 논의

현재 `AdminService.buildHourlyNotificationTraffic()`는 최근 24개 시간 구간에 속하는 알림 이력의 `createdAt`을 조회해 구간별로 집계한다. 이 현재 구현만으로 재설계의 집계 대상을 영구 알림 생성 수나 외부 발송 성공 수 등으로 확정하지 않는다.

무엇을 한 건으로 셀지, 어떤 시각을 집계 기준으로 사용할지, 재시도·다중 채널·다중 기기를 어떻게 반영할지는 후속 논의로 남긴다. 기존 이력 건수와 외부 서비스의 발송 요청 수락·처리 성공 건수를 같은 의미로 단정하지 않는다. 집계의 저장·조회 방식과 최적화는 상세 설계 사항이다.

이번 변경은 의사결정 기록이며 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 변경 결정: 관리자 페이지의 알림 트래픽 차트를 제거하고 Grafana에서 확인한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 시간대별 알림 트래픽의 제공 위치
- 대체 범위: 위 '관리자 대시보드의 시간대별 알림 트래픽 차트는 유지한다' 결정

### 변경 배경과 결정

사용자는 차트 유지 결정을 변경하여 관리자 페이지에서 제거하고 Grafana 대시보드에서 확인하겠다고 지정했다. 이전 기록은 이력으로 남기고 해당 범위에는 이번 변경 결정을 적용한다.

- 관리자 대시보드의 시간대별 알림 트래픽 차트를 제거한다.
- 해당 차트만을 위한 관리자 페이지의 집계·조회 처리와 응답의 `notificationTraffic`도 제거하는 방향으로 재설계한다.
- 알림 트래픽 추이는 Grafana 대시보드에서 확인한다. 관리자 페이지에 같은 추이 차트를 중복 제공하지 않는다.
- 차트 제거를 이유로 알림 원본·발송 이력이나 모니터링용 지표 수집을 삭제하지 않는다. 다른 기능이 사용하는 조회·집계의 필요성은 각각 판단한다.

### 영향과 후속 논의

관리자 페이지에서 별도의 시간대별 차트를 관리하지 않고 Grafana를 이용한다. 이번 결정은 알림 트래픽 차트에 한정하며, 나머지 관리자 운영 상태·통계까지 모두 제거하거나 Grafana로 이전한다는 의미는 아니다.

앞서 제안한 영구 알림 생성 수·외부 발송 성공 수·시도 수·결과 분리 방식 중 어떤 지표를 사용할지는 선택되지 않았다. Grafana에서 사용할 지표의 정의·집계 단위·시각·데이터 제공 방식은 후속 설계 사항이다. 현재 Grafana 구성과 해당 지표의 제공 여부는 확인하지 않았다.

최근 시스템 로그 영역을 제외하는 기존 결정을 유지한다. 코드·설정 변경, Grafana 구성 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 관리자 대시보드에 안읽은 문의의 최근 목록·건수·바로가기를 제공한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 관리자 대시보드의 미확인 문의 요약
- 관련 결정: [운영팀 공통 확인 상태와 문의 상세 조회 시 자동 확인 정책](2026-10-07-feedback-policy.md)

### 검토와 결정

안읽은 문의의 건수와 바로가기만 제공하는 방식, 최근 문의 목록과 건수를 제공하는 방식, 대시보드에서 제외하는 방식을 비교했다. 사용자는 최근 목록·건수와 바로가기를 함께 제공하도록 선택했다.

- 관리자 대시보드에 안읽은 문의의 최근 목록과 해당 대상의 전체 건수를 표시한다.
- 최근 목록에는 문의 제목을 표시하고 해당 문의의 운영자 상세 화면으로 이동할 수 있도록 한다.
- 안읽은 문의 목록으로 이동하는 바로가기를 함께 제공한다. 최근 일부 목록만으로 전체 대상이 표시된 것처럼 안내하지 않는다.
- 안읽음 판정은 운영팀 공통 미확인 상태를 재사용한다. 최초 문의와 작성자의 새 후속 메시지로 미확인 상태가 된 문의를 포함하며, 처리 완료·반려 상태라도 기존 정책대로 미확인 내용이 있으면 포함한다.
- 건수는 미확인 상태인 문의 단위로 센다. 같은 문의에 미확인 후속 메시지가 여러 개 있다는 이유로 문의 건수를 중복 계산하지 않는다.
- 대시보드의 최근 목록·건수를 조회하는 것만으로 공통 확인 처리하지 않는다. 운영자가 문의 상세를 열어 내용을 조회할 때 자동 확인하는 기존 정책을 유지한다.
- 소프트 삭제된 문의와 확인할 내용이 남아 있지 않아 미확인 대상에서 제외된 문의는 일반 미확인 요약에 포함하지 않는다. 보존 기록의 별도 열람 정책을 변경하지 않는다.

정상 영역은 표시하고 실패한 영역만 안내하는 방식, 하나라도 실패하면 전체 실패로 처리하는 방식, 실패한 영역에 이전 조회 결과를 표시하는 방식을 비교했다. 사용자는 정상 영역을 표시하고 실패한 영역만 안내하는 방식을 선택했다.

- 독립적으로 처리할 수 있는 관리자 대시보드 영역 중 일부의 조회가 실패해도 정상적으로 조회한 다른 영역은 표시한다.
- 실패한 영역에는 ‘불러오지 못했습니다’와 같은 조회 실패 안내를 표시한다.
- 조회 실패를 정상 빈 상태나 0건으로 대체하지 않는다. 예를 들어 문의 조회 실패를 ‘안읽은 문의 0건’, 최종 실패 조회 실패를 ‘발송 실패 없음’으로 표시하지 않는다.
- 성공적으로 조회한 빈 목록이나 0건은 정상 조회 결과로 구분해 표시한다.
- 실패한 영역을 이전 조회값으로 대신 채우는 방식은 이번 정책으로 채택하지 않는다.
- 관리자 인증·권한 검사는 유지한다. 인증·권한 오류를 일부 영역의 빈 값이나 일반 조회 실패로 바꾸어 접근을 허용하지 않는다.

### 근거와 후속 논의

일부 영역의 장애 중에도 정상적으로 조회된 운영 정보를 확인할 수 있고, 실패를 빈 상태로 오해하는 것을 막는다. 앞서 사용자 대시보드에 적용한 부분 조회 실패 처리 방향을 관리자 대시보드에도 적용한다.

공통 기반 장애로 모든 조회가 불가능한 경우까지 정상 영역을 보장하는 결정은 아니다. 영역별 상태의 API 표현, 조회·트랜잭션 경계와 재조회 방식은 상세 설계에서 정한다. 광범위한 예외를 잡아 빈 값으로 대체하는 방식으로 구현하지 않는다.

## 추가 결정: 관리자 대시보드는 진입 시 조회하고 수동 새로고침으로 갱신한다

- 결정일: 2026-10-10
- 범위: 관리자 대시보드의 데이터 갱신 방식

### 검토와 결정

진입 시 조회와 수동 새로고침을 제공하는 방식, 주기적으로 전체를 자동 갱신하는 방식, 문의·발송 실패 등 일부 영역만 자동 갱신하는 방식을 비교했다. 사용자는 진입 시 조회와 수동 새로고침을 선택했다.

- 관리자 대시보드 진입 시 데이터를 조회한다.
- 진입 후에는 운영자가 새로고침 버튼을 누르면 데이터를 다시 조회하여 갱신한다.
- 화면을 열어 둔 동안 주기적으로 전체 또는 일부 영역을 자동 조회하는 기능은 추가하지 않는다.
- 새로고침에도 앞서 결정한 부분 조회 실패 정책을 적용한다. 정상 조회된 영역은 표시하고 실패한 영역은 빈 값으로 대체하지 않고 조회 실패로 안내한다.
- 대시보드 새로고침은 화면 데이터 재조회이며 강의 수집 실행이나 학교 서버 응답시간 측정을 위한 별도 요청을 발생시키지 않는다. 응답시간은 실제 수집 때 측정한 최근 값을 표시한다.

### 근거와 후속 논의

운영자가 화면을 상시 열어 두고 변경을 확인해야 하는 필요가 생기면 자동 갱신을 재검토한다. 구체적인 API 구성과 갱신 중 화면 처리는 상세 설계에서 정한다. 영구 알림함 등 다른 화면의 갱신 정책은 이번 결정으로 변경하지 않는다.

이번 변경은 의사결정 기록이며 코드·설정 변경이나 테스트 실행은 하지 않았다.
