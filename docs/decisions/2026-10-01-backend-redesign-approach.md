## 철회 기록 — 2026-10-01

사용자는 인지 부채와 근거 없는 기술 도입을 먼저 함께 논의해야 한다고 지적하고 계획의 재작성을 요청했다. 검토 범위는 “진짜 완전 간단하고 단순한 CRUD 제외 전부 다”라고 명시했다. 사용자와 필요한 동작을 논의하기 전에 에이전트가 권장 구조와 CRUD 중심의 첫 구현을 정했으므로 이 제안을 철회한다. 아래 내용은 이전 제안의 이력이며 현재 합의나 실행 근거가 아니다. 새로운 [논의 계획](../backend-redesign-plan.md)에 따라 기능별 요구와 대안부터 함께 논의한다.

## 문제와 목표

사용자는 인지 부채와 근거 없는 기술 도입을 이유로 백엔드 전체 기능의 재설계를 요청했다. 기능 전체의 필요성과 기술 근거를 검토하면서, 코드를 이해·변경·운영하는 비용을 줄일 진행 방식이 필요하다.

## 확인된 사실, 제약, 가정, 미해결 사항

- 확인한 사실: 단일 Spring Boot 앱에 기능 패키지·contract 경계가 이미 존재한다. 수집 완료와 outbox 생성은 트랜잭션으로 연결되고, 인증에는 JWT와 Redis 세션/폐기 처리가 함께 쓰인다.
- 확인한 사실: 현재 브라우저 E2E는 API 응답을 모킹한다. 서버 CI에는 MySQL 마이그레이션 검증이 있다.
- 제약: 유지하기로 한 기능의 API 소비자·데이터·인증·알림 동작을 전환할 수 있어야 한다.
- 가정: 현재 단일 앱·DB를 출발점으로 기능별 전환이 가능하다. 새 배포 경계가 필요하다는 운영 증거는 아직 확보하지 않았다.
- 미해결 사항: 실제 기능 이용률·피크 부하·알림 전달 요구, 중복 계층의 실제 변경 비용, 인증 소비자 범위.
- 결정을 바꿀 수 있는 증거: 특정 기능의 독립 배포/격리 요구, 현재 런타임 제약, 기능별 전환의 호환성 실패 또는 새 구조의 비용 증가.

## 핵심 개념과 결정 기준

기능 단위 교체는 한 사용자 또는 운영 흐름의 입력·규칙·저장·응답·검증을 함께 바꾸는 방식이다. 한 서버 안의 기능 경계는 코드와 데이터 책임을 나누며, 별도 서버 배포를 뜻하지 않는다.

| 기준 | 통과 조건 | 근거 |
| --- | --- | --- |
| 인지 비용 | 대표 변경에서 호출·변환·수정 범위와 필요한 책임을 설명할 수 있음 | 재설계 목적 |
| 기술 근거 | 각 도입/유지 기술에 실제 기능과 필요한 보장·비용이 연결됨 | 재설계 목적 |
| 정확성·안전성 | 유지 계약, 권한·소유권, 실패/경합 시나리오를 검증 | 사용자 데이터·인증·알림 경계 |
| 전환 가능성 | 기존 소비자·데이터·대기 작업의 처리 및 복구가 가능 | 전체 기능을 바꾸는 범위 |
| 운영 적합성 | 실제 부하와 대응 요구를 충족 | 아직 확인이 필요한 운영 증거 |

## 제안

두 번째 방식을 권장한다. 현재 런타임과 기능 패키지에서 사용자 작업·데이터 소유권·필요한 경계를 다시 설계하고, 전체 기능을 단계별로 전환한다. 계층·인터페이스·DTO·이벤트는 실제로 제공하는 책임과 보장을 확인한 뒤 통합 또는 유지한다.

P0에서 이용·운영 근거와 현재 계약을 수집하고, P1에서 경계·기술·검증 방식을 구체화한다. P2의 공지·일정·D-day 구현으로 이해/변경 비용과 전환 가능성을 확인한 뒤 이 기록의 상태와 실행 순서를 재검토한다.

이 제안은 특정 프레임워크·저장소·인증 방식·알림 채널의 최종 유지 결정을 포함하지 않는다.

## 근거와 결과

- 권장 근거: 이미 기능 경계가 존재하고, 핵심 기능은 트랜잭션·계정 수명 주기로 연결되어 있어 작은 범위에서 그 계약을 확인하며 전환할 수 있는 접근을 우선 평가한다.
- 기대 효과: 기능의 사용 근거와 기술 유지 이유를 남기고, 필요한 안전 보장을 검증하며 호출·변환 복잡도를 줄인다.
- 비용·제약: 전환 중 호환 코드와 검증 환경이 필요하다. 기능별 정리 완료 조건으로 잔재를 관리한다.
- 위험·복구: 계획의 데이터/인증/worker 전환 절차를 기능별로 구체화한다. 실제 운영 수치가 확보되면 순서와 구조를 조정한다.

## 구현, 검증, 리뷰

- 구현 단위: 하나의 사용자/운영 흐름. 관리자 작업은 해당 기능과 함께 다룬다.
- 검증: 단위·필요한 DB/Redis/보안 경계·MySQL 마이그레이션·실제 서버 E2E를 변경 위험에 맞춰 선택한다.
- 리뷰: 주요 문제 해결과 이전 계약·새 근거·전환 가능성을 확인한다.
- 현재 결과: 실행 계획과 ADR 초안을 작성했다. 구현·성능 측정·운영 전환은 후속 단계다.

## 재검토 조건

P2에서 변경 비용이 개선되지 않거나, 실제 부하·독립 배포 요구·데이터 전환 제약이 권장 접근과 맞지 않으면 대안을 다시 평가한다. 해당 증거가 확보되기 전에는 별도 서비스 또는 새 기술 도입을 확정하지 않는다.

3. 충분한 기능 정책과 큰 구조가 합의되면 다음 큰 주제로 진행한다. 기존 합의를 바꾸거나 사용자 동작·보장을 달리해야 하는 문제가 발견되면 그 영향과 근거를 제시해 함께 판단한다.
4. 지금까지 확정한 결정은 유지하고, 미정인 구현 세부 사항은 미정으로 남긴다. 이번 기록은 이후 논의 방식에 대한 합의이며 위에 남아 있는 철회된 접근 방식 제안의 재채택을 뜻하지 않는다.

사용자의 진행 기준 변경을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드는 변경하지 않았다.

- 상태: Accepted

- 기준 문서: [클린 아키텍처 적용과 기존 결정 점검](2026-10-13-clean-architecture-policy.md)

사용자의 명시적인 선택에 따라 업무 코어가 외부 기술 구현에 의존하지 않는 방향으로 전체 백엔드를 재설계한다. 단순한 계층형 구조에서 Spring Data 직접 의존을 허용하던 저장소 통합 선택은 관련 문서의 변경 결정으로 대체한다.

기능 동작과 큰 구조 중심으로 함께 논의하고, 필요한 경계와 기술의 근거를 확인하는 기존 진행 방식은 유지한다. 모든 서비스에 인터페이스를 일률적으로 추가하지 않으며 외부 의존을 차단하는 계약을 구현 개수만으로 제거하지 않는다. 단일 앱·단일 발송 worker와 지금까지 정한 사용자 기능 정책도 유지한다.

이번 추가는 새 아키텍처 기준의 채택이다. 이 문서 앞부분에 철회 상태로 남은 최초 제안과 당시의 선결정된 구현 순서를 재채택하는 뜻은 아니다. 실제 코드 전환은 아직 수행하지 않았다.

## 변경 결정: 전면 재작성을 중단하고 기존 코드의 설계를 단순화한다

- 상태: Accepted
- 결정일: 2026-10-26
- 사용자 요청: 기존 코드로 새 브랜치를 만들고, 기능을 유지하면서 설계부터 실제 수정·검증까지 진행한다.
- 작업 기록: [기존 코드 단순화](../existing-code-simplification.md)

중단된 `codex/backend-rewrite` 구현을 작업 기준으로 사용하지 않는다. 기존 코드의 실제 호출·중복·실패 처리와 테스트를 근거로 작은 단위로 단순화한다. 구조 교체의 완결성보다 이해·변경 비용 감소와 동작 보존을 우선한다. 전면 재작성의 기능 정책을 기존 동작에 새로 적용하지 않는다.

공개 API, 인증·권한, 데이터 정합성, 수집·검색·시간표·구독·알림·취소·재시도와 기존 테스트를 보존한다. 실제 트랜잭션·동시성·외부 발송 책임이 있는 경계는 유지하며, 동일한 책임의 전달 코드와 반복 구현을 줄인다. 모든 인터페이스를 일괄 제거하는 규칙으로 확대하지 않는다.

새 로컬 브랜치와 별도 worktree로 작업을 격리하고 원본 미커밋 변경을 보존한다. 원격 push, PR, 병합, 운영 배포·DB 변경, 실사용자 알림, 토큰·권한 변경은 범위에 포함하지 않는다. 기준 브랜치는 로컬 dev와 최신 원격 main의 차이를 확인한 뒤 사용자 선택을 기다리고 있으며, 이번 결정으로 어느 계열을 임의 확정하지 않는다.

기존 프레임워크·저장소·운영 경계를 수용하므로 구조의 일률성이나 완전한 기술 독립을 보장하지 않는다. 기능 정책이나 주요 기술 선택이 필요해지면 선택지와 근거를 제시하고 해당 변경만 보류한다.

### 2026-10-26 추가 리뷰 후 선택: 만료 WebPush 단말만 격리

최소 변경은 기존 durable delivery의 대상 반복에서 WebPush의 영구 WEB_PUSH_INVALID_SUBSCRIPTION 오류만 분리하는 것이다. 실제 sender는 404/410 단말을 삭제한 뒤 이 오류를 반환한다. 나머지 단말을 계속 처리하고 한 건 이상 성공하면 이력 1건과 기존 성공 정산을 사용한다. 모두 만료되면 같은 영구 오류를 다시 전파해 기존 DLQ 정산을 유지한다. 다른 영구 오류·일시적 오류는 기존대로 즉시 전파한다. 관리자/사용자 테스트 발송 경로의 오류 계약은 바꾸지 않는다.

검증은 만료→정상/정상→만료, 모두 만료, 첫 대상 일시 실패 및 부분 성공 뒤 일시 실패/재시도의 발송 대상·이력·DB 정산 상태를 확인한다. 부분 성공 후 재시도는 기존처럼 채널 전체를 다시 시도하며 같은 delivery key를 사용한다. 단말별 영속 정산이나 exactly-once 보장을 새로 도입하지 않는다.

남겨 둔 위험: 회로가 열린 동안 실제 발송 없이 attempts가 소진되어 회복 전 DLQ가 될 수 있다. 사용자의 명시적 선택에 따라 이 동작을 수정하지 않는다. WebPush 하위 HTTP 취소 미전파 및 긴 수집의 scheduler 점유도 기존 검토 위험으로 남긴다.
