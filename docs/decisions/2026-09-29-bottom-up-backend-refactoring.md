# 결정: 백엔드 리팩토링 진행 방향

- 상태: Proposed
- 결정일: 2026-09-29
- 범위: `apps/server` 코드 구조·도메인 경계·데이터 접근 리팩토링
- 대체 결정: 없음
- 관련 자료: [재설계 계획](../backend-infra-redesign-plan.md), [현재 시스템 인벤토리](../current-system.md)

## 배경과 결정 질문

백엔드 인지부채를 줄이기 위해 기존 코드를 작은 영역부터 이해하고 정리할 필요가 있다. 전체 재작성이나 여러 도메인 동시 변경은 회귀 원인과 복구 범위를 크게 만들 수 있다. 작은 도메인·엔티티 단위에서 시작해 상위 흐름으로 확장하는 진행 방식이 적절한지 정한다.

## 선택지

| 선택지 | 얻는 점 | 비용·위험 |
| --- | --- | --- |
| 바텀업 기능 조각 | 작은 규칙·모델에서 시작해 저장과 애플리케이션 흐름을 단계적으로 검증한다. 변경 범위와 회귀 원인을 좁히기 쉽다. | 전체 계약을 먼저 추적하지 않으면 모델을 잘못 이해한 채 고칠 수 있다. |
| 도메인 전체 일괄 재작성 | 목표 구조를 한 번에 정렬할 수 있다. | 긴 병렬 변경, 큰 회귀 범위, 어려운 전환·롤백이 따른다. |
| 모든 DB 엔티티부터 일괄 정리 | persistence mapping의 스타일을 빠르게 통일할 수 있다. | JPA 엔티티와 도메인 소유권이 일치하지 않을 수 있고, schema·다른 도메인 참조를 한꺼번에 건드릴 수 있다. |

## 결정

바텀업 점진 진행을 제안한다. 구현 전에는 대표 요청·스케줄 흐름을 진입점에서 아래로 추적해 API, 데이터 소유, 부작용, 실패 계약을 파악한다. 그다음 감사에서 작고 위험이 낮다고 확인된 기능 조각을 골라 규칙/모델 → 필요한 저장 경계 → application 흐름 → controller·scheduler·도메인 간 통합 순으로 검증한다. JPA 엔티티는 DB 매핑으로 취급하며, 도메인 경계와 테이블 소유권을 확인한 뒤에만 변경한다.

## 근거와 가정

- 근거: [재설계 계획](../backend-infra-redesign-plan.md)은 외부 API와 핵심 동작 보존, 한 소유권 또는 실패 경계씩 변경, 운영 구조를 유지하며 코드 경계를 검토하는 제약을 둔다.
- 가정 또는 미확인: 첫 리팩토링 대상으로 적절한 저위험 기능 조각은 코드 감사와 기준선 테스트 후에 고른다. 실제 교차 도메인 변경 빈도는 아직 조사하지 않았다.
- 결정을 바꿀 수 있는 증거: baseline을 만들 수 없어 순차 변경이 더 위험한 경우, 또는 강하게 결합된 schema/계약 때문에 작은 조각으로 분리할 수 없는 경우.

## 결과와 위험

- 기대 효과: 매 단계의 외부 동작과 영향 범위를 비교하며 작은 단위로 이전할 수 있다.
- 감수하는 비용·제약: 전체 구조가 정렬될 때까지 이전·새 경로가 일정 기간 함께 존재할 수 있다.
- 대응할 위험: 각 조각에 보존 계약과 전후 테스트를 붙이고, 안정화 후 이전 경로를 제거한다. 공용 추상화나 다중 도메인 이동을 미리 확대하지 않는다.

## 검증과 재검토 조건

첫 대상은 테스트 기준선, 소유 테이블, 호출자와 되돌림 경로가 확인된 뒤 선택한다. 각 조각에서 같은 contract suite와 필요한 migration·통합 검사를 전후 실행한다. 작은 단위 변경이 반복적으로 더 많은 교차 수정과 위험을 만든다는 증거가 나오면 진행 단위를 재검토한다.
