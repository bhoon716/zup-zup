# 결정: 여러 기기에서 동시에 로그인을 유지할 수 있도록 한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 인증·계정 재설계의 다중 기기 로그인 동작
- 대체 결정: 없음
- 관련 자료: [재설계 논의 계획](../backend-redesign-plan.md), [인증·계정 기능 체크리스트](../backend-redesign-checklist.md)

## 문제와 목표

PC와 휴대폰 등 여러 기기에서 같은 계정을 사용할 때, 새 로그인이 기존 기기의 로그인을 종료해야 하는지 정한다. 사용자 동작을 먼저 합의하고 그 요구를 기준으로 인증 구조를 비교한다.

## 비교와 결정

| 방식 | 동작 | 선택 |
| --- | --- | --- |
| 여러 기기에서 로그인 유지 | PC와 휴대폰 등에서 각각 로그인해 함께 사용 | 사용자 선택 |
| 한 기기만 로그인 유지 | 새 기기에서 로그인하면 기존 기기의 로그인을 종료 | 채택하지 않음 |

1. 같은 계정의 여러 기기에서 동시에 로그인을 유지할 수 있도록 한다.
2. 새 기기에서 로그인했다는 이유로 기존 기기의 유효한 로그인을 자동 종료하지 않는다.
3. 로그아웃의 적용 범위와 로그인 유지 기간은 후속 논의에서 정한다. 이 결정으로 무기한 로그인이나 허용 기기 수를 확정하지 않는다.
4. 이 동작을 충족할 인증 구조와 JWT·세션·Redis 등 기술의 필요성은 이후 비교한다. 현재 기술 구성을 그대로 채택하는 결정은 아니다.

## 근거와 기록 상태

- PC와 휴대폰을 함께 사용하는 흐름에 맞춰 다중 기기 로그인 유지를 제안했고, 사용자가 1번을 선택했다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기록했다. 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 일반 로그아웃은 현재 기기의 로그인만 종료한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 일반 로그아웃의 적용 범위

### 비교와 결정

| 방식 | 동작 | 선택 |
| --- | --- | --- |
| 현재 기기만 로그아웃 | PC에서 로그아웃해도 휴대폰 등의 유효한 로그인은 유지 | 사용자 선택 |
| 모든 기기 로그아웃 | 한 기기에서 로그아웃하면 다른 기기의 로그인도 모두 종료 | 채택하지 않음 |

1. 일반 로그아웃은 현재 기기의 로그인만 종료한다.
2. 다른 기기의 유효한 로그인은 유지한다. 여러 기기에서 함께 사용하는 흐름을 각 기기의 로그인별로 관리한다.
3. 현재 기기의 로그인 식별·종료를 구현하는 구체적인 인증 구조는 상세 설계에서 정리한다. 별도 전체 로그아웃 기능의 제공 여부와 로그인 유지 기간은 아직 정하지 않았다.

### 근거와 기록 상태

- 여러 기기를 함께 사용하는 흐름에서 각 기기의 로그인을 독립적으로 종료하는 방식을 제안했고, 사용자가 현재 기기만 로그아웃하는 1번을 선택했다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 로그인 유지 기간은 최근 사용을 기준으로 연장한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 로그인 유지와 미사용 만료의 기본 방식

### 비교와 결정

| 방식 | 동작 | 선택 |
| --- | --- | --- |
| 최근 사용 기준으로 연장 | 계속 사용하면 유지 기간을 연장하고 일정 기간 미사용하면 재로그인 | 사용자 선택 |
| 최초 로그인부터 고정 기간 | 계속 사용해도 정해진 기간이 지나면 재로그인 | 채택하지 않음 |

1. 로그인 유지 기간은 최근 사용을 기준으로 연장하는 방식을 적용한다.
2. 유효한 로그인을 계속 사용하는 동안 유지 기간을 연장하고, 일정 기간 사용하지 않아 만료되면 다시 로그인하도록 한다.
3. 구체적인 미사용 만료 기간과 사용으로 인정할 활동의 기준은 아직 정하지 않았다. 로그인 유지의 큰 동작을 먼저 정하고 인증 구조와 세부 구현은 이후 설계한다.

### 근거와 기록 상태

- 자주 사용하는 사람이 고정 기간마다 다시 로그인하는 불편을 줄이는 방향을 제안했고, 사용자가 최근 사용 기준 연장인 1번을 선택했다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 서비스의 로그인 인증은 서버 세션 방식으로 통일한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 브라우저·PWA의 서비스 로그인 유지와 요청 인증 구조
- 관련 자료: [현재 AuthService](../../apps/server/src/main/java/bhoon/sugang_helper/identity/auth/application/AuthService.java), [Spring Security 인증 유지 공식 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/persistence.html)

### 비교와 결정

| 방식 | 동작 | 선택 |
| --- | --- | --- |
| 서버 세션으로 통일 | 브라우저가 세션 ID를 쿠키로 보내고 서버가 로그인 정보를 확인 | 사용자 선택 |
| JWT 중심으로 통일 | 요청에서 서명된 토큰을 검증하고 갱신 토큰으로 로그인 유지 | 채택하지 않음 |

1. 서비스의 로그인 유지와 인증된 요청 처리는 서버 세션 방식으로 통일한다. 브라우저·PWA는 세션 ID를 쿠키로 전달하고, 서버는 저장된 로그인 정보를 확인한다.
2. 여러 기기의 동시 로그인 유지, 현재 기기만 로그아웃, 최근 사용 기준 유지 기간 연장의 기존 요구를 세션 관리로 구현한다.
3. 서비스 자체의 access·refresh JWT 발급·갱신·폐기를 로그인 유지의 기본 구조로 사용하는 흐름은 세션 방식으로 전환한다. 외부 로그인 제공자의 OAuth 인증 절차와 토큰 처리 범위는 해당 연동 설계에서 다룬다.
4. 세션 저장소와 구체적인 유지 기간은 아직 정하지 않았다. 세션 쿠키·기존 클라이언트·로그인 상태의 전환과 API 호환성은 상세 설계에서 정리한다.

### 근거와 기록 상태

- 현재 AuthService가 JWT 갱신·폐기와 HTTP 세션 저장을 함께 처리함을 코드에서 확인했다. 지금까지 합의한 로그인·로그아웃·만료 동작을 서버의 로그인 기록으로 관리하는 흐름을 제안했고 사용자가 서버 세션 방식인 1번을 선택했다.
- 인증 상태의 관리 방식을 통일해 이해하고 수정할 흐름을 줄이는 판단이다. 세션 방식의 성능 우위를 측정한 결과는 아니다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 서버 세션은 Redis에 저장한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 서비스 로그인 세션의 저장소
- 관련 자료: [Spring Session Redis 공식 문서](https://docs.spring.io/spring-session/reference/guides/boot-redis.html)

### 결정

1. 서버 세션의 저장소는 Redis로 한다. DB 또는 백엔드 프로세스 메모리에만 세션을 저장하는 방식을 이번 재설계의 기본으로 채택하지 않는다.
2. 서버 세션 인증으로 통일하고, 여러 기기의 로그인 유지·현재 기기만 로그아웃·최근 사용 기준 유지 기간 연장의 기존 정책을 적용한다.
3. 로그인 기록은 백엔드 프로세스 메모리와 별도로 Redis에서 관리한다. 백엔드 재시작 후에도 Redis의 세션과 클라이언트 쿠키가 유효하면 로그인 상태를 이어갈 수 있도록 설계한다.
4. Redis 자체의 재시작·장애 시 세션 보존에 필요한 영속성 설정과 운영·복구 방식은 상세 설계에서 정리한다. 이번 선택만으로 Redis 데이터 보존을 보장한 것은 아니다.

### 근거와 기록 상태

- DB·Redis·프로세스 메모리 저장을 비교하고, DB와 메모리 저장의 사용자 경험 차이를 추가 설명한 뒤 사용자가 Redis를 선택했다. 성능 우열을 측정해 선택한 결과는 아니다.
- Spring Session의 Redis 기반 HTTP 세션 지원은 공식 문서에서 확인했다. 구체적인 연동·만료 설정과 기존 로그인 상태의 전환은 상세 설계에서 정리한다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 명시적으로 로그아웃해도 해당 기기의 웹 푸시는 유지한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 현재 기기의 명시적인 로그아웃과 웹 푸시 수신의 관계

### 결정

1. 사용자가 현재 기기에서 명시적으로 로그아웃해도 해당 기기의 웹 푸시 등록과 수신은 유지한다. 로그아웃을 이유로 웹 푸시 수신 경로를 제거하거나 대기 발송 작업을 취소하지 않는다.
2. 일반 로그아웃은 기존 결정대로 현재 기기의 로그인만 종료한다. 과목 구독과 이메일·Discord·웹 푸시 채널 설정은 로그아웃으로 변경하지 않는다.
3. 웹 푸시 수신 중단은 기존 구독 해제·채널 끄기 등의 알림 설정 정책으로 처리한다.
4. 같은 기기에서 다른 계정으로 로그인할 때의 웹 푸시 연결 처리는 후속 논의에서 정한다. 이번 결정의 범위는 명시적인 로그아웃이며, 미사용에 따른 세션 만료 처리는 별도로 정리한다.

### 근거와 기록 상태

- 로그아웃 시 해당 기기의 웹 푸시를 중단하는 방식과 로그인 상태와 독립적으로 유지하는 방식을 비교했고, 사용자가 유지하는 2번을 선택했다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 같은 기기에서 다른 계정으로 로그인해도 기존 계정의 웹 푸시 연결을 유지한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 동일한 기기의 계정 전환과 웹 푸시 수신 연결

### 결정

1. 같은 기기에서 A 계정을 로그아웃하고 B 계정으로 로그인해도 A 계정의 웹 푸시 연결을 자동 해제하지 않는다. 해당 기기는 A와 B 계정의 웹 푸시를 함께 수신할 수 있도록 한다.
2. 각 계정의 과목 구독·웹 푸시 채널 설정과 유효한 등록 상태에 따라 발송한다. 계정 전환만으로 기존 계정의 대기 작업을 취소하거나 다른 계정의 알림 설정을 변경하지 않는다.
3. 현재 로그인한 계정의 인증과 웹 푸시 수신 연결은 별도로 관리한다. 여러 계정의 푸시 수신을 유지하는 결정이 동시에 여러 계정의 인증 권한을 제공하는 뜻은 아니다.
4. 동일한 수신 경로와 여러 계정의 연결을 표현하는 데이터 구조 및 연결 관리 화면은 상세 설계에서 정리한다.

### 근거와 기록 상태

- 현재 로그인한 계정으로 웹 푸시 연결을 전환하는 방식과 이전·새 계정의 연결을 함께 유지하는 방식을 비교했고, 사용자가 함께 유지하는 2번을 선택했다.
- 사용자의 선택을 저장 여부를 별도로 묻지 않고 기존 문서 끝에 추가했다. 기존 내용과 애플리케이션 코드·실행 설정은 변경하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 로그인은 마지막 사용 후 30일간 유지한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 최근 사용 기준 로그인 세션의 미사용 만료 기간

### 결정

기존 관리자 조치·탈퇴 처리 로그의 보존 정책은 유지한다. 이번 변경은 의사결정 기록이며 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 변경 결정: 관리자 작업 기록은 서버 로그로만 남긴다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 관리자 작업 기록의 저장·조회 방식
- 대체 범위: 앞선 관리자 조치 기록의 DB 저장·소프트 삭제 방식. 탈퇴 처리 기록과 다른 데이터의 보존 정책은 대체하지 않는다.

### 변경 배경과 결정

관리자 전용 기록 페이지, 서버에서 DB 직접 조회, Grafana 조회 방식을 비교한 뒤 사용자는 ‘그냥 로그로만 기록하기’를 지정했다. 관리자 작업 이력을 별도 DB 감사 데이터로 관리하는 대신 서버 로그로 남기는 방향으로 해석하여 기록한다.

1. 앞서 선택한 관리자 기능의 모든 데이터 변경을 서버 로그로 기록한다. 단순 조회는 이번 작업 기록 대상에 포함하지 않는다.
2. 관리자 작업 기록만을 위한 별도 DB 저장·소프트 삭제 처리와 감사 기록 조회 API·관리 페이지는 재설계에서 제외한다. 기존 감사 기록 조회 API도 이 방향에 맞춰 제거 대상으로 삼는다.
3. 기록 확인은 서버 로그를 통해 수행한다. 이번 선택으로 Grafana 연결, 로그 검색 시스템이나 새 외부 서비스를 도입하지 않는다.
4. 작업 기록을 로그로 남기더라도 비밀번호·토큰 등 비밀값을 저장하지 않는다. 요청·응답이나 변경 대상 원문 전체를 그대로 출력하는 것으로 구현하지 않는다.
5. 기존 기록을 지금 삭제하거나 기존 로그 보관 설정을 변경하지 않는다. 이미 저장된 DB 감사 데이터의 전환·보관 방식은 상세 설계에서 정한다.

### 기존 보존 결정과의 관계

관리자 작업 이력의 영구 보존 의도를 이번 답변만으로 철회하지 않는다. 다만 DB 행의 소프트 삭제 방식은 서버 로그에 그대로 적용하지 않는다. 로그 회전·보관·백업으로 보존 의도를 충족하는 구체적인 방법은 별도로 정하며, 로그를 출력하는 것만으로 영구 보존이 보장된다고 단정하지 않는다.

탈퇴 처리 로그와 다른 도메인 데이터의 보존 정책은 이번 변경의 대상이 아니다. 관리자 한 명 운영·수동 권한 관리와 모든 관리자 데이터 변경 기록의 범위는 유지한다.

### 근거와 후속 논의

3. Redis 저장 파일을 잃거나 손상되어 세션을 복구할 수 없으면 해당 사용자는 다시 로그인한다. 파일 영속 저장만으로 디스크 손실까지 복구할 수 있다고 간주하지 않는다.
4. 영속 저장하더라도 마지막 사용 후 30일 만료, 로그아웃과 회원 탈퇴에 따른 세션 폐기 등 기존 세션 정책을 유지한다. 재시작 시 만료·폐기된 세션을 다시 유효하게 만드는 정책은 채택하지 않는다.
5. 저장 방식에 따라 갑작스러운 장애에서 최근 변경 일부가 유실될 수 있다는 제약을 수용한다. RDB·AOF의 선택, 저장 주기와 파일 보관 경로·볼륨 구성 및 손상 대응은 상세 설계에서 정한다. 이번 선택만으로 모든 장애에서 세션 유지나 무손실을 보장하지 않는다.

이번 변경은 의사결정 기록이며 Redis 설정·저장 파일·로그인 세션이나 애플리케이션 코드를 변경하지 않았고 테스트를 실행하지 않았다.

4. 명확한 발송 거절·실패는 요청에서 오류로 안내하고 사용자가 다시 요청하도록 한다. 인증 이메일에 여석 알림의 최대 10회 자동 재시도를 적용하지 않으며, 애플리케이션의 백그라운드 자동 재시도 작업을 만들지 않는다.

6. 기존 `JavaMailSender`와 실제 발송 부분 공통화 결정을 유지한다. 여석·문의 알림의 아웃박스·재시도 정책은 유지한다.

### 근거와 수용한 비용

사용자가 코드를 기다리는 흐름에서 발송 요청의 결과를 바로 안내하고, 코드 만료·재요청과 별도의 대기·재시도 작업을 함께 관리하는 부담을 줄인다. 현재 Redis 코드 저장과 MySQL 아웃박스를 결합할 때 필요한 저장소 간 상태 복구 설계를 추가하지 않는 방향을 선택했다.

- 상태: Accepted
- 범위: 기존 단순화 브랜치의 인증·인가·JWT 관리

사용자는 인증·인가와 JWT 관리를 최대한 간단하게 만들고, 애매하면 세션 복귀를 고려하겠다고 요청했다. 현재 실행 코드는 Redis 세션과 JWT를 함께 사용하며 웹은 쿠키 인증만 사용한다. 이번에는 동작·보안을 보존하는 중복 레코드/파싱과 미사용 웹 코드 정리, 로그아웃 후 늦은 refresh의 이전 요청 재전송 방지를 구현한다. 세션 완전 전환, 자체 JWT/refresh API 제거, 현재 쿠키·CSRF·CORS·TTL 정책 변경은 실행 범위로 확대하지 않는다. 과거 재설계의 세션 선택을 기존 코드 전환의 즉시 실행 승인으로 간주하지 않는다.

서명·만료·종류·uid·역할 검증, DB 사용자 확인, 원자적 회전·재사용 차단·로그아웃 폐기·실패 보상·탈퇴 차단과 기존 HTTP 응답은 유지한다. 정상·만료·갱신·로그아웃·권한 거부 및 동시/늦은 요청 회귀를 검증한다. 설정·자격 증명·운영 데이터는 바꾸지 않고 로컬 커밋까지만 한다. 현 구조와 세션 대안은 [인증 단순화 검토](../authentication-simplification.md)에 구분해 기록한다.
