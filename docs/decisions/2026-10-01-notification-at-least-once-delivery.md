# 결정: 외부 서비스의 발송 요청 수락·처리까지 at-least-once 전달을 목표로 한다

- 상태: Accepted
- 결정일: 2026-10-01
- 범위: 여석 알림의 전달 목표와 채널별 완료 판정 기준
- 대체 결정: 없음. 기존 중복 허용·채널별 결과 관리 결정을 구체화한다.
- 관련 자료: [중복 허용 결정](2026-10-01-notification-duplicate-and-mq-policy.md), [채널 정책 결정](2026-10-01-notification-channel-policy.md), [채널별 멱등성 조사](../backend-notification-idempotency-research.md)

## 문제와 목표

재발송과 중복 허용 방향을 실제 전달 목표로 정의하고, 어느 단계의 성공을 확인하면 작업을 완료할지 정한다. 외부 서비스의 요청 수락, 사용자 기기의 수신·표시, 사용자의 확인을 서로 구분한다.

## 확인된 사실과 사용자 선택

- 사용자는 여석 알림에서 at-least-once를 지키는 방향을 선택했다.
- 성공 기준으로 외부 서비스의 발송 요청 수락·처리 응답을 선택했다.
- 중복 알림 허용, outbox 유지, 같은 발생의 원래 감지 시각 표시는 기존 결정이다.
- SES의 성공 응답과 MessageId는 요청 수락을 나타낸다. Discord 메시지 생성 API는 메시지 객체를 반환한다. 웹 푸시 HTTP 201은 요청 수락이며 브라우저 전달 완료를 의미하지 않는다. [SES 명세](https://docs.aws.amazon.com/ses/latest/APIReference-V2/API_SendEmail.html), [Discord 명세](https://docs.discord.com/developers/resources/message#create-message), [RFC 8030 §5](https://www.rfc-editor.org/rfc/rfc8030#section-5)

## 선택지 비교

| 완료 기준 | 확인하는 범위 | 추가 요구·제약 |
| --- | --- | --- |
| 외부 서비스의 발송 요청 수락·처리 응답 | 우리 서버에서 채널의 외부 서비스까지 | 사용자 기기 수신·표시·읽음을 보장하지 않음 |
| 사용자 기기의 실제 수신·표시까지 | 외부 서비스 이후의 전달·클라이언트 단계 | 채널마다 확인 가능 범위가 다르고 전달 확인을 위한 추가 설계 필요 |

## 결정

1. 여석 알림은 at-least-once 전달을 목표로 한다. 선택한 채널별 발송 요청이 외부 서비스에서 최소 한 번 성공적으로 수락·처리되도록 발송과 복구를 설계하며 중복을 허용한다.
2. 성공 응답을 받고 우리 DB에 성공을 기록하면 해당 채널의 작업을 완료한다. 외부 서비스가 성공 응답을 주기 전에 완료로 기록하지 않는다.
3. 실패·타임아웃·응답 유실 등으로 성공 여부가 불확실하면 작업을 완료로 판단하지 않고 재시도 대상으로 둔다.
4. 외부 서비스가 처리했더라도 우리 DB의 성공 기록 전에 서버가 중단되면 복구 후 재시도할 수 있다. 이때 생기는 중복은 기존 결정에 따라 허용한다.
5. 같은 작업의 재시도에는 같은 멱등성 키와 최초 여석 감지 시각을 사용한다. 새로운 여석 발생과 구분한다.
6. 사용자 기기의 실제 수신·화면 표시·사용자의 읽음은 이번 완료 기준에 포함하지 않는다.
7. 발송을 건너뛰는 경우를 성공적인 수락·처리와 동일하게 기록하지 않는다. 채널 비활성화·수신 대상 없음·설정 누락 등의 구체적인 취소·실패 처리 규칙은 별도로 정한다.

## 근거와 결과

사용자의 전달 우선·중복 허용 요구를 반영하며, 우리 서버가 직접 확인할 수 있는 외부 서비스 응답을 완료 기준으로 삼는다. 단순히 API 호출을 한 번 시도한 것만으로 이 전달 목표를 충족했다고 보지 않는다.

실제 전달에는 유효한 수신 대상, 외부 서비스의 회복, 우리 시스템의 복구·재처리 지속 등 조건이 필요하다. 영구적으로 잘못된 주소나 해지된 기기에도 무조건 전달된다는 의미로 사용하지 않는다. 전달 불가·사용자 취소의 범위와 처리는 후속 논의 대상이다.

미전달 작업이 정해진 횟수 실패했다는 이유만으로 완료되거나 복구 경로 없이 사라져서는 이 목표를 지킬 수 없다. 자동 재시도와 중단 후 재개 중 어떤 방식을 사용할지, 그에 필요한 보존·복구 정책은 아직 확정하지 않았다.

## 구현과 검증 상태

사용자가 전달 목표와 성공 기준을 선택하고 의사결정 기록 작성을 승인했다. 이번에는 문서만 작성했으며, 이 목표가 현행 코드에서 충족된다는 검증은 수행하지 않았다.

현행 구현에서 다시 검토할 지점은 다음과 같다.

- [발송 처리](../../apps/server/src/main/java/bhoon/sugang_helper/seatalert/notification/application/SeatNotificationOutboxProcessor.java)는 기본 최대 5회 실패 후 자동 재시도를 중단하고 DLQ로 전환한다.
- [실패 기록 정리](../../apps/server/src/main/java/bhoon/sugang_helper/seatalert/notification/application/NotificationDeliveryRetentionScheduler.java)는 기본 30일 후 DLQ 작업을 삭제한다. 미전달 작업의 재개·보존 정책과 함께 재검토해야 한다.
- [NotificationService](../../apps/server/src/main/java/bhoon/sugang_helper/seatalert/notification/application/NotificationService.java)는 채널 비활성화·대상 없음에서 정상 반환한다. [Discord 발송기](../../apps/server/src/main/java/bhoon/sugang_helper/seatalert/notification/infra/DiscordNotificationSender.java)는 토큰 미설정에서도 정상 반환한다. 호출자가 정상 반환을 성공으로 기록하므로 실제 외부 요청 성공과 구분할 필요가 있다.

구현 시 성공 응답 전 완료 방지, 응답 유실·서버 중단 후 재시도, 발송 생략과 성공 구분을 단위 테스트 후보로 둔다. 최종 E2E 범위와 실행 여부는 구현 논의에서 정한다. 이번에는 테스트를 추가하거나 실행하지 않았다.

## 미결 사항과 재검토 조건

- 재시도 가능한 실패에서 자동 재시도를 계속할지, 일정 횟수 후 보존하고 관리자가 재개할지
- 재시도 간격·최대 간격, 장애 지속 중 요청 부담과 오래된 작업 처리
- 영구 실패·설정 오류·사용자 취소의 구분과 복구·정리 정책
- 웹 푸시의 여러 기기 중 일부만 성공한 경우의 완료 단위
- 향후 사용자 기기의 수신·표시 확인이 제품 요구가 되면 전달 경계 재검토

## 추가 결정: 최초 발송 포함 총 10회, 고정 1분 간격으로 자동 재시도한다

- 상태: Accepted
- 결정일: 2026-10-03
- 범위: 일시적 발송 실패와 성공 여부가 불확실한 요청의 자동 재시도 횟수·간격
- 관련 자료: [채널별 결과·기기 관리와 취소 정책](2026-10-01-notification-channel-policy.md), [지연된 알림의 보존](2026-10-01-delayed-seat-alert-delivery.md), [Discord 요청 제한 지침](https://docs.discord.com/developers/topics/rate-limits)

기존 미결 사항 중 자동 재시도의 횟수와 간격을 구체화한다. 과거 내용은 수정·삭제하지 않고 보존한다.

### 논의와 사용자 선택

- 처음에는 성공할 때까지 횟수 제한 없이 자동 재시도하는 방향을 선택했으나, 문서에 추가하기 전에 사용자가 횟수를 제한하는 방향으로 변경했다.
- 최초 발송을 포함해 총 10회 시도하는 제안을 사용자가 선택했다. 실패 후 재시도는 최대 9회다.
- 대기 간격을 추가로 비교한 뒤 사용자가 고정 1분 간격을 선택했다. 간격을 점차 늘리는 방식은 이번 결정으로 채택하지 않았다.
- 총 10회와 고정 1분은 초기 정책값이다. 운영 측정으로 최적성이 확인된 값은 아니다.

### 확정한 동작

1. 일시적 실패 또는 응답 유실·타임아웃 등으로 성공 여부가 불확실하면 자동 재시도한다.
2. 자동 발송 시도는 최초 발송을 포함해 총 10회로 제한한다. 작업이 성공하면 남은 시도를 수행하지 않는다.
3. 실패 처리 후 다음 시도까지 고정 1분을 기다린다. 외부 서비스가 더 긴 대기시간을 요구하면 해당 시간보다 일찍 재시도하지 않는다.
4. 성공 응답을 받고 DB에 성공을 기록하는 기존 완료 기준을 유지한다. 성공이 기록된 다른 채널·기기를 실패 대상의 재시도에 포함하지 않는다.
5. 총 10회를 소진하면 해당 작업의 자동 재시도를 중단한다. 미발송 작업은 보존하며 성공으로 처리하거나 횟수 소진만을 이유로 삭제하지 않는다.
6. 과목 구독 해제·채널 끄기로 취소된 작업은 재시도하지 않는다. 무효 웹 푸시 주소에는 반복 발송하지 않고 기존 채널 정책에 따라 처리한다. 설정 수정 등 복구가 필요한 오류의 상세 처리는 별도로 정한다.
7. 같은 발생을 재시도할 때 원래 멱등성 키와 여석 감지 시각을 유지한다. 성공 여부가 불확실한 요청을 다시 보내면서 발생하는 중복은 기존 결정대로 허용한다.

### 영향과 남은 설계

- 호출 시간·worker 지연·외부 서비스의 추가 대기 요구를 제외하면, 최대 9회의 1분 대기로 마지막 시도는 최초 시도 후 약 9분에 이루어진다. 실제 발송 시각을 정확히 9분으로 보장하는 정책은 아니다.
- 10회 소진 후 자동 재개할지, 운영자가 재처리할지와 재처리 시 횟수 관리는 아직 확정하지 않았다. 소진 작업을 보존하는 것만으로 전달 목표가 달성되는 것은 아니므로 재개·복구 경로를 추가로 설계해야 한다.
- 시도 횟수를 증가시키는 시점, 서버 중단 시 횟수 처리, SDK 내부 재시도와 작업 횟수의 관계는 상세 설계에서 정한다. 앞선 구현 설명을 저장 구조나 worker 처리 방식의 최종 승인으로 해석하지 않는다.
- 채널별 전체 요청량 제한, 여러 작업이 동시에 재시도되는 경우의 처리, 일시적 실패와 복구 필요 오류의 분류도 상세 설계에서 정한다.
- 실패 후 성공까지 필요한 시도 횟수, 소진 작업 수와 전달 지연의 운영 자료를 보고 초기 정책값을 재검토한다.

### 기록과 구현 상태

사용자가 총 10회와 고정 1분 간격을 선택하고 문서 끝에 추가하는 것을 승인했다. 이번 작업은 결정 기록이며 애플리케이션 코드·실행 설정 변경이나 테스트 추가·실행은 수행하지 않았다.

## 추가 결정: 10회 소진한 작업은 발송 실패로 종료하고 실패한 채널을 안내한다

- 상태: Accepted
- 결정일: 2026-10-03
- 범위: 자동 시도 횟수 소진 후 종료·안내·기록 보존과 전달 목표 변경
- 대체 범위: 기존의 외부 서비스 수락·처리까지 최소 한 번 전달하려는 목표를 아래의 최대 시도 횟수와 최종 실패 허용 정책으로 변경한다. 앞선 소진 후 재개 방식의 미결 사항도 확정한다.
- 관련 자료: [채널별 결과 관리와 기기 대기 정책](2026-10-01-notification-channel-policy.md), [영구 알림함 후속 논의](2026-10-01-persistent-notification-inbox.md)

과거 결정과 당시 미결 사항은 수정·삭제하지 않는다. 전달 목표와 횟수 소진 후 처리에 대해서는 이 추가 결정이 현재 정책이다.

### 비교와 사용자 선택

| 방식 | 소진 후 처리 | 사용자 선택 |
| --- | --- | --- |
| 운영자 수동 재처리 | 원인을 확인한 뒤 실패 작업 재개 | 채택하지 않음 |
| 일정 시간 뒤 자동 재개 | 쉬었다가 발송 시도를 다시 시작 | 채택하지 않음 |
| 실패 안내 후 종료 | 실패 기록을 보존하고 해당 작업은 재발송하지 않음 | 채택 |

사용자는 최초 포함 총 10회 시도, 소진 시 실패 종료·사용자 안내, 기록 보존·자동 및 수동 재발송 없음, 이후 새 여석 발생 정상 발송의 네 가지 규칙을 확정했다. 한 채널만 실패한 경우 알림 전체 실패로 안내하지 않고 해당 채널의 실패만 알리도록 지정했다.

### 확정한 동작

1. 재시도 가능한 작업은 최초 발송 포함 총 10회까지 시도한다. 실패 후 고정 1분 대기와 외부 서비스가 요구한 더 긴 대기시간을 준수하는 기존 규칙을 유지한다.
2. 성공 응답과 DB 성공 기록을 확인하지 못한 채 10회를 소진하면 해당 작업을 발송 실패로 종료하고 사용자에게 안내한다. 이를 발송 성공으로 기록하지 않는다.
3. 종료한 실패 작업의 기록은 보존하지만, 해당 작업은 자동·수동으로 다시 발송하지 않는다. 소진 후 재시도 횟수를 초기화하거나 대기 상태로 복원하는 재처리 방식은 채택하지 않는다.
4. 이후 새로 감지한 여석 발생은 별도 알림 작업으로 정상 발송한다. 이전 작업의 실패만으로 과목 구독이나 해당 채널을 자동 해제하는 것으로 해석하지 않는다.
5. 안내는 실패한 채널을 특정한다. 이메일은 성공하고 Discord만 실패했다면 Discord 발송 실패만 안내하며, 이메일 성공을 취소하거나 전체 알림 실패로 표시하지 않는다.
6. 웹 푸시 결과는 기존 결정대로 기기별로 관리한다. 일부 기기만 실패했다면 웹 푸시의 모든 기기에 실패한 것처럼 안내하지 않는다. 성공이 기록된 기기와 다른 채널은 재발송하지 않는다.
7. 수신 주소가 없어 새 등록을 기다리는 경우는 기존 기기 대기 정책으로 별도 처리한다. 이번 횟수 소진 정책을 그 대기 상태에 일괄 적용해 원래 알림을 종료하는 것으로 확대하지 않는다. 반대로 이미 10회 소진으로 종료한 작업은 새 기기 등록을 이유로 다시 발송하지 않는다.
8. 사용자 구독 해제·채널 끄기에 따른 취소, 무효 주소 처리, 원래 감지 시각과 멱등성 키 유지, 중복 허용 규칙은 계속 적용한다.

### 전달 목표의 변경과 성공 경계

- 현재 정책은 재시도 가능한 작업에 최대 10회 발송을 시도하고 최종 실패를 허용한다. 모든 발송 대상에 외부 서비스 수락·처리가 최소 한 번 이루어진다고 보장하는 at-least-once 전달 정책으로 표현하지 않는다.
- 성공 판정 자체는 외부 서비스의 수락·처리 응답과 DB 성공 기록을 기준으로 유지한다. 사용자 기기의 수신·표시·읽음은 성공 조건이 아니다.
- 성공 여부가 불확실한 요청도 횟수 제한 안에서 재시도한다. 소진으로 실패 종료했더라도 이전 요청이 외부 서비스에서 처리됐을 가능성은 남는다. 안내에서 사용자가 절대로 수신하지 못했다고 단정하지 않도록 상세 문구를 정한다.
- outbox를 유지하고 중복을 허용하는 결정은 변경하지 않는다. 실패 기록 보존은 해당 작업을 다시 보내기 위한 대기를 의미하지 않는다.

### 후속 설계와 구현 상태

- 실패 안내의 위치·문구·생성 단위와 웹 푸시 부분 실패의 표시 방법은 후속 논의에서 정한다. 영구 알림함의 상세 설계도 기존 계획대로 별도로 논의한다.
- 안내를 생성하거나 표시하는 작업이 실패한 경우의 복구, 실패 기록의 보존 기간, 기기 대기 상태와 종료 상태의 관계는 상세 설계에서 정한다.
- 자동 시도 횟수의 기록 시점, 서버 중단 복구와 SDK 내부 재시도의 관계는 아직 미정이다.
- 사용자가 정책과 문서 추가를 승인했다. 기존 문서 끝에 기록만 추가했으며 애플리케이션 코드·실행 설정 변경이나 테스트 추가·실행은 수행하지 않았다.

3. 복구 필요 오류로 확정할 근거가 부족한 경우에는 즉시 중단 대상으로 단정하지 않는다. 오류 분류에는 서비스별 응답 의미를 확인해야 하며, 모든 HTTP 4xx를 같은 오류로 취급하는 규칙을 채택한 것은 아니다.
4. 한 채널이나 기기의 오류를 다른 채널·기기의 실패로 확대하지 않는다. 성공이 기록된 대상은 유지하며 실패 안내도 실제 실패 범위를 반영한다.
5. 웹 푸시 무효 주소는 기존 정책대로 정리하고 해당 주소에 반복 발송하지 않는다. 수신 경로가 모두 사라진 경우 원래 대기 알림을 보존하고 재등록을 기다리는 별도 정책을 유지한다. 이번 즉시 중단 결정을 해당 대기 알림의 일괄 실패 종료로 확대하지 않는다.

### 근거와 남은 설계

- 설정 수정이 필요하다고 확인된 요청을 반복하지 않아 불필요한 시도를 줄인다. 즉시 중단하려면 오류 분류가 정확해야 한다.
- 채널별 구체적인 오류 코드·응답의 분류, 사용자 설정 문제와 서버 설정 문제의 구분은 아직 확정하지 않았다.

- 설정 복구 이후 처리와 이후 새 여석 발생에 대한 동작은 상세 설계에서 정한다. 이번 결정으로 기존 실패 작업의 재발송 기능을 승인하지 않는다.

사용자가 즉시 중단 방식을 선택하고 기존 문서 끝에 추가하는 것을 승인했다. 기존 내용은 수정·삭제하지 않았다. 이번에는 결정만 기록했으며 애플리케이션 코드·실행 설정 변경이나 테스트 추가·실행은 수행하지 않았다.

## 추가 결정: 총 10회는 외부 발송 요청 시도 기준으로 계산한다

| 기준 | 효과 | 선택 |

4. 최종 실패 상태·영구 안내의 DB 저장 복구는 외부 발송 요청이 아니므로 이 한도에 포함하지 않는 기존 결정을 유지한다.

### 남은 설계와 기록 상태

- 요청 전에 횟수를 기록할지 요청 이후 기록할지, 서버 중단으로 요청 실행 여부를 확인하지 못한 시도를 어떻게 계산할지는 아직 확정하지 않았다. 외부 요청과 DB 기록은 같은 트랜잭션으로 묶이지 않으므로 중단 경계를 별도로 설계해야 한다.
- 동시 worker의 한도 예약·중복 실행 방지와 채널별 클라이언트 내부 요청·자동 재시도 동작도 상세 설계에서 확인한다.
- 사용자가 외부 요청 기준을 선택하고 기록 요청에 1번으로 응답했다. 기존 내용은 수정·삭제하지 않고 끝에 추가했다. 이번에는 결정만 기록했으며 애플리케이션 코드·실행 설정 변경이나 테스트 추가·실행은 수행하지 않았다.

## 추가 결정: 단일 worker로 시작하고 외부 호출과 DB 트랜잭션을 분리한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: worker 운영 규모, 발송 시도 기록 시점, 트랜잭션 경계와 외부 호출 제한시간
- 관련 자료: [최종 실패 상태·영구 안내의 동시 저장](2026-10-01-persistent-notification-inbox.md)

### worker 운영 규모

1. 발송 worker는 우선 하나로 운영한다. 여러 worker를 전제로 Redis 잠금 등 별도 조율 기술을 이번 결정으로 도입하지 않는다.
2. 나중에 확장이 필요하다고 판단되면 그때 다중 worker와 작업 확보·조율 방식을 검토한다. 영구적으로 worker 하나만 사용하겠다는 결정은 아니다.
3. 배포·재시작 때에도 의도치 않게 발송 worker가 중복 실행되지 않도록 해야 한다. 단일 운영을 보장하는 배포 방식은 상세 설계에서 정한다.

### 시도 기록과 트랜잭션 경계

1. 첫 DB 트랜잭션에서 작업 확보와 발송 시도 횟수 증가를 기록하고 커밋한다.
2. 첫 트랜잭션이 종료된 뒤 DB 트랜잭션 없이 외부 알림 서비스를 호출한다. 응답을 기다리는 동안 앞선 DB 트랜잭션·잠금을 유지하지 않는다.
3. 외부 호출 결과는 새 DB 트랜잭션에서 저장한다. 성공, 다음 재시도, 최종 실패를 구분하며 최종 실패라면 영구 안내도 같은 트랜잭션에서 저장하는 기존 규칙을 적용한다.
4. 발송 메서드 전체를 하나의 DB 트랜잭션으로 감싸 외부 호출까지 포함하는 방식은 채택하지 않는다.
5. 요청 전에 기록한 시도는 요청 실행 여부가 불확실해도 한 회로 소진한다. 횟수 기록 직후 실제 요청 전에 서버가 중단되면 보내지 못했어도 기회를 소진할 수 있다는 제약을 수용한다.
6. 기존 외부 요청 기준의 총 10회 정책을 사전 시도 기회 기록으로 구체화한다. 실행 여부가 불확실한 사전 기록도 한도에 포함하므로 실제 외부 요청 횟수는 기록한 시도 수보다 적을 수 있다. SDK 내부 재시도가 한도를 우회하지 않아야 한다는 기존 규칙은 유지한다.

### 외부 호출 제한시간

1. 외부 발송 호출 전체에 10초 제한을 둔다. 연결·응답 대기를 각 10초로 두어 전체 시간이 더 늘어나는 정책을 뜻하지 않는다.
2. 타임아웃은 성공 여부 불확실로 처리하고 해당 시도를 한 회로 계산한다. 남은 횟수 내에서 고정 1분 재시도와 외부 서비스가 요구하는 대기시간을 준수한다.
3. 외부 서비스에서는 이미 처리했을 수 있으므로 타임아웃이 미수락·미수신을 보장한다고 해석하지 않는다. 이후 재시도의 중복은 기존 결정대로 허용한다.
4. 10초는 초기 정책값이며 실제 응답 시간에 따른 적정성이 검증된 값은 아니다. 채널별 SDK·HTTP 클라이언트의 제한시간 설정과 요청 종료 동작은 구현 설계에서 확인한다.

최종 실패만 표시하는 방식, 최종 실패와 재시도 대기를 함께 표시하는 방식, 성공·실패·대기·취소 등 모든 발송 상태를 조회하는 방식을 비교했다. 사용자는 최종 실패만 표시하는 방식을 선택했다.

1. 관리자 발송 조회 화면에는 더 이상 발송을 시도하지 않고 실패로 종료된 작업을 표시한다. 재시도 횟수 소진뿐 아니라 명확한 영구 오류로 즉시 최종 실패한 작업도 해당한다.
2. 성공·취소·재시도 대기 작업이나 수신 경로 재등록 대기를 이번 화면에 함께 표시하지 않는다. 아직 종료되지 않은 작업을 최종 실패로 취급하지 않는다.
3. 채널별·웹 푸시 기기별 결과를 구분하여 실패한 작업과 원인을 확인할 수 있게 한다. 한 작업의 실패를 같은 알림의 모든 발송 대상이 실패한 것으로 표시하지 않는다.
4. 대시보드의 최종 실패 요약에서 이 화면으로 이동하는 기존 방향을 유지한다. 재시도 진행 상황이나 전체 성공 이력을 조회하는 화면으로 확대하지 않는다.
5. 종료된 여석·문의 알림은 자동·수동으로 다시 보내지 않는 기존 정책을 유지한다. 이 화면에 해당 작업의 재발송 기능을 추가하지 않는다.
6. 표시 범위 제한은 다른 상태의 원본 작업·발송 기록을 삭제하는 결정이 아니다. 기존 상태·기록 보존 정책은 유지한다.

### 근거와 후속 논의

운영자가 확인할 최종 실패와 원인에 집중하면서 조회 화면의 범위를 제한한다. 재시도 중인 작업의 진행 상황이나 성공 이력을 제품 내 같은 화면에서 확인하지 못하는 제약을 수용한다.

검색·필터·페이지 방식, 진단 정보의 노출 범위와 알림 종류별 포함 범위는 상세 설계에서 정한다. 운영용 Discord 알림의 수동 재발송 허용 여부는 이번 선택으로 확정하지 않는다. 기존 DLQ 조회·재발행 API와 새 화면의 구체적인 전환은 이 범위 및 기존 재발송 금지 정책에 맞춰 후속 설계한다.

이번 변경은 의사결정 기록이며 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 배포 시 진행 중인 요청·발송의 마무리를 제한 시간 동안 기다린다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 계획된 배포 종료에서 HTTP 요청과 알림 worker의 처리
- 참고 자료: [Spring Boot graceful shutdown](https://docs.spring.io/spring-boot/reference/web/graceful-shutdown.html)

### 검토와 결정

진행 중인 처리를 일정 시간 기다린 뒤 종료하는 방식과 바로 종료한 뒤 새 앱에서 복구하는 방식을 비교했다. 사용자는 제한 시간 동안 마무리를 기다리는 방식을 선택했다.

1. 계획된 배포로 종료를 시작하면 새 HTTP 요청을 받아 처리하는 것과 새 발송 작업을 시작하는 것을 멈춘다. worker의 새로운 작업 확보·발송 인계도 종료 흐름에 맞춰 중단한다.
2. 이미 처리 중인 HTTP 요청과 이미 실행 중인 발송은 제한 시간 안에서 처리를 마무리할 기회를 준다. 진행 중인 발송의 결과 저장도 마무리 대상에 포함한다.
3. 종료 대기시간을 무제한으로 두지 않는다. 대기·재시도 예약 작업 전체의 발송 완료를 기다리거나 종료 중 다음 작업을 계속 시작하는 방식은 채택하지 않는다.
4. DB에 남은 대기·미완료 작업은 새 앱에서 기존 복구 정책에 따라 이어서 처리한다. 메모리 대기 목록을 유일한 기록으로 삼지 않으며, 이미 기록한 시도 횟수·예약과 성공·취소·최종 실패 상태를 유지한다.
5. 제한 시간 안에 마무리하지 못한 발송의 성공 여부가 불확실하면 기존 재시도 정책을 적용한다. 종료 대기로 외부 발송 중복 가능성이 사라진다고 보장하지 않는다.
6. 기존 단일 worker 운영을 유지한다. 이전 앱의 worker 종료와 새 앱의 worker 시작이 중첩되지 않도록 구체적인 배포 순서를 설계한다.

### 근거와 후속 논의

즉시 종료에 비해 사용자 요청 중단과 발송 결과 미기록을 줄이면서 배포 종료가 무한히 지연되지 않도록 한다. Spring Boot의 HTTP 종료 대기와 알림 worker의 종료 처리는 각각 확인·설계해야 하며, HTTP graceful shutdown 설정만으로 worker 마무리까지 보장된다고 보지 않는다.

종료 대기 상한, HTTP 요청·worker·DB 결과 저장의 종료 순서, 확보한 대기 작업의 반납·복구와 배포 도구의 종료 유예시간은 상세 설계에서 정한다. 기존 운영 설정의 30초 값을 이번 선택으로 정책값으로 확정하지 않는다. 앱 강제 종료나 프로세스 자체 장애에서 같은 마무리 대기를 보장하는 결정은 아니다.

이번 변경은 의사결정 기록이며 실제 배포·앱 종료, 코드·설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: worker 실행과 업무 정책·트랜잭션 구현의 경계를 분리한다

- 상태: Accepted
- 결정일: 2026-10-13
- 기준: [클린 아키텍처 적용 결정](2026-10-13-clean-architecture-policy.md)

시도 횟수·예약 시각·성공·취소·최종 실패 판단과 결과 저장 복구 정책은 안쪽 유스케이스·도메인에 둔다. 스케줄·스레드·메모리 확보·종료 제어, 외부 호출 제한시간 실행과 Spring 트랜잭션 구현은 바깥 실행·연동 어댑터에서 담당한다. 코어는 필요한 저장·발송 계약을 사용한다.

최초 포함 총 10회·고정 1분, 더 긴 외부 대기 요구 준수, 호출 전체 10초, worker 하나·5초 poll·100개 확보·한 번에 하나 발송과 DB 결과 저장 복구 정책은 유지한다. 결과 저장과 안내 저장의 원자성은 바깥의 같은 DB 트랜잭션 실행 범위에서 보장하고, 외부 호출은 해당 DB 트랜잭션 밖에서 수행한다.

이 추가는 실행 기술의 위치를 보완하는 결정이다. 초기의 무제한 전달 목표를 다시 적용하거나 소진한 작업의 재발송을 허용하지 않는다. 실제 worker·트랜잭션 코드 변경이나 테스트 실행은 하지 않았다.
