# 결정: DB 구조 변경은 Flyway로 관리한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 백엔드 재설계의 DB 스키마 변경 관리 도구
- 대체 결정: 없음
- 관련 자료: `apps/server/build.gradle`, `apps/server/src/main/resources/db/migration/`, `apps/server/src/main/resources/application-prod.yml`, `infra/docker-compose.yml`, `infra/scripts/deploy-release.sh`, `infra/README.md`

## 문제와 확인된 사실

DB 구조 변경을 언제 실행할지 논의하던 중 사용자가 운영 설정에서 Flyway를 꺼둔 이유를 질문했다. 저장소 설정·배포 스크립트와 변경 이력을 확인하여 앱 시작 시 자동 실행만 비활성화되어 있고 별도 Flyway 컨테이너에서 마이그레이션을 실행하는 구성을 설명했다. 이후 사용자는 DB 구조 변경을 Flyway로 하겠다고 결정했다.

- 현재 저장소에 Flyway 의존성과 버전별 SQL 마이그레이션이 있다.
- `application-prod.yml`과 Compose의 앱 환경은 Flyway 자동 실행을 비활성화한다.
- 배포 스크립트는 기존 앱 중지, 별도 Flyway 실행, 성공 후 앱 시작 순서이다. 이는 저장소에서 확인한 구성으로 실제 운영 배포를 실행해 확인한 결과는 아니다.
- 2026-07-13의 `48409fbb` 커밋은 앱 시작 시 Flyway 실행을 끄고 앱의 데이터 접근 권한과 마이그레이션 권한을 분리했다. 현재 Compose와 `infra/README.md`에서는 앱·마이그레이션이 모두 root 계정을 사용하므로 당시 권한 분리 의도를 현재 상태로 단정하지 않는다.

## 결정

1. 재설계에서도 DB 구조 변경은 Flyway로 관리한다. 테이블·컬럼·인덱스·제약 등의 변경을 마이그레이션으로 관리하는 방향을 유지한다.
2. 이번 선택은 DB 구조 변경 관리 도구에 관한 것이다. Flyway를 배포 별도 단계에서 실행할지, 앱 시작 시 실행할지 또는 운영자가 수동으로 실행할지는 아직 확정하지 않는다.
3. 앱과 마이그레이션의 DB 계정·권한 분리 여부도 이번 답변만으로 확정하지 않는다. 현재 자동 실행 비활성화 설정이나 root 계정을 지금 변경하지 않는다.

## 근거와 후속 논의

Flyway 사용은 사용자가 명시적으로 선택했다. 이미 저장소에 있는 도구와 마이그레이션 체계를 활용한다. 이번 대화에서 다른 스키마 관리 도구를 별도로 비교·선택한 것은 아니다.

실행 시점·배포 순서, 기존 적용 이력과 재설계 스키마의 연결, 구버전 호환성·데이터 이동·실패 복구, 마이그레이션 계정과 현재 구성에 맞지 않는 설정 주석의 정리는 후속 논의 또는 상세 설계에서 정한다. 기존 운영 데이터나 적용 이력을 삭제·초기화하는 결정은 아니다.

## 구현과 재검토

이번 변경은 의사결정 기록이며 SQL 작성·실행, 코드·DB·배포 설정 변경이나 테스트 실행은 하지 않았다. Flyway로 해결하기 어려운 구체적인 운영 요구가 확인되면 관리 방식을 재검토한다.

## 추가 결정: Spring Boot 기본 동작대로 앱 시작 시 Flyway를 실행한다

- 상태: Accepted
- 결정일: 2026-10-10
- 확정 범위: 위 실행 시점 미정 항목
- 참고 자료: [Spring Boot 3.5 Flyway 설정 기본값](https://docs.spring.io/spring-boot/3.5/appendix/application-properties/index.html), [시작 시 Flyway 실행](https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html#howto.data-initialization.migration-tool.flyway)

### 검토와 결정

배포 단계에서 별도로 실행하는 방식, 앱 시작 시 실행하는 방식, 운영자가 수동 실행하는 방식을 비교했다. 사용자는 Spring Boot의 `spring.flyway.enabled` 기본값이 `true`이며 앱 시작 시 실행된다는 설명을 확인한 뒤 ‘원래 디폴트로’ 진행하도록 선택했다.

1. 재설계에서는 앱 시작 과정에서 Flyway 마이그레이션을 실행한다. `spring.flyway.enabled`는 기본값 `true`를 따르며 자동 실행 비활성화 설정을 유지하지 않는 방향으로 설계한다.
2. 마이그레이션이 성공해야 앱이 정상적으로 시작하여 요청·발송 작업을 처리하도록 한다. 마이그레이션 실패를 무시하고 실행을 계속하는 방식은 채택하지 않는다.
3. 별도 Flyway 컨테이너 실행을 앱 시작 전 필수 배포 단계로 두는 기존 흐름은 앱 시작 시 실행으로 대체하는 방향으로 재설계한다.
4. 운영 프로필과 Compose 환경변수에 각각 있는 Flyway 비활성화 설정 및 배포 스크립트의 별도 실행 단계를 실제 구현에서 함께 정리한다. 설정 한 곳만 바꾸어 다른 곳의 비활성화 값이 남는 상태를 피한다.
5. 이번 ‘기본값’ 선택은 자동 실행 여부와 실행 시점에 관한 것이다. baseline·repair·clean 등의 다른 Flyway 옵션까지 일괄 초기화하거나 기존 적용 이력을 재작성하는 결정은 아니다.

### 근거와 후속 논의

사용자는 Spring Boot 기본 동작을 선택했다. 앱 시작과 필요한 스키마 변경을 하나의 실행 흐름으로 묶고 별도 필수 마이그레이션 실행 단계의 관리 부담을 줄인다. DB 변경 실패가 앱 시작 실패로 이어지거나 마이그레이션 시간만큼 앱 시작이 지연되는 제약을 수용한다.

DB 계정과 권한 범위, 마이그레이션 실패 시 복구, 구버전 앱과의 호환성 및 실제 배포 전환 순서는 후속 논의 또는 상세 설계에서 정한다. 시작 시 마이그레이션 실패가 이미 실행된 모든 DB 변경을 자동으로 되돌린다고 보장하지 않는다.

이번 변경은 의사결정 기록이며 SQL 실행, 코드·DB·배포 설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 앱과 Flyway는 현재처럼 root 계정을 사용한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 앱 데이터 접근 및 시작 시 Flyway 마이그레이션의 DB 계정

### 검토와 결정

서비스 DB에 필요한 데이터·구조 변경 권한을 부여한 전용 계정 하나를 앱과 Flyway가 함께 사용하는 방식과 현재처럼 root 계정을 사용하는 방식을 비교했다. 사용자는 현재처럼 root 계정을 사용하는 두 번째 방식을 선택했다.

1. 앱의 DB 연결과 앱 시작 시 실행되는 Flyway 마이그레이션 모두 현재처럼 MySQL root 계정을 사용한다.
2. 이번 재설계에서 이를 서비스 전용 계정으로 전환하거나 앱·마이그레이션용 계정을 별도로 나누는 것을 필수 작업으로 추가하지 않는다.
3. Spring Boot 기본 동작에 따라 앱 시작 시 Flyway를 실행하는 기존 결정을 유지한다. 계정 선택을 이유로 별도 마이그레이션 컨테이너의 필수 실행 단계를 되살리지 않는다.

### 근거와 후속 논의

사용자는 전용 계정의 초기 설정 비용과 root 사용 시 앱에 넓은 DB 관리 권한을 주는 제약을 비교한 뒤 기존 구성을 유지하기로 했다. 서비스 DB에 필요한 권한보다 넓은 권한을 앱이 보유하는 비용을 수용하고 계정 운영 구성을 단순하게 유지한다.

이 선택은 앱과 Flyway의 계정에 한정한다. 백업·모니터링 등 다른 작업의 계정 구성이나 DB 네트워크 접근·비밀값 보관 설정까지 변경하는 결정은 아니다. 실제 구현 시 과거 권한 분리 의도와 맞춰 남아 있는 설정 주석·운영 설명을 현행 선택에 맞게 정리한다.

이번 변경은 의사결정 기록이며 실제 DB 계정·권한 변경, SQL 실행, 코드·배포 설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 배포 후 앱의 이전 버전 복귀는 운영자가 판단하여 수행한다

- 상태: Accepted
- 결정일: 2026-10-11
- 범위: 새 버전 배포 후 문제 발생 시 앱 복귀와 DB 복구의 판단
- 관련 결정: [DB·첨부 파일 백업과 수동 복구](2026-10-10-database-backup-policy.md)

### 비교와 결정

운영자가 판단해 이전 앱으로 복귀하는 방식, 조건에 따라 자동 복귀하는 방식, 이전 앱으로 복귀하지 않고 수정 버전으로만 해결하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 새 버전 배포 후 문제가 발생하면 운영자가 원인과 현재 DB 상태를 확인하고, 이전 앱으로 되돌릴지 직접 판단한다. 이번 재설계에 장애 감지에 따른 앱 자동 복귀를 추가하지 않는다.
2. 이전 앱이 현재 DB 구조·데이터 및 실행 설정과 호환되는지 확인한 뒤 복귀한다. 앱 버전만 바꾸면 모든 배포를 되돌릴 수 있다고 전제하지 않는다.
3. 앱의 이전 버전 복귀와 DB 백업 복구를 분리하여 판단한다. 앱을 되돌린다는 이유만으로 DB를 자동으로 백업 시점으로 복원하거나 이미 적용한 Flyway 변경을 자동 역실행하지 않는다.
4. DB 복구가 필요하면 기존 결정대로 운영자가 백업과 복구 시점을 선택하여 수동으로 수행한다. 이전 앱과 호환되지 않는 경우 수정 버전 배포 등 다른 대응이 필요할 수 있다.
5. 앱 시작 시 Flyway 실행·성공 후 정상 시작 정책과 계획된 종료 시 진행 중 요청·발송 정리 및 단일 worker 운영 정책은 유지한다.

### 근거와 후속 논의

관리자 한 명이 운영하는 상황에서 자동 복귀 판단·실행 구성을 추가하지 않고, 장애 원인과 DB 호환성을 확인하여 대응한다. 운영자의 직접 대응이 필요하고 복구 시간이 판단·작업 시간에 영향을 받는 비용을 수용한다.

이전 앱 배포 산출물의 확보, 복귀 실행 절차·기동 확인, DB 변경의 구버전 호환 범위와 실패한 마이그레이션의 복구 방법은 상세 설계에서 정한다. 이번 선택은 모든 DB 변경을 구버전과 호환되게 만드는 방식을 확정하는 결정은 아니다.

이번 변경은 의사결정 기록이며 실제 배포·앱 복귀·DB 복원·SQL 실행이나 코드·서버 설정 변경은 하지 않았다.

## 추가 결정: 배포 중 일시 중단을 허용하고 기존 앱 종료 후 새 앱을 시작한다

기존 앱을 종료한 뒤 새 앱을 시작하여 일시 중단을 허용하는 방식과 새 앱을 미리 시작하여 요청을 전환하는 무중단 배포 목표를 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 앱 배포는 기존 앱 종료 후 새 앱 시작 순서로 진행한다. 배포 중 서비스의 일시 중단을 허용한다.
2. 기존 앱은 앞서 정한 계획된 종료 정책에 따라 새 요청·발송 작업을 시작하지 않고 진행 중 작업을 제한된 시간 동안 정리한다. 기존 worker 종료와 새 worker 시작이 중첩되지 않도록 한다.
3. 새 앱은 시작 과정에서 Flyway 마이그레이션을 실행하며, 성공 후 정상적으로 요청·발송 작업을 처리한다. 중단 시간은 기존 앱 종료, DB 변경 및 새 앱 기동에 걸리는 시간에 따라 달라진다. 일정한 짧은 중단 시간을 보장하지 않는다.
4. 새 버전 배포 후 문제 발생 시 이전 앱 복귀 여부와 DB 호환성은 운영자가 판단하는 기존 정책을 적용한다.

### 근거와 후속 논의

앱 내부 worker 하나를 운영하는 현재 방향에서 두 버전 동시 실행과 요청·worker 전환 제어의 관리 부담을 줄이기 위해 선택했다. 배포와 앱 시작 중 사용자가 서비스를 이용할 수 없는 시간을 수용한다.

구체적인 배포 명령·종료 대기시간·기동 확인과 실패 시 대응 절차는 상세 설계에서 정한다. 이번 변경은 의사결정 기록이며 실제 배포·앱 중지·SQL 실행이나 코드·서버 설정 변경은 하지 않았다.

## 추가 결정: DB 변경은 기본적으로 이전 앱과의 호환성을 유지한다

- 상태: Accepted
- 결정일: 2026-10-11
- 범위: DB 구조·데이터 변경의 구버전 앱 호환 방침

### 비교와 결정

기본적으로 이전 앱의 호환성을 유지하는 방식, 필요한 변경을 한 번에 적용하는 방식, 변경마다 호환 유지 여부를 선택하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

일반 기능은 자동으로 확인하고 실제 외부 서비스 호출·발송 시점은 운영자가 조절할 수 있도록 한다. 명령 실행 대상의 외부 연동 E2E를 별도로 실행해야 해당 연결까지 확인할 수 있다는 비용을 수용한다.

구체적인 시나리오 목록·데이터 준비, CI 실행 조건과 실패 시 배포 차단 여부는 후속 논의 또는 상세 설계에서 정한다. 이번 분류만으로 명령 실행 대상 전체를 매 배포의 필수 검증으로 지정하지 않는다.

이번 변경은 의사결정 기록이며 CI·코드·설정 변경이나 테스트 추가·실행·실제 외부 요청·발송은 하지 않았다.

## 추가 결정: CI 검증 대상 테스트가 실패하면 배포를 중단한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: CI 테스트 결과와 배포 가능 여부의 연결

### 비교와 결정

CI 테스트 실패 시 배포를 중단하는 방식과 실패를 알리되 운영자가 배포 여부를 판단하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. CI 검증 대상으로 정한 테스트가 실패하면 해당 변경의 배포를 중단한다. 실패 안내만 표시하고 같은 변경의 배포를 계속하는 방식을 기본으로 하지 않는다.
2. 배포할 변경의 CI 검증이 성공해야 배포할 수 있도록 한다. 실패 원인이 구현인지 테스트 구성인지 확인하고 수정하여 다시 검증한다.
3. 일반 기능 E2E는 CI, 실제 외부 연동 E2E는 필요할 때 명령으로 실행하는 분류를 유지한다. 이번 선택은 명령 실행 대상 E2E 전체를 매 배포의 필수 실행 단계로 추가하는 결정이 아니다.
4. CI 성공 후 배포를 자동으로 시작할지 운영자가 직접 시작할지는 아직 정하지 않았다. 검증 성공을 배포 시작 방식의 확정으로 해석하지 않는다.

### 근거와 후속 논의

CI에 포함한 일반 기능의 실패를 확인한 상태로 배포하는 것을 막는다. 테스트 구성의 문제도 해결하여 검증을 통과해야 배포할 수 있는 비용을 수용한다.

구체적인 CI 작업·필수 검사 연결과 배포 실행 경로는 상세 설계에서 정한다. 이번 변경은 의사결정 기록이며 CI·배포 설정 변경이나 테스트 실행·실제 배포는 하지 않았다.

## 추가 결정: CI 성공 후 운영자가 직접 배포를 시작한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: CI 검증 성공 이후의 배포 시작 방식

### 비교와 결정

CI 통과 후 버튼이나 명령으로 직접 배포를 시작하는 방식, 기본 브랜치 반영 시 자동 배포하는 방식, 릴리스 태그 생성 시 자동 배포하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 배포할 변경의 CI 검증 성공을 배포의 전제 조건으로 유지하되, CI 성공만으로 배포를 자동으로 시작하지 않는다.
2. 운영자가 원하는 시점에 버튼이나 명령으로 배포를 직접 시작한다. 기본 브랜치 반영이나 릴리스 태그 생성 자체를 자동 배포 시작 조건으로 두지 않는다.
3. 기존의 계획된 종료 처리, 기존 앱 종료 후 새 앱 시작, 발송 worker 하나 운영 및 배포 시 중복 실행 방지, 새 앱 시작 시 Flyway 실행 정책을 유지한다.
4. 배포 실패 시 이전 앱으로 되돌릴지는 운영자가 현재 DB·데이터·설정과의 호환성을 확인하여 판단한다는 기존 정책을 유지한다.

### 근거와 후속 논의

CI로 변경을 검증하는 시점과 실제 서비스에 반영하는 시점을 구분하여 운영자가 배포 시간을 조절할 수 있도록 한다. 배포를 직접 시작해야 하는 운영 비용을 수용한다.

구체적인 버튼·명령과 배포 대상 산출물의 선택·검증 연결은 상세 설계에서 정한다. 이번 변경은 의사결정 기록이며 CI·배포 설정 변경이나 테스트 실행·실제 배포는 하지 않았다.
