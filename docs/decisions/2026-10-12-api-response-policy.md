# 결정: 성공 응답은 데이터를 직접 반환하고 오류만 공통 형식을 사용한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 백엔드 JSON API의 성공·오류 응답 구조와 프론트 전환
- 대체 결정: 없음. 성공·오류 모두 공통 포맷을 유지하는 방식은 비교 제안이며 확정된 결정이 아니었음
- 관련 자료: `apps/server/src/main/java/bhoon/sugang_helper/common/response/CommonResponse.java`, `apps/server/src/main/java/bhoon/sugang_helper/common/response/ErrorResponse.java`, `apps/web/src/shared/types/api.ts`, `apps/web/src/features/`

## 문제와 확인된 사실

현재 성공 응답의 공통 포맷은 `code`, `message`, `data`로 구성된다. 오류는 별도의 `ErrorResponse`를 사용한다. 프론트의 공통 타입과 여러 기능 API 모듈에서 `CommonResponse<T>`를 사용하고 있다.

현재 구조를 유지하는 방식과 성공 응답의 공통 포장을 제거하고 오류 응답만 통일하는 방식을 비교했다. 사용자는 ‘성공은 데이터만 반환하고 오류만 감싸서’라고 선택했다.

## 결정

1. 성공 JSON 응답은 기능에 필요한 데이터 자체를 반환한다. 성공 응답을 공통 `code`, `message`, `data` 객체로 감싸는 방식은 재설계에서 제거한다.
2. 오류 응답은 공통 오류 형식으로 처리한다. 이번 선택은 기존 오류 응답의 모든 필드 유지나 추가 `error` 중첩 객체의 도입까지 확정하는 결정은 아니다. 구체적인 필드는 상세 설계 또는 후속 논의에서 정한다.
3. 페이지 목록의 항목·다음 페이지 여부 등 기능에 필요한 데이터 구조는 유지할 수 있다. 성공 응답을 직접 반환한다는 선택을 모든 목록을 메타데이터 없는 배열로 바꾸라는 요구로 해석하지 않는다.
4. 서버 응답과 함께 프론트의 `CommonResponse<T>` 타입, API 호출 모듈 및 성공 응답에서 공통 `data`를 해제하는 사용처를 전환 대상으로 삼는다. 서버 응답만 변경하여 기존 프론트가 잘못 해석하는 상태를 피한다.
5. 데이터 없는 성공 응답과 각 API의 HTTP 상태 코드, 파일 다운로드·리다이렉트 등의 구체적인 계약은 상세 설계에서 정한다.

## 근거와 결과

사용자는 성공 응답을 데이터 자체로 단순화하고 오류 처리 형식은 공통으로 유지하기로 했다. 성공 데이터 접근의 공통 중첩을 줄이는 대신 기존 서버·프론트의 응답 해석을 함께 바꾸는 비용을 수용한다.

## 구현과 후속 논의

API별 응답·프론트 사용처의 전환 순서, 오류 응답의 필드·메시지 규칙과 빈 성공 응답 처리는 상세 설계에서 정한다. 응답 데이터 안에 기능상 필요한 이름이 `data`인 필드까지 일괄 금지하는 규칙은 아니다.

이번 변경은 의사결정 기록이며 실제 서버·프론트 코드나 실행 설정을 변경하지 않았고 테스트를 실행하지 않았다.

## 재검토 조건

공통 성공 메타데이터가 필요한 구체적인 사용 사례가 나타나면 필요한 범위에 한해 다시 검토한다.

## 추가 결정: 오류 코드와 사용자 안내 문구는 서버에서 관리한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: API 오류의 사용자 표시 문구 관리 위치

### 비교와 결정

서버에서 코드·안내 문구를 관리하는 방식, 서버는 코드만 보내고 프론트가 문구를 선택하는 방식, 서버 기본 문구와 프론트의 일부 대체 문구를 혼합하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 서버는 공통 오류 응답에 오류 코드와 사용자에게 보여줄 안내 문구를 제공한다. 프론트는 서버가 전달한 안내 문구를 표시하는 것을 기본으로 한다.
2. 업무 규칙과 관련 안내 문구를 서버에서 함께 관리한다. 예를 들어 구독 개수 제한 규칙과 해당 제한을 설명하는 문구를 함께 관리한다.
3. 프론트에서 모든 오류 코드에 대한 안내 문구를 별도로 매핑하는 구조나 일부 코드의 문구를 프론트에서 대체하는 혼합 구조는 이번 기본 방식으로 채택하지 않는다.
4. 성공 데이터를 직접 반환하고 오류만 공통 형식을 사용하는 기존 결정을 유지한다. 이번 선택은 오류 응답의 세부 필드·입력 검증 오류의 표현 방식까지 확정하는 결정은 아니다.

### 근거와 후속 논의

업무 규칙과 오류 안내 문구의 관리 위치를 모아 같은 오류의 문구를 서버·프론트 양쪽에서 맞추는 부담을 줄인다. 문구 변경에 서버 배포가 필요한 비용을 수용한다.

네트워크 단절처럼 서버 오류 응답을 받지 못한 경우의 프론트 안내와 예상하지 못한 내부 오류의 사용자 안내 범위는 상세 설계 또는 후속 논의에서 정한다. 서버가 제공하는 사용자 안내 문구를 내부 예외 원문과 동일한 것으로 간주하지 않는다.

이번 변경은 의사결정 기록이며 실제 서버·프론트 코드나 오류 안내 문구를 변경하지 않았고 테스트를 실행하지 않았다.

## 추가 결정: 확인 가능한 입력 오류는 항목별로 한꺼번에 안내한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 한 요청에 여러 입력 검증 오류가 있을 때의 응답과 표시

### 비교와 결정

항목별 오류를 한꺼번에 안내하는 방식, 첫 번째 오류만 안내하는 방식, 입력값을 확인하라는 공통 안내만 표시하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 한 요청에서 확인 가능한 입력 검증 오류들을 모아 공통 오류 응답으로 반환한다. 첫 번째 입력 오류만 고친 뒤 제출을 반복하도록 하는 방식을 기본으로 하지 않는다.
2. 오류가 있는 입력 항목을 식별할 수 있는 정보와 각 항목의 사용자 안내 문구를 제공한다. 프론트는 해당 입력칸에 오류를 표시한다.
3. 항목별 안내 문구도 기존 결정대로 서버에서 관리한다. 성공 응답은 데이터 자체를 반환하고 오류 응답만 공통 형식을 사용한다.
4. 이 결정은 확인 가능한 입력 오류의 일괄 안내에 관한 것이다. 앞선 검증 실패로 확인할 수 없는 후속 업무 규칙이나 외부 시스템의 모든 오류까지 반드시 실행·수집하는 요구로 확대하지 않는다.

### 근거와 후속 논의

사용자가 잘못 입력한 항목을 한 번에 확인하고 수정할 수 있도록 한다. 서버의 항목별 오류 응답과 프론트의 입력칸별 표시 처리가 필요한 비용을 수용한다.

오류 목록의 구체적인 필드명·형식, 같은 항목에 여러 오류가 있는 경우의 표시와 특정 입력칸에 연결되지 않는 검증 오류의 안내는 상세 설계에서 정한다. 이번 변경은 의사결정 기록이며 실제 검증 코드·서버 응답·프론트 표시를 변경하지 않았고 테스트를 실행하지 않았다.

## 추가 결정: 브라우저의 API 요청은 실패 시 자동 재시도하지 않는다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 브라우저·PWA에서 우리 백엔드로 보내는 API 요청의 실패 후 동작

### 비교와 결정

조회 요청만 제한적으로 자동 재시도하는 방식, 자동 재시도하지 않는 방식, 멱등성을 보장한 일부 변경 요청까지 자동 재시도하는 방식을 비교했다. 일시적인 조회 실패를 숨길 수 있는 편의성과 재시도에 따른 요청 증가·실패 안내 지연·관리 부담을 설명한 뒤 사용자는 두 번째 방식을 선택했다.

1. 브라우저·PWA의 API 요청이 실패하면 클라이언트가 같은 요청을 자동으로 재전송하지 않는다. 조회·등록·수정·삭제 모두 이 기본 방침을 적용한다.
2. 실패를 안내하고, 사용자가 필요에 따라 새로고침·재조회·재제출 등의 동작을 직접 선택하도록 한다. 입력 검증 실패는 기존 결정대로 항목별 오류를 안내한다.
3. 응답을 받지 못한 변경 요청은 서버에서 이미 처리되었을 수 있다. 자동 재시도를 없애는 것만으로 중복 제출이나 결과 불확실성이 해결된다고 간주하지 않는다. 처리 결과를 확인할 수 있는 기능별 안내·재제출 처리는 상세 설계에서 정한다.
4. 이번 결정은 API 요청 실패에 따른 클라이언트 자동 재시도에 한정한다. 서버의 outbox 발송 재시도와 DB 결과 저장 복구 정책은 기존 결정을 유지한다. 화면 진입이나 사용자의 수동 새로고침에 따른 새 조회를 금지하는 결정은 아니다.

### 근거와 후속 논의

현재는 자동 재시도 없이 시작하여 동작을 단순하게 유지한다. 일시적인 조회 실패도 사용자가 다시 시도해야 하는 비용을 수용한다. 조회 실패로 인한 사용자 불편이 실제로 확인되면 필요한 범위의 자동 재시도를 재검토한다.

기존 클라이언트 라이브러리·공통 요청 처리에 설정된 재시도 여부와 기능별 실패 안내는 실제 구현에서 함께 점검한다. 이번 변경은 의사결정 기록이며 서버·프론트 코드나 실행 설정을 변경하지 않았고 테스트를 실행하지 않았다.

## 추가 결정: 예상하지 못한 서버 오류는 공통 안내와 요청별 오류 ID를 표시한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 예상하지 못한 내부 서버 오류의 사용자 안내와 로그 연결
- 관련 자료: `apps/server/src/main/java/bhoon/sugang_helper/common/response/ErrorResponse.java`, `apps/server/src/main/java/bhoon/sugang_helper/common/web/GlobalExceptionHandler.java`

### 비교와 결정

공통 안내와 요청별 오류 ID를 표시하는 방식, 공통 안내만 표시하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 예상하지 못한 서버 오류가 발생하면 사용자에게 공통 안내 문구와 해당 요청을 식별할 수 있는 오류 ID를 표시한다.
2. 상세 원인은 서버 로그에 기록하고, 사용자에게 전달한 오류 ID로 해당 로그를 찾을 수 있도록 연결한다. 사용자 화면에 내부 예외 원문을 그대로 표시하는 방식은 채택하지 않는다.
3. 요청별 오류 ID는 오류 종류를 나타내는 업무 오류 코드와 구분한다. 오류 ID는 같은 종류의 오류 중 사용자가 겪은 요청을 찾기 위한 용도로 사용한다.
4. 구독 개수 제한과 입력 검증 실패 등 예상된 업무 오류에는 기존 결정대로 서버에서 관리하는 구체적인 안내 문구를 사용한다. 모든 오류를 예상하지 못한 내부 오류의 공통 안내로 바꾸지 않는다.

### 근거와 후속 논의

사용자 문의에서 전달받은 ID로 서버 로그를 찾을 수 있어 발생 시각과 상황만으로 조사하는 부담을 줄인다. 현재 `ErrorResponse`와 예외 처리 코드에도 `correlationId`를 통한 응답·로그 연결이 있으므로 해당 개념을 활용하는 방향으로 설계한다.

응답 필드명과 화면 표시·복사 방식, 로그의 ID 생성·전파 세부 구현은 상세 설계에서 정한다. 이번 결정은 새 로그 검색 서비스나 자동 문의 생성 기능을 도입하는 결정은 아니다.

이번 변경은 의사결정 기록이며 실제 응답·로그·프론트 화면이나 서버 설정을 변경하지 않았고 테스트를 실행하지 않았다.

## 추가 결정: 업무 오류와 HTTP 오류 매핑을 분리한다

- 상태: Accepted
- 결정일: 2026-10-13
- 기준: [클린 아키텍처 적용 결정](2026-10-13-clean-architecture-policy.md)

1. 안쪽 도메인·유스케이스는 업무 오류 종류와 필요한 데이터를 정의하며 Spring `HttpStatus`·`ResponseEntity`·Servlet·웹 오류 JSON에 의존하지 않는다. 현행 `ErrorCode`의 업무 오류와 HTTP 상태 결합은 분리 대상이다.
2. 웹 어댑터가 업무 오류를 HTTP 상태·공통 오류 응답·사용자 안내 문구로 연결한다. 안내 문구는 기존 결정대로 서버에서 관리한다. 같은 서버 안에서 경계를 분리하는 것이며 프론트에 전체 오류 문구 매핑을 넘기지 않는다.
3. 항목별 입력 오류는 웹 형식 검증과 안쪽 업무 검증의 결과를 필요한 범위에서 조합해 안내한다. 소유권·상태·제한 같은 업무 규칙을 웹 검증에만 맡기지 않는다.
4. 성공 데이터 직접 반환, 오류 공통 형식, 요청별 오류 ID, 내부 원문 비노출·로그 연결과 브라우저 자동 재시도 없음 정책은 유지한다. HTTP·로그 형식은 바깥에서 변환한다.

이번 추가는 오류 표현의 의존성 정정이며 실제 오류 코드·응답·프론트 변경이나 테스트 실행은 하지 않았다.

## 변경 기준: MVC 레이어드 구조로 폴더 정리 후 기능을 전환한다

- 상태: Accepted
- 결정일: 2026-10-13
- 기준: [기능별 MVC 레이어드 구조 결정](2026-10-13-mvc-layered-architecture-policy.md)

앞서 클린 아키텍처를 전제로 추가한 순수 코어·별도 영속성 모델·포트·어댑터·프레임워크 의존 제한은 최신 MVC 결정으로 대체한다. 서비스의 Spring·트랜잭션·로거 사용과 JPA 엔티티·저장소 연결을 허용한다. 기능에 관한 기존 사용자 정책은 유지한다. 현재 단계는 기존 동작을 보존한 역할별 폴더 정리이며, 계약 통합·업무 동작·API·DB 변경은 후속 구현에서 진행한다.
