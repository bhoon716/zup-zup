# 결정: Lombok은 getter·생성자·로거·빌더에 한정한다

- 상태: Accepted
- 결정일: 2026-10-12
- 범위: 백엔드 재설계에서 허용할 Lombok 기능
- 대체 결정: 없음
- 관련 자료: [백엔드 재설계 체크리스트](../backend-redesign-checklist.md), [Lombok getter·setter](https://projectlombok.org/features/GetterSetter), [생성자](https://projectlombok.org/features/constructor), [로거](https://projectlombok.org/features/log), [빌더](https://projectlombok.org/features/Builder)

## 문제와 선택지

현재 백엔드에서 사용하는 Lombok의 반복 코드 감소 효과와 컴파일 시 생성되는 동작을 이해·관리하는 비용을 비교했다. 필요한 기능만 제한하여 사용하는 방식, 폭넓게 사용하는 방식, 제거하고 직접 작성하는 방식을 논의했다.

## 결정

1. Lombok 의존성은 유지하되 허용 범위는 getter·생성자·로거·빌더로 한정한다. 사용자는 제한 사용 방식을 선택하면서 이 네 가지 범위를 명시했다.
2. `@Getter`, `@NoArgsConstructor`·`@RequiredArgsConstructor`·`@AllArgsConstructor`, `@Slf4j`, `@Builder` 등이 허용 범위에 해당한다. 필요한 곳에 선택하여 사용하며 모든 클래스에 일괄 적용하지 않는다.
3. `@Setter`, `@Data`, `@Value`, `@EqualsAndHashCode`, `@ToString` 등 위 네 가지 범위를 넘어서는 Lombok 기능은 재설계의 허용 범위에서 제외한다. getter·생성자 외 동작도 함께 생성하는 묶음 애너테이션을 허용된 기능의 대체로 사용하지 않는다.
4. 생성자·빌더 사용 시에도 객체 생성에 필요한 검증과 초기화 규칙을 지켜야 한다. 각 클래스의 접근 수준과 사용 방식은 상세 설계에서 정한다.
5. 이번 선택으로 DTO의 Java record 전환, 엔티티의 동등성 규칙이나 실제 데이터 변경 메서드의 구체적인 설계를 함께 확정하지 않는다.

## 근거와 수용한 비용

반복되는 getter·생성자·로거·빌더 코드를 줄이면서 Lombok이 생성하는 기능의 범위를 제한한다. Lombok 애너테이션 처리와 IDE·빌드 연동 비용은 유지하고, 제외한 기능이 필요한 경우 해당 동작을 명시적으로 작성하는 비용을 수용한다.

기존 허용 범위 밖의 사용은 재설계 시 확인하여 전환한다. 이미 생성되어 사용 중인 메서드를 애너테이션 제거만으로 없애지 않도록 실제 호출과 동작을 확인한다.

## 구현과 재검토

이번 변경은 의사결정 기록이며 Java 코드·의존성·빌드 설정 변경이나 테스트 실행은 하지 않았다. 범위 밖의 기능이 반복 코드를 줄이는 데 필요하다는 구체적인 근거가 생기면 추가 사용 여부를 다시 논의한다.

## 추가 결정: 로거 생성은 업무 코어 밖에서 사용한다

- 상태: Accepted
- 결정일: 2026-10-13
- 기준: [클린 아키텍처 적용 결정](2026-10-13-clean-architecture-policy.md)

getter·생성자·빌더의 기존 제한 사용은 컴파일 보조 기능으로 유지한다. 로거 생성도 허용 기능 목록에 유지하되 `@Slf4j`가 생성하는 로깅 구현 의존성은 웹·실행·영속성·외부 연동 어댑터 등 바깥 영역에 한정한다. 안쪽 도메인·유스케이스에서 SLF4J나 Micrometer를 직접 사용하지 않는다.

업무 결과·필요한 기록 계약을 통해 바깥 기록 경로로 정보를 제공한다. 일반 로그 보관과 교수·시간 변경을 로그로만 기록하는 기존 정책은 유지한다. 이번 추가는 사용 영역 제한이며 실제 Lombok·로그 코드 변경이나 테스트 실행은 하지 않았다.
