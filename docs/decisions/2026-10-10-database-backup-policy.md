# 결정: DB 백업은 서버에 보관하고 외부 복사는 수동으로 한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: DB 백업의 보관 위치와 서버 밖 복사 방식
- 대체 결정: 없음
- 관련 자료: `infra/README.md:118`, [Flyway 마이그레이션 정책](2026-10-10-database-migration-policy.md)

## 문제와 확인된 사실

DB 변경 실패나 서버 장애에 대비한 백업 보관 위치를 결정한다. 저장소의 운영 문서에는 같은 OCI 서버 안에 MySQL logical dump를 주기적으로 저장하는 구성이 설명되어 있다. 문서상 주기는 매주 월요일 04:00(Asia/Seoul)이며, 실제 서버의 백업 파일이나 timer 실행 결과는 이번 대화에서 확인하지 않았다.

## 선택지 비교

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 서버 보관과 외부 자동 복사 | 서버를 잃어도 별도 저장소의 백업을 사용할 수 있음 | 외부 저장소와 자동 복사 설정을 관리해야 함 |
| 같은 서버에만 보관 | 운영 구성이 단순함 | 서버와 백업을 함께 잃을 수 있음 |
| 서버 보관과 외부 수동 다운로드 | 외부 자동 전송 설정 없이 별도 사본을 보관할 수 있음 | 다운로드를 잊으면 서버 밖 사본이 오래되거나 없을 수 있음 |

## 결정

1. DB 백업은 서버에 보관하고, 필요할 때 운영자가 본인 PC 등 서버 밖으로 직접 다운로드한다. 사용자는 세 번째 방식을 선택했다.
2. 이번 재설계에서 외부 저장소로 자동 복사하는 기능을 추가하지 않는다. 특정 외부 저장소 서비스나 새 자동 전송 기술을 도입하지 않는다.
3. 서버 안의 백업 생성과 서버 밖 사본의 복사를 구분한다. 외부 복사를 수동으로 한다는 선택을 서버 안의 정기 백업 생성까지 수동으로 바꾸라는 요구로 해석하지 않는다.
4. 서버 자체를 잃었을 때는 실제로 다운로드하여 보관한 외부 사본의 시점까지 복구할 수 있다. 서버 안의 최신 백업이 외부에도 자동 보관된 것으로 간주하지 않는다.

## 근거와 후속 논의

사용자는 외부 자동 복사 설정을 추가하는 방식 대신 필요할 때 직접 사본을 다운로드하는 방식을 선택했다. 외부 사본의 최신성을 운영자가 직접 관리하는 부담을 수용한다.

서버 안의 백업 생성 주기·보존 기간, 다운로드 시점·보관 방법, 복구 절차와 백업 실패 확인은 후속 논의 또는 상세 설계에서 정한다. 문서에 기재된 주간 백업 주기를 이번 답변만으로 재설계 정책값으로 확정하지 않는다. 이번 선택은 DB 백업 보관에 한정하며 문의 첨부 파일·Redis·로그 등 다른 데이터의 백업 범위를 자동 확정하지 않는다.

## 구현과 재검토

이번 변경은 의사결정 기록이며 실제 DB 백업·다운로드·외부 전송, 서버 설정 변경이나 테스트 실행은 하지 않았다. 사본 다운로드 누락이나 복구 시점의 오래됨이 문제가 되면 외부 자동 복사를 재검토한다.

## 추가 결정: DB 자동 백업은 매일 한 번 생성하고 최신 소수만 보관한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 서버 안의 DB 자동 백업 생성 주기와 보관 규모

### 검토와 결정

매일 자동 생성, 매주 자동 생성, 필요할 때만 수동 생성하는 방식을 비교했다. 사용자는 논의 대상이 로그 백업이 아닌 DB 백업임을 확인한 뒤 ‘매일 1회, 대신 최신 개수는 조금만’으로 결정했다.

1. MySQL DB 자동 백업을 매일 한 번 생성한다. 기존 운영 문서의 주간 백업 설명을 재설계 주기로 그대로 채택하지 않는다.
2. 서버 안에는 최신 백업을 소수만 보관하는 방식으로 저장량을 제한한다. 정확한 보관 개수는 아직 선택되지 않았으므로 별도로 정한다.
3. 서버 밖 사본은 앞서 결정한 대로 필요할 때 운영자가 직접 다운로드한다. 일간 자동 생성 선택을 외부 자동 복사 도입으로 확대하지 않는다.
4. 이번 보관 규모 선택은 서버 안의 DB 백업 파일에 한정한다. 실제 DB의 원본 데이터 보존 기간, 로그 보관 정책이나 이미 다운로드한 개인 PC 사본의 자동 삭제를 정하는 결정은 아니다.

### 근거와 후속 논의

주간보다 자주 복구 시점을 확보하면서 최신 소수 보관으로 백업 파일의 누적을 제한한다. 오래전 시점으로 되돌아갈 수 있는 범위가 줄어드는 제약을 수용한다.

정확한 보관 개수와 일일 실행 시각, 백업 성공 확인·오래된 파일 정리의 순서와 실패 처리는 후속 논의 또는 상세 설계에서 정한다. 이번 기록만으로 기존 백업을 삭제하거나 서버의 timer를 변경하지 않는다.

이번 변경은 의사결정 기록이며 실제 DB 백업·파일 삭제·다운로드, 서버 설정 변경이나 테스트 실행은 하지 않았다.

## 추가 결정: 서버에는 최신 DB 백업 세 개를 보관한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 서버 안의 DB 백업 보관 개수

### 결정

1. 매일 한 번 생성하는 DB 백업 중 성공적으로 생성된 최신 세 개를 서버에 보관한다. 앞서 미정으로 남긴 정확한 보관 개수를 확정한다.
2. 새 백업의 생성 성공을 확인한 뒤 보관 개수를 넘는 오래된 백업을 정리한다. 새 백업 생성이 실패하면 기존 백업을 유지한다.
3. 세 개는 성공한 백업의 개수이며, 백업 실패가 있으면 최근 사흘의 복구 시점이 모두 확보된다는 뜻은 아니다.
4. 서버 밖 사본은 기존 결정대로 필요할 때 수동 다운로드한다. 개인 PC에 내려받은 사본의 삭제 정책이나 DB 원본 데이터의 보존 기간은 이번 결정에 포함하지 않는다.

### 근거와 후속 논의

사용자는 최신 세 개와 일곱 개 중 세 개를 선택했다. 일간 백업을 유지하면서 서버 안에 누적되는 사본의 수를 작게 제한한다.

일일 실행 시각과 백업 성공 확인·파일 정리의 구체적인 구현은 상세 설계에서 정한다. 이번 변경은 의사결정 기록이며 실제 백업 생성·삭제·다운로드나 서버 설정 변경은 하지 않았다.

## 추가 결정: 문의 첨부 이미지도 DB와 함께 백업한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 정기 백업에 포함하는 문의 첨부 이미지 파일

### 검토와 결정

DB와 첨부 이미지를 모두 백업하는 방식과 DB만 백업하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. DB뿐 아니라 서버의 별도 파일로 저장하는 문의 첨부 이미지도 백업 대상에 포함한다. DB의 첨부 정보만 복구하고 실제 이미지 파일은 잃는 상황을 줄이기 위한 결정이다.
2. 앞서 결정한 매일 한 번 생성·최신 세 개 보관 정책의 백업 범위에 첨부 이미지를 포함한다. 서버 밖 사본을 수동으로 다운로드할 때도 이미지 파일을 함께 확보할 수 있도록 한다.
3. 문의 첨부 이미지의 영구 보존 정책을 반영하여, 보존 대상인 소프트 삭제된 첨부 이미지도 백업 범위에서 제외하지 않는다. 백업 사본 세 개의 보관 제한은 원본 첨부 이미지의 삭제 기간을 정하는 규칙이 아니다.
4. Redis와 로그의 백업 여부는 이번 선택으로 확정하지 않는다.

### 근거와 후속 논의

현재 파일 저장 구현은 이미지 파일을 로컬 업로드 디렉터리에 기록한다. DB 백업만으로는 해당 파일의 실제 내용을 복구할 수 없다. 문의와 첨부 이미지의 복구를 위해 백업 용량과 생성 시간이 늘어나는 비용을 수용한다.

DB와 첨부 파일 사이의 복구 시점 일치 방법, 묶음 파일 형식과 성공 확인·보관 정리 방법은 상세 설계에서 정한다. 이번 변경은 의사결정 기록이며 실제 백업 실행이나 파일·서버 설정 변경은 하지 않았다.

## 추가 결정: 백업 실패 발생과 이후 성공을 Discord로 안내한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 정기 백업 실패와 복구의 운영자 안내
- 관련 결정: [상태 확인과 장애 안내 정책](2026-10-10-health-check-policy.md)

### 검토와 결정

한 번의 실패부터 안내하는 방식, 이틀 연속 실패한 뒤 안내하는 방식, 로그만 기록하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 정기 백업이 한 번 실패해도 기존 장애 안내용 Discord 채널로 운영자에게 안내한다. 이틀 연속 실패할 때까지 기다리거나 로그 확인에만 의존하지 않는다.
2. 실패 안내 후 이후 백업이 성공하면 같은 채널로 백업 복구 안내를 보낸다. 백업을 시작했거나 앱이 정상 응답한다는 사실만으로 백업 복구를 안내하지 않는다.
3. 안내 대상 백업에는 앞서 선택한 DB와 문의 첨부 이미지가 포함된다. 성공 확인의 구체적인 검증 방법은 상세 설계에서 정한다.
4. 기존 장애 안내 정책의 동일 장애에 대한 주기적 재안내 제외 원칙을 적용한다. 최초 실패와 이후 복구를 안내하며, 반복 실패 안내의 구체적인 상태 관리와 Discord 전송 실패 처리는 상세 설계에서 정한다.
5. 이번 안내 결정을 백업 자동 재시도나 외부 자동 복사 도입으로 확대하지 않는다. 매일 한 번 생성·최신 세 개 보관과 새 백업 실패 시 기존 사본 유지 정책은 그대로 적용한다.

### 근거와 후속 논의

최신 소수의 백업을 보관하는 운영에서 백업 생성 실패를 바로 파악하고 대응하기 위해 선택했다. 일시적인 실패도 안내받는 비용을 수용한다.

장애 안내용 기존 경로를 사용하며, 별도 개인 수신 채널이나 새 알림 기술은 이번 결정으로 추가하지 않는다. 백업 실행 누락의 감지 여부와 백업 프로세스·안내 전송의 구현은 상세 설계에서 정한다. 이번 변경은 의사결정 기록이며 실제 백업·Discord 발송·서버 설정 변경은 하지 않았다.

## 추가 결정: 백업 복구는 운영자가 서버에서 수동으로 수행한다

- 상태: Accepted
- 결정일: 2026-10-10
- 범위: 백업으로부터 실제 데이터를 복구하는 실행 방식

### 검토와 결정

운영자가 서버에서 수동 복구하는 방식, 관리자 페이지에서 실행하는 방식, 장애 시 자동 복구하는 방식을 비교했다. 사용자는 첫 번째 방식을 선택했다.

1. 운영자가 복구 필요성과 사용할 백업을 판단하고, 서버에서 복구 절차를 직접 실행한다.
2. DB와 문의 첨부 이미지의 복구 절차를 문서화한다. 실제 실행 명령과 작업 순서, 복구 전후 확인 항목은 상세 설계에서 작성한다.
3. 관리자 페이지의 백업 복구 기능과 장애 발생에 따른 자동 백업 복원은 이번 재설계 범위에 추가하지 않는다. 앱 프로세스 자동 재시작과 백업 데이터 복원은 별개의 동작으로 취급한다.
4. 백업 시점으로 복구하면 그 이후의 변경 내용이 사라질 수 있음을 전제로 운영자가 복구 시점을 선택한다. 복구 실행에 운영자의 직접 작업이 필요하다는 비용을 수용한다.
5. 기존 매일 한 번 백업 생성, 최신 세 개 보관, 외부 사본 수동 다운로드 및 백업 실패·복구 안내 정책은 유지한다. 이번 선택은 정기 백업 생성까지 수동으로 변경하는 결정이 아니다.

### 근거와 후속 논의

관리자 한 명이 운영하는 상황에서 별도의 복구 UI나 자동 판단 기능을 관리하는 부담을 줄이고, 데이터를 되돌릴지 운영자가 직접 판단하도록 한다.

복구 중 앱·worker 운영, 백업과 실행할 앱 버전의 호환성, 복구된 대기 알림의 처리 및 DB·첨부 파일 확인 방법은 상세 설계에서 다룬다. 이번 변경은 의사결정 기록이며 실제 DB 복원·파일 덮어쓰기·서버 설정 변경은 하지 않았다.
