# 결정: 영구 알림함 요구를 별도로 기록하고 상세 설계는 추후 논의한다

- 상태: Accepted
- 결정일: 2026-10-01
- 범위: 사용자에게 남는 서비스 내 알림함의 제품 요구와 후속 논의 범위
- 대체 결정: 없음
- 관련 자료: [채널별 발송 정책과 기기 대기 안내](2026-10-01-notification-channel-policy.md), [전달 목표와 완료 기준](2026-10-01-notification-at-least-once-delivery.md)

## 사용자 설명과 목표

사용자는 현재 알림을 외부 채널 알림과 프론트의 일시적인 팝업 알림으로 설명했다. 일시적인 팝업 대신 메일처럼 나중에도 확인할 수 있는 영구 알림을 추가하고 싶다고 밝혔다. 상세 내용은 나중에 다시 논의하고, 이 요구는 채널 정책과 별도 문서로 저장하도록 요청했다.

## 확정한 요구와 진행 방식

1. 사용자에게 지속적으로 남는 서비스 내 알림함을 추가하는 방향으로 논의한다.
2. 알림은 DB에 저장하며 사용자가 읽었는지, 읽지 않았는지 확인할 수 있어야 한다.
3. 받을 웹 푸시 기기가 없어 미발송 알림이 새 기기를 기다리는 경우, 사용자에게 안내 알림 한 건을 남기는 요구와 연결한다. 안내 정책 자체는 관련 채널 정책 문서에 기록한다.
4. 이번에는 요구와 후속 논의 주제만 기록한다. 구체적인 데이터 구조, API, 화면, 처리 방식은 사용자와 추후 논의한다.

## 후속 논의 항목

- 알림함에 저장할 알림 종류와 생성 시점
- 기기 대기 안내 한 건의 생성 기준, 반복 안내 방지, 새 기기 등록 후 표시 방식
- 읽음·안읽음 상태와 상태 변경 동작
- 팝업을 대체할 범위와 기존 외부 채널 알림과의 관계
- 보존 기간, 삭제·정리 정책, 사용자별 접근 범위
- 기존 발송 이력과 사용자 알림함의 관계 및 기존 데이터 처리
- 데이터 모델, API와 화면 구성

위 항목은 아직 확정하지 않았다. '영구 알림'은 일시적인 팝업과 달리 나중에도 확인할 수 있다는 요구이며, 물리적인 무기한 보존 정책까지 결정한 것은 아니다.

## 기존 결정과의 관계

알림함의 읽음·안읽음은 사용자 확인 상태다. 외부 서비스의 발송 요청 수락·처리 응답과 DB 성공 기록을 기준으로 하는 기존 채널 전달 완료 조건에 읽음을 추가하지 않는다. 알림함에 안내를 저장했다는 사실만으로 대기 중인 웹 푸시 발송을 성공으로 처리하지 않는다.

## 기록과 구현 상태

사용자가 요구를 제시하고 별도 문서 저장을 요청했다. 제품 방향과 논의 보류를 기록했으며 상세 설계나 애플리케이션 구현은 수행하지 않았다. 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 사용자 발송 실패 안내는 영구 알림함에 저장한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 사용자에게 발송 실패를 안내하는 수단
- 관련 자료: [최종 실패와 원인별 안내 대상](2026-10-01-notification-at-least-once-delivery.md), [웹 푸시 부분 성공·실패 처리](2026-10-01-notification-channel-policy.md)

### 확정한 동작

1. 사용자에게 필요한 발송 실패 안내는 서비스 내부 영구 알림함에 DB로 저장한다. 읽음·안읽음을 확인할 수 있다는 기존 요구를 적용한다.
2. 이 실패 안내를 이메일·Discord·웹 푸시로 다시 발송하지 않는다. 실패를 집계하는 채널과 안내를 전달하는 수단을 구분한다.
3. 영구 알림에는 실패한 채널을 표시한다. 한 채널의 실패를 전체 여석 알림 실패로 안내하지 않는다. 웹 푸시 일부 대상만 실패한 경우에도 모든 대상이 실패한 것처럼 표시하지 않는다.
4. 여석 발생 알림 자체의 외부 채널 발송 정책과 성공 판정은 유지한다. 영구 알림에 실패 안내를 저장했다고 외부 발송을 성공으로 처리하지 않는다.
5. 운영자 안내의 전달 수단은 이번 결정에 포함하지 않는다. 사용자 안내와 운영자 진단 정보의 기존 대상 구분을 유지한다.

### 남은 논의와 기록 상태

- 여러 기기·채널의 실패를 영구 알림 몇 건으로 묶을지, 생성 시점·문구·화면·데이터 구조는 아직 확정하지 않았다.
- 영구 알림 저장 실패의 복구와 중복 안내 방지, 보존 기간도 상세 설계에서 정한다.
- 사용자가 실패 안내의 전달 수단을 명확히 하고 기존 문서에 추가하도록 승인했다. 기존 내용은 수정·삭제하지 않고 끝에 추가했다. 이번에는 결정만 기록했으며 애플리케이션 코드 변경이나 테스트 추가·실행은 수행하지 않았다.

## 추가 결정: 웹 푸시 최종 실패 안내는 기기별로 한 건씩 남긴다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 웹 푸시 발송 실패 안내의 영구 알림 생성 단위
- 관련 자료: [기기별 발송 결과와 종료 정책](2026-10-01-notification-channel-policy.md), [최종 실패 정책](2026-10-01-notification-at-least-once-delivery.md)

### 비교와 결정

| 방식 | PC 성공·휴대폰 및 태블릿 최종 실패 시 안내 | 선택 |
| --- | --- | --- |
| 기기별 한 건 | 휴대폰 실패 한 건, 태블릿 실패 한 건 | 사용자 선택 |
| 웹 푸시 결과를 묶어 한 건 | 성공·실패 대상 수를 집계한 안내 한 건 | 채택하지 않음 |

1. 웹 푸시 사용자 발송 실패 안내는 해당 여석 발생의 실패한 기기별로 영구 알림 한 건씩 남긴다. 외부 채널로 다시 발송하지 않는다.
2. 성공한 기기는 실패 안내에 포함하지 않는다. 한 기기의 실패를 웹 푸시 전체나 다른 채널의 실패로 표시하지 않는다.
3. 일시적 실패의 매 시도마다 안내를 한 건씩 만드는 규칙은 아니다. 재시도 소진·명확한 복구 필요 오류 등 기존 정책의 최종 실패를 안내하는 단위다.
4. 받을 주소가 없어 재등록을 기다리는 안내는 최종 발송 실패 안내와 구분한다. 이번 결정으로 재등록 대기를 최종 실패로 바꾸지 않는다.

### 후속 논의와 기록 상태

- 기기별 최종 실패 직후 안내를 저장할지 전체 대상 처리가 끝난 뒤 저장할지는 아직 미정이다.
- 대상 작업 교체 이력과 물리적 기기 식별, 안내의 구체적인 식별·중복 방지 기준, 문구·화면과 저장 실패 복구는 상세 설계에서 정한다.
- 사용자가 기기별 한 건 방식을 선택하고 기존 문서 끝에 추가하는 것을 승인했다. 기존 내용은 수정·삭제하지 않았다. 이번에는 결정만 기록했으며 애플리케이션 코드 변경이나 테스트 추가·실행은 수행하지 않았다.

## 추가 결정: 최종 실패 직후 실패 상태와 영구 안내를 함께 저장한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 웹 푸시 기기별 실패 안내 생성 시점과 최종 실패 상태 저장의 원자성
- 관련 자료: [발송 재시도·최종 실패 정책](2026-10-01-notification-at-least-once-delivery.md)

### 비교와 선택

| 결정 질문 | 선택한 방식 | 채택하지 않은 방식 |
| --- | --- | --- |
| 안내 생성 시점 | 해당 기기의 최종 실패가 확정되는 즉시 | 다른 기기의 처리가 끝날 때까지 대기 |
| 실패 상태·안내 저장 | 같은 DB 트랜잭션으로 함께 저장 | 안내 생성 작업을 별도로 남겨 worker가 추후 생성 |

### 확정한 동작

1. 해당 웹 푸시 기기의 최종 발송 실패가 확정되면 다른 기기의 처리가 끝나기를 기다리지 않고 영구 알림 한 건을 저장한다. 재시도 중 개별 실패마다 안내를 생성하지 않는다.
2. 최종 실패 상태와 해당 실패를 안내하는 영구 알림은 같은 DB 트랜잭션으로 저장한다. 두 기록은 함께 커밋되거나 함께 롤백된다.
3. 영구 알림 저장 실패가 최종 실패 상태 저장도 롤백시킬 수 있다는 제약을 수용한다. 별도 안내 생성 worker를 이번 결정으로 도입하지 않는다.
4. DB 저장 실패 후 복구는 외부 여석 알림을 재발송하는 대신 최종 실패 상태와 영구 안내 저장을 재완료하는 방향으로 설계한다. 종료 후 자동·수동 재발송하지 않는 기존 정책을 유지한다.

### 근거와 남은 설계

- 안내를 기기별로 남기므로 다른 기기 결과를 기다리지 않는다. 실패 상태만 남고 사용자 안내가 누락되는 저장 순서의 문제를 같은 트랜잭션으로 방지한다.
- 단일 DB에 기록하는 요구에서 추가 안내 생성 작업·worker를 관리하는 부담을 줄인다.
- 외부 요청 결과와 DB 저장 사이에 서버가 중단되는 경우, 최종 실패 판정의 복구 가능한 저장·재실행 방법은 상세 설계에서 정한다. 트랜잭션 선택만으로 모든 서버 중단 상황의 복구가 완성된 것은 아니다.
- 동일 실패 안내의 중복 생성 방지 방식은 아직 확정하지 않았다. DB 고유 제약 제안은 별도 선택을 기다린다.
- 이메일·Discord 등 다른 채널의 안내 저장 적용 범위, 데이터 모델·API·화면과 보존 정책은 후속 논의에서 정한다.

### 기록과 구현 상태

사용자가 즉시 저장과 같은 DB 트랜잭션 방식을 선택하고 두 결정을 함께 기록하도록 승인했다. 기존 내용은 수정·삭제하지 않고 끝에 추가했다. 이번에는 결정만 기록했으며 애플리케이션 코드 변경이나 테스트 추가·실행은 수행하지 않았다.

## 추가 결정: 최종 실패 안내 저장에 DB 고유 제약으로 멱등성을 보장한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 같은 최종 실패 안내의 중복 저장 방지

### 비교와 결정

| 방식 | 효과 | 선택 |
| --- | --- | --- |
| DB 고유 제약으로 동일 안내 제한 | 동시 처리·재실행에서도 동일 안내를 한 건으로 제한 | 사용자 선택 |
| 저장 전 존재 여부 조회만 수행 | 동시 처리에서 중복 생성 가능 | 채택하지 않음 |

1. 같은 최종 실패 작업에 대한 같은 종류의 영구 안내는 한 건만 저장되도록 멱등성을 보장한다. 최종 보장은 DB 고유 제약으로 구현한다.
2. 안내 원인 식별 기준으로 '실패한 발송 작업 ID + 안내 종류'를 제안했다. 실제 컬럼·키 형식은 상세 설계에서 확정한다. 사용자나 채널만으로 제한해 다른 여석 발생·대상의 안내까지 막지 않는다.
3. 같은 저장 처리를 다시 실행하면 기존 안내를 유지하고 새 안내를 생성하지 않는다. 기존 읽음 상태를 초기화하지 않는다. 서로 다른 발송 작업의 실패 안내는 별도로 저장할 수 있다.
4. 최종 실패 상태와 안내를 같은 트랜잭션에 저장하는 기존 결정을 유지한다. 중복 삽입 충돌이 실패 상태 저장까지 방해하지 않도록 안전한 충돌 처리 방식을 상세 설계에서 정한다.
5. 외부 채널의 중복 발송 허용과 DB 내부의 동일 실패 안내 중복 방지는 별개의 정책이다.

### 기록과 구현 상태

사용자가 DB 고유 제약으로 멱등성을 적용하는 방식을 선택하고 문서 기록 요청에 1번으로 응답했다. 기존 내용은 수정·삭제하지 않고 끝에 추가했다. 실제 스키마·저장 코드와 DB 저장 실패 복구는 아직 구현하지 않았으며 테스트를 추가하거나 실행하지 않았다.

## 추가 결정: 최종 실패 상태·안내 저장은 고정 1분 간격으로 완료될 때까지 복구한다

- 상태: Accepted
- 결정일: 2026-10-04
- 범위: 최종 발송 실패 이후 DB 저장 실패의 자동 복구 정책
- 관련 자료: [외부 발송 총 10회 제한과 최종 실패 종료](2026-10-01-notification-at-least-once-delivery.md)

### 확정한 동작

1. 외부 발송이 최종 실패하면 최종 실패 상태와 영구 안내의 DB 저장을 즉시 시도한다. 기존의 같은 트랜잭션 저장과 안내 멱등성 정책을 유지한다.
2. DB 저장이 실패하면 고정 1분을 기다린 뒤 저장 처리를 다시 시도한다. DB 저장 복구에는 시도 횟수 제한을 두지 않고 저장 완료까지 자동 복구한다.
3. 이 복구 과정에서 외부 여석 알림을 다시 발송하지 않는다. DB 저장 재시도 횟수는 외부 발송의 최초 포함 총 10회에 포함하지 않는다.
4. 이미 커밋됐으나 완료 여부를 확인하지 못해 저장을 재실행하더라도 동일 안내를 추가로 만들거나 기존 읽음 상태를 초기화하지 않는다.

### 근거와 남은 설계

- 외부 발송의 횟수 제한과 사용자에게 결과를 남기는 DB 저장 복구를 구분한다. DB 장애 때문에 최종 실패 안내를 포기하지 않는 방향을 선택했다.
- 첫 저장에 추가 대기를 두는 것이 아니라 저장 실패 이후의 재시도 간격을 1분으로 정한 것이다. 재시도 간격은 초기 정책값이며 최적성이 운영 측정으로 확인된 것은 아니다.
- 서버 재시작 후에도 저장할 결과를 복구하는 구조, 외부 요청 결과와 DB 저장 사이의 중단 처리, 저장할 수 없는 데이터 오류의 진단·복구는 상세 설계에서 정한다. DB 장애 중 결과가 메모리에만 남은 경우까지 복구 가능하다고 현재 보장하지 않는다.
- DB 연결·worker를 1분간 점유하는 구현을 승인한 것은 아니다. 다음 시도 예약·실행 방식은 상세 설계에서 정한다.

### 기록과 구현 상태

2. 보존 대상에는 소프트 삭제된 알림도 포함한다. 사용자 삭제나 탈퇴에 따른 소프트 삭제는 일반 알림함 조회에서 숨기는 기존 정책을 적용하며, 해당 동작만으로 DB 기록을 실제 삭제하지 않는다.

영구 알림 생성·읽음·삭제·실패 안내 조건은 안쪽 유스케이스·도메인에서 관리하고, DB 저장은 안쪽 계약을 구현한 바깥 영속성 어댑터에서 수행한다. 실패 상태와 실패 안내를 같은 DB 트랜잭션으로 저장하는 기존 결정은 유지하며, 해당 원자적 처리 범위는 바깥 트랜잭션 실행 어댑터에서 감싼다. 알림 데이터의 읽음·보존·기기별 안내·조회 정책은 유지한다.

이번 추가는 구현 경계의 보완이며 실제 알림함·DB 코드 변경이나 테스트 실행은 하지 않았다.
