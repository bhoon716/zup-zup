# 첫 전환 구현 계획: 수집 → 강의 갱신 → outbox 기록

- 작성일: 2026-10-13
- 상태: 첫 전환 범위 확정, 구현 전 계획
- 기준: [클린 아키텍처와 첫 전환 결정](decisions/2026-10-13-clean-architecture-policy.md), [수집 정책](decisions/2026-10-04-course-collection-policy.md)
- 목적: 확정한 정책을 유지하면서 순수 업무 코드와 외부 구현을 분리한다.

이 문서의 첫 전환 범위와 아키텍처 기준은 사용자 결정이다. 아래 클래스명·작업 분할은 코드 조사에 따른 구현 초안이며 세부 명칭을 확정된 사용자 정책으로 취급하지 않는다. 실제 코드·DB는 아직 전환하지 않았다.

## 1. 범위와 기존 접점

첫 전환의 끝은 여석 발생 outbox의 커밋이다. 수신자 선정과 채널 발송 worker의 전체 정책 전환은 이후 작업이다. 첫 구현이 끝났다는 이유로 모든 알림 정책이 구현됐다고 표시하지 않는다.

| 현재 코드 | 확인한 책임 | 전환할 책임 |
| --- | --- | --- |
| `CourseScheduler`, `AdminCourseController` | 예약·수동 수집 진입 | 바깥 입력 어댑터로 유스케이스 호출 |
| `CourseCrawlerService` | 중복 실행 방지, 수집·반영 순서, 실행 상태·로그·지표 | 업무 흐름과 바깥 실행·관측 제어 분리 |
| `CourseCrawlFetcher`, `JbnuCourseParser`, `JbnuCourseApiClient` | 학교 요청·파싱, 정규화, 전체 결과 검증 | 학교 기술 형식은 외부 어댑터에, 업무 유효성·동일성 규칙은 코어에 배치 |
| `CourseCrawlCompletionService` | 강의 동기화와 수집 성공 상태를 같은 DB 트랜잭션으로 기록 | 바깥 트랜잭션 실행으로 원자성 보존 |
| `CourseCatalogSynchronizationService` | JPA 강의 갱신, 좌석 이력, 이벤트 발행, 지표 | 순수 반영 유스케이스와 저장·기록 계약으로 분리 |
| `Course`, `CourseSchedule`, `CourseSeatHistory` | 현재 JPA 모델과 업무 상태가 결합 | 순수 업무 모델과 영속성 표현 구분 |
| `SeatNotificationOutboxService` | `BEFORE_COMMIT` 이벤트 리스너에서 저장 | 안쪽 기록 계약을 구현하는 영속성 어댑터로 직접 호출 |
| `SeatNotificationOutboxProcessor` | 커밋된 outbox에서 수신자·발송 작업 생성 | 첫 전환에서는 호환 소비 접점으로 연결 |

현재 수집은 분류별 결과를 누적하고 전체 검증 후 DB 반영을 호출한다. 동기화의 100건 묶음은 현재 하나의 트랜잭션 안에서 처리된다. 이를 서로 다른 커밋으로 나누면 전체 미반영 정책이 깨지므로 묶음 최적화와 트랜잭션 경계를 구분한다. 이 100건은 발송 worker의 100개 확보 정책과 별개의 값이다.

## 2. 목표 실행 흐름

```text
예약·수동 입력 어댑터
  → 실행 중 여부 확인과 시작 당시 설정 확보
  → 수집 유스케이스
      → 학교 수집 계약 → RestClient·JSON 파싱 어댑터
      → 정규화된 전체 강의 데이터의 업무 검증
      → 반영 실행 계약 → 바깥 DB 트랜잭션 실행
          → 반영 유스케이스
              → 기존 강의 조회 계약
              → 순수 모델로 변경·여석 발생 판단
              → 강의·좌석 이력 저장 계약
              → 여석 발생 기록 계약 → outbox 영속성 어댑터
              → 수집 성공 상태 기록
          → 함께 커밋 또는 롤백
  → 실행 결과·변경 정보를 바깥 로그·지표 경로에 전달
```

코어가 호출할 반영 실행 계약은 안쪽에서 정의하고 바깥 트랜잭션 실행기가 구현한다. 해당 실행기가 반영 유스케이스를 같은 DB 트랜잭션 안에서 호출하도록 조립한다. Spring 애너테이션은 이 실행기에 둔다. 학교 HTTP 호출 전체를 감싸는 트랜잭션은 만들지 않는다.

outbox 저장은 커밋 전 동기 호출로 완료한다. 외부 채널 발송은 이 트랜잭션에서 수행하지 않는다. 별도의 `REQUIRES_NEW`로 outbox만 먼저 커밋하거나 비동기 이벤트에 맡기지 않는다.

## 3. 패키지와 주요 계약 초안

단일 Gradle 모듈에서 기존 기능 구분을 활용한다.

| 기능 | 안쪽 | 바깥 |
| --- | --- | --- |
| `academic/crawling` | 수집 유스케이스, 대상·설정·결과 데이터, 학교 수집·반영 실행 계약 | 학교 HTTP·JSON, 수집 설정·상태 저장, 예약·수동 입력·중복 실행 제어 |
| `academic/course` | 강의 식별·상태·여석 변화, 반영 유스케이스, 강의·좌석 이력 저장 계약 | JPA 매핑·쿼리·저장·조회, 변경 정보 관측 |
| `seatalert/notification` | 여석 발생 기록 계약과 발생 데이터 | 기존 outbox 형식에 저장하는 영속성 어댑터 |
| 바깥 구성 영역 | 없음 | Spring 빈 조립, 반영 트랜잭션 실행, 시간·로그·지표 연결 |

예시 계약은 `CollectCourses`, `SchoolCourseSource`, `ApplyCollectedCourses`, `CourseStore`, `SeatHistoryStore`, `RecordSeatOpening`처럼 실제 역할이 드러나게 둔다. 기존 계약과 책임이 같으면 이름만 다른 계층을 추가하지 않고 기존 계약을 정리한다. 출력 계약의 소유 위치는 호출하는 코어와 기능 간 순환 의존을 확인해 정한다.

학교의 원본 스트림·Jackson 표현·외부 예외는 학교 어댑터 안에 둔다. 코어에는 정규화된 강의 데이터·자체 오류를 전달한다. 기존 `ParsedCourseDto`의 순수 값은 활용할 수 있으며 JPA 객체를 생성하는 단계와 분리한다.

## 4. 유지할 업무 규칙

- 개설 연도·학기·과목코드·분반을 동일 개설 강의로 취급하고 교수·시간 변경은 같은 강의에 반영한다. 현행 키 형식은 `연도:학기:과목코드:분반`이므로 불필요하게 다시 만들지 않는다.
- 교수명이 비어 있으면 정해진 `교수 미지정` 처리 규칙을 적용한다. 교수별 평가 조회의 미지정 예외와 연결되는 사용처도 확인한다.
- 최초 수집은 좌석 기준 이력만 남기고 여석 발생 알림을 만들지 않는다.
- 이후 정원·수강 인원 변화에 좌석 이력을 남기며, 이전 만석에서 새 여석이 생긴 전환만 outbox 대상이다.
- 정상 결과에서 누락된 기존 강의는 유지한다. 누락을 좌석 0·폐강·삭제로 변환하지 않는다.
- 처리 불가 데이터가 있으면 해당 반영 회차 전체를 저장하지 않는다. DB 저장 실패도 해당 회차 전체를 롤백한다.
- 수집 모드·기본/여석 수집 주기·중복 요청·시작 당시 설정 완료·다음 예약 시점 실행 등 확정한 운영 규칙을 적용한다. 스케줄·관리 화면을 새로 늘리는 것은 이 전환의 목표가 아니다.
- 교수·시간·강의실 변경은 정상 반영 결과를 바깥 로그에 기록하고 별도 사용자 알림은 만들지 않는다. 롤백된 내용을 확정 변경처럼 기록하지 않는다.

현재 과거 여러 학기 수집은 학기별 반영을 반복한다. 회차의 원자적 반영 범위는 해당 대상 학기의 전체 분류 결과를 기준으로 명확히 표시하고, 여러 학기 작업 전체를 하나의 긴 트랜잭션으로 묶지 않는다. 기존 정책의 해석과 다른 요구가 확인되면 구현 전에 별도로 정리한다.

## 5. 데이터·기존 코드와의 전환

### 강의와 좌석 이력

순수 모델을 새로 정의하고 영속성 어댑터에서 기존 DB 자료와 변환한다. 전환 중 기존 JPA 모델을 활용하는 연결이 필요하면 바깥 어댑터에 한정하고 새 코어에서 참조하지 않는다. JPA 모델의 최종 패키지 이동·이름 변경 시 검색·평가·시간표 등 기존 사용처의 import·쿼리 엔티티 이름·매핑을 함께 확인한다. 서로 다른 JPA 클래스가 같은 역할로 중복 등록되는 상태를 만들지 않는다.

기존 강의·좌석 이력의 PK·courseKey·테이블·참조 관계를 우선 유지한다. 신규 순수 모델을 만든다는 이유로 데이터를 다시 적재하거나 찜·구독·시간표 연결을 끊지 않는다. 영속성 모델 분리 과정에서 JPA dirty checking에 의존하던 갱신은 명시적인 저장·변경 반영으로 보존한다.

### outbox와 감지 시각

기존 `seat_notification_outbox`의 식별자·상태·필드와 대기 행은 보존한다. 새 기록 어댑터가 기존 worker의 입력을 만들어 연결하고, 커밋 전 이벤트 경로와 직접 저장 경로가 동시에 같은 발생을 기록하지 않도록 한 경로로 전환한다.

현재 발생 데이터에는 별도 감지 시각이 없고 outbox의 `created_at`은 DB 기록 생성 시각이다. 새로 감지한 발생은 감지 시각을 한 번 정해 저장하고 재시도 때 바뀌지 않도록 계약에 포함한다. 저장 필드 추가가 필요하면 신규 Flyway migration으로 기존 행·이전 코드와의 호환성을 유지한다. 과거 행의 실제 감지 시각을 근거 없이 복원하거나 재시도 시각을 감지 시각으로 대체하지 않는다. 과거 행의 시각 표시와 발송 메시지 전환은 worker 전환에서 구분해 다룬다.

첫 단위에서는 기존 worker의 기기별 재시도·영구 알림 등 미구현 정책을 모두 완성했다고 표시하지 않는다. 필요한 outbox 읽기 호환 변경을 한정해 연결하고 이후 발송 흐름 전환으로 이어간다.

### 입력·응답

기존 수동 수집·조회 API의 프론트 사용처를 대조하고 호출을 새 유스케이스로 연결한다. 실행 중 추가 수집 요청은 정해진 ‘현재 수집 진행 중’ 안내를 유지한다. 실제 응답 계약을 바꾸면 해당 프론트 해석까지 같은 작업 단위에서 전환한다.

## 6. 구현 작업 순서

1. 기존 수집·동기화·outbox·조회 사용처와 DB 매핑의 접점을 목록화하고, 새 코어의 값·계약을 정의한다.
2. 강의 식별·정규화·여석 변화·좌석 이력 조건을 순수 모델·반영 유스케이스로 작성한다.
3. RestClient·파서의 외부 수집 어댑터와 기존 수집 설정·상태 연결을 정리한다. 최근 전환한 HTTP 제한·쿠키·압축 처리를 보존한다.
4. 강의·좌석 이력·outbox 영속성 어댑터와 반영 트랜잭션 실행을 구현하고, 필요한 신규 migration을 작성한다.
5. 예약·수동 입력과 기존 worker·조회 접점을 새 흐름에 연결한다. 이벤트 기반 outbox 저장의 중복 실행을 제거한다.
6. 합의한 검증 범위를 수행한 뒤 불필요해진 구 경로를 정리하고 구현 완료·잔여 worker 전환을 구분해 기록한다.

작업 순서는 첫 흐름의 구현 초안이다. 단위 작업마다 질문을 반복하기보다 기존 합의 안의 구현 선택을 구체화하고, 사용자 동작이나 보장을 바꿔야 하는 문제만 별도로 논의한다.

## 7. 검증 계획과 배포

테스트는 사용자 지침대로 단위 테스트와 최종 E2E만 사용한다. 아래는 실행 계획이며 이번 문서 작성에서 테스트를 추가·실행하지 않았다.

| 범위 | 확인할 보장 |
| --- | --- |
| 순수 단위 테스트 | 식별·정규화, 최초 기준 이력, 무변경, 정원/수강 인원 변경, 만석→여석, 여석 증가만 있는 경우, 누락 유지, 잘못된 전체 결과 거부 |
| 유스케이스 단위 테스트 | 저장·outbox 계약의 호출 조건과 오류 전파, 설정 입력과 발생 감지 시각 유지. 가짜 저장소로 실제 DB 롤백을 입증했다고 간주하지 않음 |
| 최종 E2E | 실행한 서버의 수동 수집 API부터 Docker MySQL의 강의·이력·outbox까지 확인. 준비된 응답과 DB 저장 실패 조건으로 전체 미반영·원자성·기존 대기 행 보존 확인 |
| 실제 학교 연동 E2E | 기존 정책대로 필요할 때 별도 명령으로 실제 학교 수집 확인. 실제 사용자 발송은 별도 승인된 채널 E2E 범위와 구분 |
| 코드·문서 검토 | 새 코어의 외부 import, 같은 DB 트랜잭션 참여, 외부 호출 경계, 구·신 중복 기록 여부와 API 사용처 확인 |

E2E의 실패 조건은 준비된 검증 환경에서 구성하며 이를 위한 운영 API를 추가하지 않는다. CI 대상과 실제 외부 호출 대상은 기존 테스트 운영 정책에 따른다. 별도의 통합 테스트나 아키텍처 검사 도구는 추가하지 않는다.

배포는 기존대로 CI 성공 후 운영자가 시작하며, 기존 앱·worker 종료 후 새 앱을 시작한다. 신규 Flyway migration이 있다면 앱 시작 시 성공을 확인한 뒤 처리한다. 기존 앱 복귀 가능 여부와 추가 필드의 호환성을 확인하고, DB 원자성이 확인되지 않은 상태로 새로운 수집 경로를 운영하지 않는다.

## 8. 완료 기준

- [ ] 새 수집·반영 업무 코어가 Spring·JPA·HTTP·로그·지표 구현에 의존하지 않는다.
- [ ] 확정한 수집·좌석·여석 발생 정책이 한 흐름에서 적용된다.
- [ ] 전체 검증 후 강의·좌석 이력·outbox와 수집 성공 상태가 같은 DB 트랜잭션으로 저장된다.
- [ ] 기존 데이터·강의 참조·대기 outbox가 유지되고 기존 worker와 연결된다.
- [ ] 이벤트와 직접 호출의 중복 기록 경로가 제거된다.
- [ ] 합의한 단위·최종 E2E 검증 결과와 미검증 범위가 기록된다.
- [ ] 실제 구현한 정책과 이후 발송 worker에 남긴 작업을 구분해 정리한다.

## 추가 기준 — 2026-10-13: 테이블 구조 변경 허용

사용자는 결정한 정책에 더 적합하면 기존 테이블도 수정할 수 있다고 명시했다. 위의 기존 테이블·키 우선 유지 계획은 검토 출발점으로 적용하고, 필요한 스키마 변경을 막는 제약으로 삼지 않는다. 신규 Flyway migration과 기존 데이터·대기 작업·참조 관계의 이전 및 배포 호환성을 함께 설계한다. [결정 기록](decisions/2026-10-13-clean-architecture-policy.md#추가-결정-재설계에-필요하면-기존-테이블-구조도-변경한다)

## 변경 기준 — 2026-10-13: 구현 취소 후 MVC 폴더 정리부터 진행

사용자는 진행한 미커밋 클린 아키텍처 구현을 취소하고, 기능별 `entity/`, `controller/`, `repository/`, `service/` 등의 MVC 레이어드 폴더 구조를 먼저 정리하도록 요청했다. 기준 동작은 작업 전 커밋 `7149c32b`다. 위 계획에서 클린 아키텍처를 강제하는 순수 모델·포트·어댑터·트랜잭션 실행기 구성은 현재 계획으로 적용하지 않는다.

현재 작업은 클래스·package·import·QueryDSL·기존 테스트 참조 경로의 이동이다. 업무 동작·API·테이블·트랜잭션·이벤트 흐름 변경은 이후 합의한 기능 설계에 따라 수행한다. 첫 기능 대상인 수집 → 강의 갱신 → outbox 기록은 유지한다. [현재 아키텍처 결정](decisions/2026-10-13-mvc-layered-architecture-policy.md), [파일 이동 목록](backend-mvc-package-moves.md)
