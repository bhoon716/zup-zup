# 백엔드 전체 재설계 논의 계획

- 갱신일: 2026-10-01
- 상태: 재설계 범위를 확인하고 여석 알림의 동작·전달 목표를 논의 중이다. 구체적인 설계와 구현 순서는 아직 확정하지 않았다.
- 목적: 기능을 이해하고 수정할 때의 인지 부채를 줄이고, 기술마다 필요한 이유를 설명할 수 있게 한다.
- 사용자 지정 범위: **“진짜 완전 간단하고 단순한 CRUD 제외 전부 다.”**
- 현황 자료: [전체 기능 체크리스트](backend-redesign-checklist.md)
- 이전 [접근 방식 제안](decisions/2026-10-01-backend-redesign-approach.md)은 철회했다.

## 1. 계획을 다시 세우는 이유

기존 계획은 사용자와 문제를 논의하기 전에 단일 Spring 앱에서 기능별로 교체하는 방식을 권장하고, 공지·일정·D-day로 구조를 검증하는 순서를 정했다. 사용자가 문제로 보는 복잡한 기능을 뒤로 미루고 조사·검증 절차를 먼저 실행했다.

새 계획은 **현재 구현을 설명하고 → 필요한 동작을 함께 정하고 → 더 단순한 설계를 비교하고 → 선택한 범위를 구현하는 것**을 기능마다 반복한다. 현재 존재하는 기능·계층·기술을 유지해야 한다는 요구사항으로 취급하지 않는다. 전체 아키텍처와 기술 목록을 미리 확정하지 않는다.

## 2. 범위와 논의 주제

단순 조회·등록·수정·삭제 자체는 이번 재설계의 중심 대상에서 제외한다. 같은 기능에 시간 규칙·권한·집계·외부 연동·동시성·복구가 붙어 있으면 그 부분은 검토한다. 예를 들어 공지 CRUD와 D-day 활성 규칙을 구분한다. 구체적인 경계는 해당 기능을 논의할 때 확인한다.

| 논의 묶음 | 먼저 확인할 동작 | 다시 평가할 구조·기술 |
| --- | --- | --- |
| 강의 수집·여석 알림 | 무엇을 수집하고 언제 알릴지, 구독 조건, 필요한 채널, 누락·중복·지연 시 동작 | 수집 단계·이벤트·outbox/delivery·claim·worker·재시도·DLQ·중복 억제 |
| 인증·계정 | 로그인 대상, 로그인 유지, 갱신·로그아웃, 이메일/Discord/기기, 탈퇴 후 처리 | JWT와 HTTP 세션의 역할, Redis 상태, 회전·폐기·실패 보상, 기능 간 정리 호출 |
| 강의 검색·시간표·찜 | 검색 조건과 기본 학기, 강의 식별, 대표 시간표·중복/충돌 규칙, 개인화 | QueryDSL·읽기 모델·조회 인터페이스·DTO 변환·기능 간 조회 경계 |
| 리뷰·반응 | 작성/중복/삭제·별점 집계, 리뷰 반응과 이모지의 목적 | 모델 분리·집계·소유권·계정 및 강의 변경 시 처리 |
| 문의·첨부 | 파일 처리, 소유권, 상태/답변, 요청 제한, 삭제·정리 | 파일/DB 실패 처리·고아 파일·Redis 제한·파일 검증 라이브러리 |
| 집계·관리·운영 | 화면에서 필요한 집계, 감사 기록, 자동 정리, 장애 확인과 대응 | 집계용 경계·예약 작업·health/readiness·지표·Slack·보존 정책 |

공통 계층·응답·오류·설정·의존성은 위 흐름에서 실제 사용 지점을 함께 검토한다. 이 표는 검토 범위이며 모든 장치가 불필요하다고 판정한 목록이 아니다.

## 3. 기능마다 함께 진행할 순서

### A. 현재 동작과 복잡한 지점을 보여주기

에이전트가 한 흐름의 입력부터 결과까지 실제 코드 경로를 정리한다. 사용자에게 먼저 세부 기술 이름이나 문제 파일을 찾아달라고 요구하지 않는다.

- 사용자에게 보이는 동작과 내부 처리 흐름
- 읽고 고쳐야 하는 파일, 호출 단계, 값의 변환
- 기술·추상화마다 맡은 역할
- 코드로 확인한 사실과 추정·미확인 사항

**산출물:** 한 기능을 논의할 수 있는 짧은 현황 설명. 전체 목록 완성이나 운영 수치 수집을 논의의 선행 조건으로 삼지 않는다.

### B. 필요한 동작을 함께 정하기

현재 구현의 복잡도를 정당화하기 전에 실제로 필요한 동작인지 이야기한다. 한 번에 모든 기능의 질문을 쏟아내지 않고 해당 흐름의 설계를 바꾸는 질문부터 다룬다.

- 누가 무엇을 하려고 사용하는가
- 유지·변경·통합·제거할 동작은 무엇인가
- 실패·중복·경합 때 어느 수준의 처리가 필요한가
- 기존 사용자·데이터·API 호환성은 어느 정도 필요한가

**산출물:** 합의한 요구와 보장, 아직 결정하지 않은 질문. 현재 코드의 보장과 새 설계에 필요한 보장을 구분한다.

### C. 구체적인 설계 대안을 비교하기

합의한 요구를 만족하는 가장 직접적인 흐름부터 작성한다. 그 방식으로 부족한 부분에 필요한 경계를 추가한 대안을 비교한다. 패키지 이름·계층 수·이벤트·저장소부터 결정하지 않는다.

각 대안에는 실제 파일 구성, 호출 흐름, 책임과 데이터 소유자, 실패 시 동작, 수정 사례를 포함한다. 사용자는 구체적인 설계를 보고 선택한다. 에이전트는 장단점과 추천 근거를 설명하고, 합의되지 않은 제안을 확정된 설계로 기록하지 않는다.

**산출물:** 함께 선택한 설계와 선택 이유.

### D. 기술과 추상화의 필요성을 결정하기

기존 기술과 새 후보에 동일한 질문을 적용한다.

| 항목 | 기록할 내용 |
| --- | --- |
| 문제 | 합의한 요구 중 무엇을 해결하는가 |
| 단순한 대안 | 별도 기술·계층 없이 어떻게 구현할 수 있는가 |
| 필요한 이유 | 단순한 대안으로 충족되지 않는 구체적인 동작·제약은 무엇인가 |
| 근거 | 사용자 요구·실제 코드·필요한 운영 자료나 비교 결과 |
| 비용 | 이해할 개념, 설정, 장애 대응, 수정 시 영향 |
| 결정 | 유지·통합·대체·제거 또는 근거 부족으로 보류 |
| 재검토 | 어떤 상황이 바뀌면 선택을 다시 보는가 |

“보통 이렇게 한다”, “나중에 확장할 수 있다”, “현재 들어가 있다”는 단독 근거로 삼지 않는다. 인터페이스·DTO·이벤트·repository wrapper도 실제 책임과 비용으로 설명한다. 자료 조사나 실험은 결정에 필요한 질문을 정한 뒤 수행한다.

**산출물:** 합의한 기술·추상화의 선택과 이유. 중요한 선택은 결정 기록에 남긴다.

### E. 선택한 범위를 구현하고 다시 함께 살펴보기

설계 논의가 끝난 흐름을 검토 가능한 크기로 구현한다. 변경 범위, 유지할 동작, 필요한 검증 방법과 실행 범위를 먼저 정한다. 사용자와 합의한 방향 안의 통상적인 코드 편집은 에이전트가 진행한다.

결과는 대표 변경 작업으로 전후 비교한다. 사용자가 흐름과 기술의 이유를 설명할 수 있는지, 수정할 때 불필요한 추적·변환이 줄었는지 확인한다. 파일 개수 감소만으로 성공을 판단하지 않는다. 문제가 남으면 설계를 수정하고 다음 흐름으로 넘어간다.

**산출물:** 검토 가능한 구현, 전후 비교, 유지·수정할 설계 원칙, 남은 작업.

## 4. 논의 순서 제안

첫 논의 후보는 **강의 수집 → 여석 변화 → 구독자 알림**이다. 사용자 핵심 흐름 안에 여러 기술과 실패 처리가 연결되어 있어 필요한 보장과 복잡도를 함께 판단할 수 있기 때문이다.

이후 인증·계정, 검색·시간표·찜, 리뷰·반응, 문의·첨부, 집계·운영을 다룬다. 이 순서는 논의를 시작하기 위한 제안이며 구현 순서의 확정이 아니다. 사용자 우선순위와 기능 간 의존관계에 따라 조정한다. CRUD 기능을 먼저 구현하는 단계는 두지 않는다.

전체 코드·데이터 전환 순서는 각 기능의 요구와 설계가 정해진 범위부터 작성한다. API·스키마·인증 상태·대기 발송·파일에 실제 변경이 생기면 그 범위에 맞는 호환성과 복구 방법을 붙인다.

## 5. 여석 알림 논의 기록

### 합의한 동작

- 알림 발생 조건: 사용자는 **“만석이다가 여석이 발생하면”**이라고 지정했다.
- 이전에 만석이었고 새로 여석이 생기는 전환을 알림 대상으로 한다. 이미 여석이 있는 상태에서 여석 수가 증가하는 것은 이 조건에 포함하지 않는다.
- 구독은 알림 발송 후에도 유지한다. 같은 강의가 다시 만석이 됐다가 여석이 생기면 다시 알림 대상으로 한다.
- outbox 패턴은 유지한다. 강의 상태 반영과 발송할 일의 기록을 같은 DB 트랜잭션에 남기는 것을 설계 전제로 둔다. 기존 outbox/delivery 테이블 구성·이벤트 전달 방식·처리 구현 전체를 그대로 유지한다는 결정은 아니다.
- 발송 전 강의 여석 상태를 재조회하지 않고 발생 사실을 전달한다. 여석이 발생했던 사실도 사용자에게 가치가 있다는 판단에 따른 선택이다. 메시지에 수집 주기·알림 전달 지연 등으로 실제 여석 상태와 다를 수 있다는 안내를 포함한다. [결정 기록](decisions/2026-10-01-seat-alert-occurrence-notification.md)
- 사용자가 켜둔 채널 각각에 전달하는 것을 목표로 하고 채널별 결과를 구분한다. 한 채널의 성공으로 다른 채널의 실패까지 완료로 판단하지 않는다. 재시도를 한다면 실패한 채널을 대상으로 한다. [결정 기록](decisions/2026-10-01-notification-channel-policy.md)
- 이메일·Discord·웹 푸시를 유지하고 FCM은 제거한다. FCM은 모바일 앱을 고려해 넣었으나 PWA로 방향을 정하면서 필요 없어졌다는 사용자 설명에 따른 선택이다. 현재 코드에는 FCM 구현이 존재하며 제거 구현은 아직 진행하지 않았다.
- 전달을 우선하며 결과가 불확실한 발송의 재시도로 생기는 중복 알림은 일단 허용한다. 같은 발생의 메시지에는 원래 여석 감지 시·분·초를 표시하고 재시도 때 바꾸지 않는다. 중복 방지 목적의 MQ 도입은 보류하되 다른 요구에서의 도입 가능성은 열어둔다. [결정 기록](decisions/2026-10-01-notification-duplicate-and-mq-policy.md)
- at-least-once 전달을 목표로 한다. 외부 서비스의 발송 요청 수락·처리 성공 응답을 받고 DB에 성공을 기록하면 해당 채널의 작업을 완료한다. 성공 여부가 불확실하거나 성공 기록 전에 서버가 중단되면 재시도한다. 사용자 기기의 실제 수신·표시·읽음은 완료 기준에 포함하지 않는다. [결정 기록](decisions/2026-10-01-notification-at-least-once-delivery.md)
- 지연된 알림도 발송 대상으로 유지한다. 정정기간이 며칠간 이어지고 늦게라도 발생 사실을 받는 것이 중요하다는 사용자 설명에 따라, 지연됐다는 이유만으로 미발송 작업을 취소·만료·삭제하지 않는다. 늦게 발송해도 최초 감지 시각을 표시한다. [결정 기록](decisions/2026-10-01-delayed-seat-alert-delivery.md)
- 사용자가 구독을 해제하면 **해제 요청 처리에서 해당 사용자·강의의 대기 발송 작업을 취소하는 방식만 적용**한다. 첫 발송·재시도 직전에 구독 상태를 재조회하는 방식은 추가하지 않는다. 발생 당시 구독 중이었다는 이유로 해제 후에도 기존 대기 알림을 계속 보내는 방식도 선택하지 않았다. 신청 기간 종료와 사용자의 구독 해제는 다른 사유로 다룬다.
- 선택 이유는 사용자가 더 이상 받지 않으려는 의도를 반영하고, 발송 때마다 추가 조회하는 비용을 피하며, 상대적으로 적게 일어난다고 보는 구독 해제 처리에 취소 작업을 두기 위해서다. 추가 조회가 실제로 유의미한 지연을 만든다는 측정 결과와 구독 해제 빈도 자료는 아직 없다. 외부 발송을 이미 시작한 작업은 해제 후 도착할 수 있으며, worker와 취소 처리의 경합 경계는 구체적인 설계에서 확인한다.
- [채널별 멱등성 조사](backend-notification-idempotency-research.md)를 작성했다. Discord는 시간 범위가 제한된 중복 생성 억제, 웹 푸시는 대기 메시지·기존 화면 알림 교체를 지원한다. 이메일의 현재 임의 헤더는 공급자 중복 방지 보장으로 확인되지 않았다. 원래 감지 시각 표시는 아직 구현되지 않았다.
- 현행 [CourseCatalogSynchronizationService](../apps/server/src/main/java/bhoon/sugang_helper/academic/course/application/CourseCatalogSynchronizationService.java)의 기존 강의 처리도 `이전 available <= 0 && 갱신 후 available > 0` 조건으로 이벤트를 발행한다. 조건이 같다는 사실은 이후 발송 구조의 필요성을 입증하지 않는다.

### 아직 논의할 동작

- 구독 당시 이미 여석이 있거나 최초 수집한 강의의 처리
- 자동 재시도 지속 또는 횟수 제한 후 보존·관리자 재개의 선택, 재시도 간격, 서버 중단 때의 복구와 장기 장애에서 쌓인 작업의 처리 순서·처리량
- 영구 실패·서버 설정 오류·발송 생략·채널 비활성화 등의 구분과 복구·정리 정책
- 구독 해제 시 취소할 작업 상태, worker가 발송 정보를 읽은 뒤 취소되는 경합, 해제·재구독과 아직 생성되지 않은 발송 작업의 처리
- 감지 시각을 정하는 수집 단계·저장 형식·시간대·최종 메시지 문구, 채널별 추가 중복 억제의 필요성
- 웹 푸시의 여러 기기 중 일부만 실패한 경우의 처리
- 기존 FCM 이력·기기·대기 작업·사용자 설정 데이터와 제거 배포 순서
- outbox에서 수신자를 정하는 시점, 사용자·채널별 작업 분리, 실행 방식·작업 점유·실패 목록의 필요성과 구현

구독 유지, outbox 패턴, 발생 사실 발송과 상태 차이 안내, 채널별 결과 관리, 유지 채널과 FCM 제거, 재발송 우선·중복 허용·원래 감지 시각 표시, 중복 방지 목적의 MQ 보류, at-least-once 전달 목표와 외부 서비스 응답 기준, 지연된 알림의 발송 대상 유지, 구독 해제 요청 처리에서의 대기 작업 취소는 사용자 결정으로 확정했다. 나머지는 사용자와 계속 브레인스토밍하며 결정한다. 현행 구현을 새 설계의 요구로 확정하지 않는다.

## 추가 기준 — 2026-10-13: 클린 아키텍처 적용과 기존 결정 정정

사용자가 전체 재설계에 클린 아키텍처를 채택하고 충돌하는 결정을 수정하도록 요청했다. 현재 아키텍처 기준은 [클린 아키텍처 결정과 기존 문서 27개 점검 결과](decisions/2026-10-13-clean-architecture-policy.md)다. 앞서 기록한 계획과 충돌하는 기술 배치는 최신 추가 기준을 우선한다.

- 업무 코어는 도메인·유스케이스·순수 계약과 데이터로 구성한다. Spring·JPA·HTTP·Redis·메일·로깅 구현은 바깥에서 연결한다.
- 저장소 통합 선택은 철회하고 순수 저장소 계약·영속성 어댑터·Spring Data 구현의 경계를 유지한다. JPA 영속성 모델과 도메인도 분리한다.
- 기능 간 강의 조회 계약은 유지한다. 직전의 계약 제거 안은 미확정 제안으로 남았으며 채택하지 않는다.
- outbox 기록과 가입 시 기본 시간표 생성의 동기 직접 호출, 같은 DB 트랜잭션 원자성, 외부 호출의 트랜잭션 밖 실행을 유지한다.
- 기존 사용자 동작·재시도·보존·채널·운영 정책은 유지하고 기술 배치만 필요한 범위에서 보완한다.
- 다음 설계에서는 대표 흐름의 실제 계약·어댑터·트랜잭션 실행 위치와 데이터 전환을 구체화한다. 모든 구현 세부 사항을 개별 질문으로 이어가지 않는다.

이번 추가에서는 결정과 계획만 정정했다. 전체 코드 전환은 수행하지 않았고 테스트를 실행하지 않았다. 검증은 기존 사용자 지침대로 단위 테스트와 최종 E2E 범위에서 별도로 진행한다.

## 추가 결정 — 2026-10-13: 현재 서버에서 기능별 전환

사용자는 별도 새 백엔드의 일괄 교체 대신 현재 서버에서 기능별로 클린 아키텍처로 전환하는 방식을 선택했다. 상세 근거는 [전환 방식 결정](decisions/2026-10-13-clean-architecture-policy.md#추가-결정-현재-서버에서-기능별로-클린-아키텍처로-전환한다)에 기록한다.

기능별 패키지 내부의 도메인·애플리케이션·어댑터를 단일 Gradle 모듈에서 구성한다. 기능 흐름 하나의 계약과 실패·원자성·데이터·API 접점을 함께 설계하고 전환하며, 필요한 코드는 새로 작성할 수 있다. 기존 구조와 새 구조가 함께 존재하는 기간의 연결과 중복 실행 방지, 전환 후 이전 코드 정리를 포함한다.

기존 사용자 데이터·대기 알림·프론트 계약을 이어받는 계획을 기능별로 정한다. 첫 전환 기능과 전체 구현 순서는 아직 확정하지 않았다. 과거 철회된 CRUD 우선 계획은 재채택하지 않는다. 이번 추가에서 코드·DB를 변경하거나 테스트를 실행하지 않았다.

## 추가 결정 — 2026-10-13: 첫 전환 범위 확정

사용자는 **수집 → 강의 갱신 → outbox 기록**을 첫 전환 대상으로 선택했다. 앞선 첫 대상 미정 상태는 이 추가로 대체한다. [결정 기록](decisions/2026-10-13-clean-architecture-policy.md#추가-결정-첫-전환은-수집강의-갱신outbox-기록으로-한다)과 [첫 전환 구현 계획](backend-redesign-first-slice-plan.md)에 범위·실제 코드 접점·원자적 저장·기존 데이터와 worker 호환·검증 계획을 정리했다.

첫 구현의 끝은 outbox 기록이며, 이후 발송 worker·채널 처리 전체의 전환과 나머지 기능의 전체 순서는 별도로 구분한다. 이번 추가는 범위 확정과 구현 계획 작성이며 실제 서버·DB 변경이나 테스트 실행은 하지 않았다.
