# 계절학기 수집 실패 점검

- 점검일: 2026-10-23
- 대상: 현재 작업 트리의 수집 코드와 2026년 동기 계절학기(`U211600025`)
- 상태: 사용자 확정 후 코드 수정 완료. 최초 점검 당시의 제안과 결과는 보존하며 후속 구현·검증은 아래에 기록한다.
- 관련 정책: [강의 수집 정책](decisions/2026-10-04-course-collection-policy.md)

## 확인한 문제

수집기는 `certDivisions=1,2,5,7,3,4`를 순서대로 조회한다. `JbnuCourseParser.parseJumpCourses()`는 정상 응답에 `dsEstSbjList: []`가 있어도 `CRAWLER_NO_DATA(C003)`를 던진다. 분류 하나가 비어 있으면 나머지 분류에서 강의를 가져왔더라도 `CourseCrawlFetcher.fetch()`가 실패한다.

`CourseCrawlerService.executeCrawl()`는 전체 조회·파싱·검증 성공 후에만 `CourseCrawlCompletionService.complete()`를 호출하므로, 이 경우 해당 회차의 강의 데이터는 DB에 반영되지 않는다. 실패 회차를 반영하지 않는 흐름 자체는 기존 정책과 일치한다. 문제는 강의가 없는 분류의 정상 응답과 전체 수집 결과가 없는 경우를 같은 오류로 취급하는 데 있다.

## 실제 학교 응답과 재현 결과

저장소의 `JbnuCourseApiClient`로 [전북대학교 JUMP 강의 조회](https://jump.jbnu.ac.kr/link?div=sucrPlan)에 접근하여 각 분류를 조회했다. 내부 학기 코드는 요청 시 `SUSR016.025`로 변환되었고, 비어 있지 않은 모든 응답의 `SEMSTR_CD`도 `SUSR016.025`였다.

| 조회 순서 | certDiv | dsEstSbjList 건수 |
| --- | --- | --- |
| 1 | 1 | 25 |
| 2 | 2 | 48 |
| 3 | 5 | 2 |
| 4 | 7 | 7 |
| 5 | 3 | 4 |
| 6 | 4 | 0 |
| 합계 | | 86 |

모든 응답에서 `ERRMSGINFO` 오류 envelope는 없었다. 응답을 메모리에 다시 공급하여 실제 파서와 수집기를 실행한 결과는 다음과 같다. 이 재현은 DB에 접근하지 않는다.

```text
FETCH_FAILED divisions=[1, 2, 5, 7, 3, 4] code=C003 detail=JUMP course list is empty
FETCH_SUCCEEDED divisions=[1, 2, 5, 7, 3] courses=86
```

두 번째 실행은 실패 지점을 분리하기 위한 진단이다. 운영 설정에서 분류 4를 영구 제거하자는 제안은 아니다. 이후 해당 분류에 강의가 개설되면 누락될 수 있다.

## 기존 테스트가 놓친 이유

관련 기존 단위 테스트 38건은 모두 통과했다. 실행 범위는 `JbnuCourseParserTest`, `CourseCrawlFetcherTest`, `CourseCrawlerTargetServiceTest`, `CourseCrawlerServiceTest`, `JbnuCourseApiClientRetryPolicyTest`, `JbnuCourseHttpResponseTest`다.

- `JbnuCourseParserTest.parseCourses_rejectsEmptyCourseList()`는 분류별 정상 빈 목록에도 예외가 발생하는 현재 동작을 검증한다.
- `CourseCrawlFetcherTest.fetch_ReturnsCompleteParsedList()`는 파서를 mock으로 대체하고 일부 호출에서 빈 iterator를 반환한다. 실제 파서는 그 전에 예외를 던지므로, 이 테스트가 통과해도 실제 빈 분류를 처리할 수 있음을 보장하지 않는다.
- 실제 파서와 정상 빈 분류 응답을 함께 사용하는 수집기 단위 테스트가 필요하다. 외부 API만 대체하고 파서는 실제 객체를 쓰면 DB나 외부 통신 없이 검증할 수 있다.

## 수정 방향 제안 — 미확정

선택 기준은 정상 강의 누락 방지, 오류 응답에 대한 기존 보호 유지, 분류별 수동 예외 설정 최소화다.

1. 파서는 정상 JSON의 빈 `dsEstSbjList`를 빈 목록으로 반환한다. 모든 분류를 합친 결과가 0건인 경우에만 기존 `CourseCrawlFetcher.validateCompleteResult()`가 `C003`으로 실패시킨다. 권장 방향이다.
2. 분류 4를 수집 설정에서 제외하는 방법은 현재 응답에 대해서는 86건 조회를 통과시키지만, 다른 분류·학기에서 같은 문제가 다시 발생할 수 있고 추후 개설 강의가 누락될 수 있어 근본 수정으로 권장하지 않는다.
3. 모든 `C003` 예외를 무조건 무시하기보다 정상 빈 배열 자체를 처리하는 편이 의도가 명확하다. 오류 envelope, 누락되거나 잘못된 배열, 필수 필드 누락, 중복 강의 등은 계속 실패시켜야 한다.

수정 시에는 정상 빈 분류 앞뒤에 강의가 있는 경우, 모든 분류가 빈 경우, 빈 분류 뒤에서 오류가 발생하는 경우를 수집기 단위 테스트로 확인한다. 실제 파싱 오류를 허용하거나 실패 회차를 부분 반영하는 정책 변경은 제안하지 않는다.

## 검증 범위와 남은 확인

- 확인 완료: 실제 학교 API 응답, 동기 계절학기 코드 변환, 실제 파서·수집기의 실패 및 원인 분리 재현, 관련 기존 단위 테스트 38건.
- 미확인: 운영 서버의 현재 배포 버전·저장된 수집 설정·오류 로그, 실제 DB 저장과 전체 서비스 E2E. 따라서 운영에서 발생한 오류와의 최종 대조는 남아 있다.
- 이번 점검에서는 애플리케이션 코드·운영 설정·운영 데이터·배포를 변경하지 않았다. 통합 테스트는 실행하지 않았다.

## 후속 구현: 분류별 정상 빈 목록 허용

- 작업일: 2026-10-23
- 사용자 확정: 분류별 빈 목록은 허용하고 전체가 0건일 때만 실패하도록 수정하며 회귀 테스트를 추가하고 검증한다.
- 결정 기록: [분류별 정상 빈 목록과 전체 0건 처리](decisions/2026-10-04-course-collection-policy.md#추가-결정-분류별-정상-빈-목록을-허용하고-전체-수집-결과가-0건일-때-실패한다)

`JbnuCourseParser`의 정상 빈 배열에 대한 `C003` 발생 조건을 제거했다. 빈 배열은 기존 반복문을 그대로 통과하여 빈 목록이 된다. 수집기의 전체 합산 후 0건 검증과 통신·오류 envelope·파싱·필수 필드·중복 검증은 유지했다. 수집 분류 설정과 DB 반영 경계는 변경하지 않았다.

수집기 테스트에서는 외부 API만 mock으로 대체하고 실제 파서를 사용한다. 빈 분류의 6개 위치, 여러 빈 분류와 정상 강의의 혼합, 전체 0건, 빈 분류 이후의 통신 실패·학교 오류·배열 누락/형식 오류·잘못된 JSON·필수 식별자 누락, 필수 강의명 누락, 분류 간 중복 키를 검증한다. 파서의 목록·스트림 진입점 모두에서 정상 빈 배열을 반환하는 테스트도 추가했다.

### 확인한 검증 결과

- 구현 전에 새 테스트를 실행했을 때 31건 중 20건이 실패하여 기존 결함을 검출함을 확인했다. 전체 0건 테스트는 첫 빈 분류에서 즉시 끝내지 않고 모든 분류를 조회했는지까지 검증한다.
- 수정 후 수집·파싱·대상 설정·실행 상태·스케줄러·동기화 관련 11개 클래스의 단위 테스트 67건이 모두 통과했다. Spring 컨텍스트·DB·외부 API를 연결하는 통합 테스트는 실행하지 않았다.
- 최초 점검에서 확보한 실제 학교 응답을 수정된 수집기와 실제 파서에 다시 공급하여, 빈 분류 4를 포함한 기존 6개 분류 전체에서 86건을 반환함을 확인했다. 새로운 실시간 조회나 DB 저장을 수행한 결과는 아니다.
- 독립 코드 검토에서 수정이 필요한 문제는 발견되지 않았다.
- 변경한 Java 파일 3개를 대상으로 저장소의 기존 규칙을 그대로 적용한 PMD·Checkstyle 검사는 모두 통과했다. 소스 범위와 별도 보고서 경로만 임시 Gradle init script로 지정했으며 규칙·실패 기준·저장소 빌드 설정은 변경하지 않았다.
- 전체 PMD 검사에서 발견한 20건 중 새 테스트의 중복 문자열 1건은 상수로 정리했다. 나머지 19건은 이번에 변경하지 않은 파일에 있으며, 각 파일이 Git HEAD와 동일함을 확인했다. 전체 Checkstyle 경고 9건도 변경하지 않은 파일에 있다. 전체 저장소 정적 검사가 통과했다고 보고하지 않는다.

운영 서버의 실제 배포 버전·설정·오류 로그 대조, DB 저장을 포함한 서비스 전체 E2E 및 운영 배포는 이번 작업에서 수행하지 않았다.

## 후속 확인: 계절학기 서비스 전환에 필요한 운영 조건

코드에서 검색 필터와 관리자 학기 선택 모두 동기 계절학기를 지원함을 확인했다. 이번 수정은 확인된 계절학기 수집 차단 조건을 해소한다. 운영에서 검색·구독·외부 알림까지 정상인지 검증한 결과는 아니다.

- 관리자에서 기본 수집 대상을 `2026` / 동기 계절학기(`U211600025`)로 저장해야 한다. 현재 수집 대상은 검색 기본 학기와 강의의 알림 신청 가능 여부에도 사용된다. 운영 DB에 이미 이 값이 저장되어 있는지는 확인하지 않았다.
- 특정 학기 1회 수집 API는 전달받은 학기로 조회만 수행하며 기본 수집 대상을 변경하지 않는다. 1회 수집 성공만으로 정기 수집·검색 기본 학기·알림 신청 대상의 전환이 완료되지는 않는다.
- 저장소의 운영 설정은 정기 수집 주기가 5분이고 서버 시작 즉시 수집은 꺼져 있다. 기본 대상 저장 후 기본 크롤링 실행으로 첫 수집을 수행하거나 다음 예약 시점까지 기다린다. 실제 운영 서버에서 적용된 설정은 별도 확인이 필요하다.
- 배포 후에는 대상 학기의 강의 DB 반영, 검색 노출, 알림 신청과 실제 여석 알림 흐름을 확인해야 서비스 전체의 정상 동작을 확정할 수 있다.

운영 기본 설정 파일의 학기 기본값은 1학기(`U211600010`)지만, 수집 대상 DB 설정이 있으면 그 값이 우선한다. 기본값만 보고 운영의 현재 대상이 1학기라고 단정하지 않는다. 이 확인을 이유로 코드·운영 설정·수집 대상·운영 데이터를 변경하지 않았다.

## 운영 반영 및 검증 결과 — 2026-10-23

사용자의 운영 배포·기본 대상 전환·운영 검증 요청에 따라 아래 작업을 수행했다. 시각은 `Asia/Seoul` 기준이다. 앞선 절의 미실행 기록은 당시 상태의 이력으로 보존한다.

### 배포 범위와 결과

- 배포 전 운영 실행 버전은 `533a5cee54a9d1a1b0bddc7d105cf553000fa78d`였고, 기본 대상은 `2026 / U211600020`, 동기 계절학기 저장 강의는 0건이었다.
- 개발 브랜치의 별도 변경을 포함하지 않고 운영 버전 위에 파서 수정·두 회귀 테스트 파일·결정 문서만 적용했다. 적용 커밋은 `5f73a8a457ca8e546aa5aeef26f15cab2db24de6`다.
- 운영 기준 코드의 관련 8개 클래스 단위 테스트 56건, 전체 PMD·Checkstyle 검사, `bootJar` 빌드가 통과했다. 앞서 개발 브랜치에서 확인한 정적 검사 기존 위반은 이번 운영 배포본에 포함되지 않았다.
- [PR #34](https://github.com/bhoon716/zup-zup/pull/34)의 [필수 CI](https://github.com/bhoon716/zup-zup/actions/runs/39906928687)가 통과한 뒤 보호 규칙을 우회하지 않고 병합했다. 기존 CI 파이프라인 자체의 추가 검증도 성공했다.
- [Production CD](https://github.com/bhoon716/zup-zup/actions/runs/39907356600)가 성공했고, 실행 이미지가 병합 커밋 `8efb5c4e544a9cd861fb6cbfec2b6cd229c05c7a`인지 확인했다. 앱 컨테이너는 `healthy`, readiness는 `UP`이었다.

### 기본 대상과 수집

로그인한 운영자의 관리자 화면에서 **기본 대상 설정**을 `2026 / 동기 계절학기(U211600025)`로 저장하고 DB의 `crawler_settings` 및 공개 기본 학기 API로 일치 여부를 확인했다. 특정 대상 1회 실행만 수행한 것이 아니다.

| 실행 | 완료 시각 | 실행 식별자 | 결과 |
| --- | --- | --- | --- |
| 저장된 기본 대상으로 수동 수집 | 14:49:04 | `02cf836c-eab8-40a7-a7ed-4eb750c6afd7` | `PERSIST` 성공, 86건 |
| 다음 5분 예약 수집 | 14:50:09 | `4fff433e-1785-4e0b-ace0-940540d08a0f` | `PERSIST` 성공, 86건 |

분류별 수집 건수는 기존 재현과 같은 `25,48,2,7,4,0`이었다. 마지막 분류 0건을 정상 처리하고 DB에 86건을 반영했다. 실행 상태는 `SUCCESS`였으며 마지막 실패 시각은 기존 10월 17일 기록으로 유지되어 이번 수집의 새 실패가 없음을 확인했다.

### 검색·알림 신청·자가 알림

- 공개 검색 API에서 해당 연도·학기의 강의 86건을 한 페이지로 조회했다. 모든 `courseKey`가 `2026:U211600025:`로 시작했고 `isSubscribable=true`였다.
- 실제 운영 검색 화면에서 기본 필터 `2026 / 동기 계절학기`와 강의 목록·여석 알림 신청 버튼을 확인했다.
