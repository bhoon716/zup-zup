# 공개 홈 렌더링과 긴 강의 목록 성능 비교

외부 평가의 홈 초기 렌더링과 검색 결과 누적 문제를 로컬 Next.js 프로덕션 빌드에서 비교했음.

| 지표 | 변경 전 | 변경 후 | 변화량 |
| --- | ---: | ---: | ---: |
| 전체 홈 HTML 응답에서 소개 제목·공지·일정 확인 | 0/5회 | 5/5회 | +5회 |
| 게스트 첫 방문에서 브라우저가 보낸 공개 위젯 API 요청 | 3회 | 0회 | -3회 |
| 게스트 첫 방문에서 Next.js 서버가 보낸 공개 위젯 API 요청 | 0회 | 3회 | +3회 |
| 강의 240개를 불러오고 목록 끝에서 DOM에 남은 카드 | 240개 | 12개 | -228개 (95%) |
| 위 강의 카드 안의 DOM 요소 | 15,360개 | 768개 | -14,592개 (95%) |

## 측정 조건

- 변경 전은 외부 평가 반영 직전 워킹 트리의 프로덕션 빌드, 변경 후는 같은 환경에서 평가를 반영한 빌드임.
- 로컬 HTTP 스텁에서 공개 공지 1건, 일정 1건, D-Day 1건을 사용했음. 서버의 각 API 응답에 120ms 지연을 줬고, 홈 HTML을 5회 읽어 제목을 확인했음. 새 Chromium 컨텍스트에서 게스트 홈을 열고 브라우저 요청 수를 별도로 확인했음.
- 검색 응답은 동일한 강의 240개를 20개씩 12페이지로 나눴음. Chromium 390×844 뷰포트에서 문서 끝으로 스크롤하며 모든 페이지를 받은 뒤 마지막 카드가 렌더링된 시점의 DOM을 1회씩 비교했음. 마지막 페이지 추가 후 목록 높이가 늘어나므로 새 목록 끝으로 다시 스크롤했음.
- DOM 수와 요청 위치를 비교한 실험임. 사용자 체감 LCP, FPS, 힙 사용량, 운영 환경에서의 지연은 측정 범위에 포함되지 않음.

## 구현과 트레이드오프

- 홈 소개는 서버 컴포넌트로 렌더링함. 공개 공지·일정·D-Day는 서로 독립적으로 요청하고, 준비된 결과를 스트리밍해 React Query의 초기값으로 재사용함. 세션 쿠키가 있는 요청은 공개 위젯의 서버 조회를 건너뛰고 기존 세션 확인을 기다림. 개인 대시보드는 브라우저에서 세션을 확인한 뒤에 조회함.
- 공개 위젯 API는 정상 게스트 첫 방문 기준 총 3회로 동일함. 서버 API가 실패하거나 제한 시간을 넘기면 해당 위젯이 브라우저에서 조회를 시도함. 공개 홈은 첫 HTML을 요청 시 생성하며 공지 공개 상태를 서버 캐시에 보관하지 않음.
- 강의 40개까지는 일반 목록으로 렌더링함. 그 이상은 창 스크롤을 따라 주변 행만 유지하며 실제 카드 높이를 측정함. 다음 페이지 로딩, 카드 액션, 상세 모달에서 돌아오는 키보드 초점을 유지함. DOM에 없는 행은 브라우저 페이지 내 찾기에서 제외됨. 전체 결과는 강의 검색과 스크롤로 접근할 수 있음.

## 회귀 검증

- `npm --prefix apps/web test -- --run`
- `NEXT_PUBLIC_GA_MEASUREMENT_ID=G-LOCALTEST npm --prefix apps/web run build`
- `npm --prefix apps/web run e2e -- --workers=2 --retries=0`
- `npm --prefix apps/web run lint`
- 브라우저 회귀 테스트는 자바스크립트를 끈 상태의 홈 소개, 긴 검색 목록의 페이지 로딩과 DOM 상한, 상세 모달을 닫았을 때의 키보드 초점을 확인함.

Node 22에서도 동일한 DOM 수와 공개 위젯 요청 수를 재현했음. Node 22 프로덕션 빌드와 Chromium 테스트 33개가 통과했음.
