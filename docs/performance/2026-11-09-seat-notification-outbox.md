# 빈자리 알림 발송 작업 생성 성능

- 측정일은 2026-11-09 (KST)이다.
- 기준 코드는 `2d490ce02`다. 성능 테스트만 실제 MySQL을 사용하도록 교체한 뒤 기준을 측정한다.
- 비교 대상은 `SeatNotificationOutboxProcessor.materializePendingOutboxes()`가 여석 이벤트 한 건의 발송 작업을 생성하고 커밋하는 과정이다.

## 실험 조건

- MacBook Air M1의 Docker Desktop에서 Testcontainers로 MySQL 8.4를 실행한다. Java는 Amazon Corretto 21.0.7이다. Flyway로 운영과 같은 마이그레이션을 적용하고 합성 구독자와 기기를 넣는다.
- 구독자 100명·1,000명에 이메일·웹 푸시·Discord를 모두 활성화한다. 이벤트당 각각 300·3,000개의 발송 작업이 생성돼야 한다.
- Spring JPA 테스트에서 실제 Outbox, 구독, 사용자, 기기 저장소와 채널 정책을 사용한다. 배치 크기를 1로 설정해 한 호출이 한 이벤트만 처리하도록 한다.
- 지표는 애플리케이션 호출부터 커밋까지의 p50·p95, 이벤트당 중복 확인 SELECT 수, 업무 SQL 실행 횟수다. 데이터 준비·검증은 측정 구간 밖에서 수행한다. SQL은 테스트 DB의 Performance Schema 문장별 실행 카운터 차이로 집계한다.
- 기존 작업의 ID, 상태, 시도 횟수, 멱등성 키가 유지되고, 비활성 채널이 제외되며, 같은 이벤트를 재처리할 때 중복 작업이 생기지 않는지 확인한다.
- 본 비교는 규모별 10회 예열 후 30개 표본씩 3회 시행한다. 각 시행에 새로운 PENDING 이벤트를 준비한다. 기준본은 분리한 worktree에서 실행하고 두 버전에서 같은 벤치마크 파일을 사용한다.

```sh
OUTBOX_BENCH_SAMPLES=30 apps/server/gradlew -p apps/server --offline performanceTest \
  --tests '*SeatNotificationOutboxProcessorBenchmarkTest' --rerun
```

## 예비 측정

| 구독자 | 이벤트당 중복 확인 SELECT | 이벤트당 INSERT | 전체 업무 SQL |
| --- | ---: | ---: | ---: |
| 100 | 300 | 300 | 606 |
| 1,000 | 3,000 | 3,000 | 6,006 |

예비 실행은 구독자 규모마다 한 번 예열하고 한 번 측정했다. 쿼리 실행 횟수와 테스트 구성을 확인하는 데 사용했다.

초기 반복 실행에서 `@DataJpaTest`가 Hibernate SQL을 콘솔에 출력하는 것을 확인했다. 콘솔 출력이 처리 시간에 포함된 해당 시행은 비교에서 제외하고, `showSql = false`를 지정한 동일한 벤치마크로 다시 실행했다. 실행 시간을 고려해 최초 제안한 회당 100개 표본을 30개로 조정했다.

## 비교 변경

발송 대상별 `existsByOutboxIdAndUserIdAndChannel` 호출을 이벤트별 일괄 조회로 바꿨다. 해당 이벤트에 속한 기존 발송 작업에서 사용자 ID와 채널만 읽어 사용자별 집합으로 구성한다. 조회는 현재 지원하는 채널을 대상으로 하고 기존 작업 상태와 관계없이 같은 사용자·채널을 재생성하지 않는다. Outbox 잠금, 발송 작업 생성과 상태 변경의 트랜잭션, DB 유니크 제약을 유지한다.
