## 알림 worker 큐 거절과 5분 주기 지연 분석 (2026-09-28)

### 쉽게 말하면

알림 worker는 메일을 보내기 전에 DB에 먼저 “이 알림은 처리 중”이라고 표시한다. 그런데 실제 작업을 넣는 내부 대기열이 꽉 차면 메일 작업은 시작도 못 한다. 현재 코드는 이때 DB 표시를 바로 취소하지 않는다. 그래서 해당 알림은 약 1분 동안 다시 시도할 수 없는 상태로 남을 수 있다.

쉽게 비유하면, 창구가 꽉 찬 걸 확인하기 전에 접수표부터 발급한 상황이다. 접수한 일은 실제 창구에 전달되지 않았는데, 시스템은 1분 동안 이미 처리 중이라고 생각한다.

### 확인된 처리 흐름

1. worker는 최대 40건을 맡도록 구성되어 있다. 일하는 thread 8개와 대기 queue 32개다.
2. DB에서 알림을 가져올 때 먼저 상태를 `PROCESSING`으로 바꾸고, 현재 시각부터 60초 뒤까지 다른 worker가 가져가지 못하게 한다.
3. 그다음 executor에 실제 작업을 넣는다. 시험 로그에는 thread 8개와 queue 32개가 모두 찬 상태에서 제출 거절이 기록됐다. 두 번의 현재 규모 실행에서 각각 41회와 44회였다.
4. 제출이 거절되면 현재 코드는 메모리상의 빈자리 계산만 원상 복구한다. DB 상태는 `PROCESSING`으로 남는다. 같은 DB 조회에서 이 상태는 60초 만료 뒤에야 다시 선택된다. 조회 주기도 5초이므로 재시도까지 약 60–65초가 걸릴 수 있다.
5. 한 번의 제출에서 거절 예외가 나면 그 제출 반복도 중단된다. 이미 DB에서 함께 가져온 나머지 알림도 실제 executor에 넣지 못했다면 같은 만료 시간을 기다릴 수 있다.

거절된 알림은 실제 발송 처리를 시작하지 못했으므로 일반 발송 실패처럼 시도 횟수가 증가하지 않는다. 두 시험 모두 마지막에는 1,625건 전부 발송됐고 누락은 확인되지 않았다.

관련 코드는 [SeatNotificationOutboxWorker](../../apps/server/src/main/java/bhoon/sugang_helper/notification/application/SeatNotificationOutboxWorker.java#L59), [SeatNotificationOutboxProcessor](../../apps/server/src/main/java/bhoon/sugang_helper/notification/application/SeatNotificationOutboxProcessor.java#L70), [SeatNotificationDeliveryJpaRepository](../../apps/server/src/main/java/bhoon/sugang_helper/notification/infra/SeatNotificationDeliveryJpaRepository.java#L47)에 있다.

### 큐가 꽉 찬 이유의 현재 판단

**확인된 사실:** executor가 작업을 거절한 순간 로그에 thread pool 8개와 queue 32개가 나타났다. 즉 executor가 실제로 작업을 더 받지 못하는 상태였다. 이 거절은 한 번의 우연이 아니라 같은 설정의 두 실행에서 반복됐다.

**가장 의심되는 코드 경로:** 빈자리를 세는 세마포어와 실제 executor의 빈자리가 아주 짧은 순간 서로 다를 수 있다. worker 코드는 작업 본문이 끝날 때 세마포어를 먼저 돌려준다. executor가 해당 thread의 작업 완료 처리를 마치고 다음 queue 작업을 가져오는 시점은 그 뒤다. 이 사이에 다음 제출이 들어오면 세마포어는 자리가 있다고 보지만 executor queue는 아직 가득 차 있어 거절할 수 있다.

이 설명은 코드 구조와 로그에 맞는 유력한 원인이지, 현재 기록만으로 확정한 원인은 아니다. 거절 순간의 세마포어 개수, executor 상태, delivery ID, 한 번의 poll에서 claim한 개수가 함께 기록되지 않아 어떤 알림이 얼마나 오래 기다렸는지 추적할 수 없다. 기존 worker 테스트도 작은 queue에서 정상 처리되는 경우만 확인하며 포화·거절·claim 회수는 확인하지 않는다. 기존 테스트는 [SeatNotificationOutboxWorkerTest](../../apps/server/src/test/java/bhoon/sugang_helper/notification/application/SeatNotificationOutboxWorkerTest.java#L44)에 있다.

### 5분 주기와 비교

재실행의 마지막 메일은 wave 시작 후 323.3초에 도착했다. 5분보다 23.3초 늦은 결과다. 1,625건을 323.3초 동안 처리한 속도는 초당 약 5.03건이다. 같은 물량을 300초 안에 끝내려면 초당 약 5.42건이 필요하다.

이 결과만으로 23.3초 지연 전체가 queue 거절 때문에 생겼다고 말할 수는 없다. 측정한 값은 여러 요인이 합쳐진 전체 처리시간이다. queue 거절로 묶인 알림은 지연에 기여했을 가능성이 크지만, 거절 시각과 각 알림의 claim·발송 시각이 없어 정확한 기여 시간은 분리할 수 없다.

또한 이번 시험은 로컬 ARM64 Docker에서 이메일만 Mailpit으로 보낸 현재 규모 wave 한 번이다. JUMP 크롤러는 약 26초 함께 돌았지만, 실제 운영 메일·Discord·Web Push·FCM 제공자 동작이나 5분마다 반복되는 여러 wave는 재현하지 않았다. 따라서 운영에서 항상 23초 늦는다거나 매번 1,625건의 알림이 생긴다는 뜻은 아니다.

### 다음 조치와 아키텍처 판단

서버를 분리하기 전에 worker가 큐 거절 뒤 DB claim을 안전하게 회수하는지와 빈자리 계산이 executor 상태와 어긋나는 경우를 먼저 재현해야 한다. 포화 시험은 8개 작업을 실행 중으로 막고 queue 32개를 채운 뒤 추가 delivery를 넣어, 거절·미제출 delivery가 오래 `PROCESSING`으로 남지 않는지와 중복·누락이 없는지를 확인해야 한다.

수정과 검증 뒤에는 현재 규모 wave를 5분 간격으로 최소 세 번 이어 실행해 다음 wave가 들어오기 전에 이전 wave가 끝나는지 확인한다. 그때 queue 거절 횟수, 가장 오래 기다린 delivery 나이, 미완료 건수, API 지연을 함께 기록한다.

이번 시험은 알림 worker 처리와 claim 회수의 개선 필요성을 보여준다. API 실패나 앱 재시작은 없었으므로 이 결과만으로 서버 분리가 필요하다고 결론 내리기는 이르다. worker 문제를 먼저 바로잡고 반복 부하에서도 API와 크롤러가 자원 경합으로 영향을 받는지 확인한 뒤 분리 여부를 판단한다.

## 운영 서버와 로컬 부하테스트의 자원 차이 (2026-09-28)

운영 서버와 로컬 Docker의 자원 정보를 읽기 전용으로 비교했다.

| 항목 | OCI 운영 서버 | 로컬 부하테스트 |
| --- | --- | --- |
| CPU 구조 | ARM64 Neoverse-N1, 1 vCPU | ARM64 Docker Desktop, Docker 엔진은 8 CPU 제공 |

| 앱 컨테이너별 한도 | 별도 메모리·CPU quota 없음 | 별도 메모리 한도 없음. 시험 서비스들은 CPU 0에만 고정 |

운영 앱은 컨테이너별 메모리 한도 없이 호스트 메모리를 공유한다. 부하테스트도 컨테이너별 메모리 한도는 없지만, Docker Desktop 전체가 운영 서버보다 약 1.9 GiB 더 넓다. 두 환경에서 앱 이미지의 Java 21 기본 설정을 조회했을 때 최대 힙 추정치가 운영 약 1.39 GiB, 로컬 약 1.85 GiB로 달랐다. 따라서 같은 코드와 요청량이어도 JVM의 최대 힙·GC 동작과 메모리 압박 시점은 달라질 수 있다.

CPU는 로컬 시험 컨테이너를 모두 CPU 0에 고정해 동시 사용 CPU 개수는 운영과 비슷하게 제한했다. 하지만 로컬 Mac의 가상 CPU와 OCI Neoverse-N1은 같은 속도가 아니며, 운영에는 Grafana·Loki·Prometheus·Alloy·Nginx Proxy Manager도 같이 실행된다. 기존 시험은 이 모니터링·proxy 컨테이너들을 포함하지 않았다. 따라서 “API 실패 0건, 재시작 0회, OOM 없음”은 시험 조건에서 관측한 결과이지, 운영 서버에서 동일하게 나온다고 보장하지 않는다.

### 더 비슷하게 맞추는 방법

- Docker Desktop 전체 메모리를 운영 Docker가 보는 5.765 GiB에 가깝게 낮추고, Docker Desktop의 CPU 수도 1개로 제한한다. Compose에서도 앱·DB·Redis가 같은 CPU 자원을 공유하도록 유지한다.
- 운영 Compose에 개별 앱 메모리 한도가 없으므로, 앱에만 임의의 `mem_limit`을 주면 운영과 다른 시험이 된다. 먼저 전체 Docker 환경의 메모리를 맞춘다.
- 앱 이미지와 Java 버전을 같게 유지하고, JVM 옵션을 별도로 강제하기 전에 운영과 동일한 기본 JVM 메모리 추정치가 나오는지 확인한다. `-Xmx`는 JVM 힙만 제한하며 DB나 native memory, 다른 컨테이너가 쓸 전체 메모리까지 제한하지 않는다.
- 가능한 경우 운영의 모니터링·proxy 컨테이너도 시험 Compose에 포함한다. 실제 외부 메일·푸시 제공자는 Mailpit과 처리 시간·실패 특성이 다를 수 있으므로, 해당 부분은 별도 통제 시험으로 확인한다.
- 서버 CPU 모델과 Docker Desktop CPU는 같지 않으므로 로컬 결과를 운영 성능 수치로 그대로 환산하지 않는다. 로컬 시험은 제한 상태에서의 회귀 비교와 병목 재현에 쓰고, 실제 운영 용량 결론은 안전한 단계 부하와 운영 지표로 보완한다.

이번 자원 비교는 서버에 부하를 주지 않고 `nproc`, 메모리 정보, Docker 상태·설정, 컨테이너 안의 Java 21 JVM 정보를 조회해 수행했다. 애플리케이션이나 Compose 파일은 변경하지 않았다.

## 후속 코드 검토와 개선 순서 — 2026-09-29

### 크롤러가 알림 poll을 막을 수 있음

앱은 `@EnableScheduling`을 켰고 별도 `TaskScheduler` bean이나 `spring.task.scheduling.pool.size` 설정이 없다. 프로젝트 Spring Boot 버전은 3.5.9이며, Spring Boot 3.5 문서상 기본 scheduler는 스레드 1개를 쓴다. `applicationTaskExecutor` 설정은 `@Async`용 executor이며 이 scheduler 설정을 바꾸지 않는다. [Spring Boot scheduling 문서](https://docs.spring.io/spring-boot/3.5/reference/features/task-execution-and-scheduling.html)

`CourseScheduler.runCrawler()`는 `crawlAndSaveCourses()`를 동기식으로 호출한다. 크롤러가 실행되는 동안 같은 scheduler thread에서 돌아야 하는 5초 주기 알림 poll도 실행될 수 없다. 실제 혼합 테스트에서 크롤러는 23:55:00.006부터 25.27초 동안 `scheduling-1`을 사용했다. 그러므로 알림 wave부터 전체 전달 확인까지 약 323초가 걸린 수치에는 poll이 시작되기 전 대기 시간이 들어갔을 수 있다. poll의 실제 시작 시각을 기록하지 않았으므로 이 지연이 실제로 25초였는지는 미확인이다.

따라서 323초를 worker의 순수 발송 속도(초당 5.03건)로 보면 안 된다. 이전 실행의 마지막 메일 시각이나 이번 실행의 전체 전달 수 확인 시각은 end-to-end 시간일 뿐, provider 발송과 DB 처리만의 속도를 분리해 주지 않는다.

### 권장 개선 순서

1. **스케줄 작업이 서로 막지 않게 한다.** 우선 scheduler pool을 2개로 설정해 크롤러와 알림 poll을 동시에 실행하는 시험을 한다. 기본 설정처럼 task 종류를 구분하지 않고 엄격히 분리해야 한다면 crawler 전용 scheduler를 둔다. CPU 서버 한 대를 더 쓰지 않고 스레드 설정만 바꾸는 변경이다. CourseCrawlerService에는 중복 크롤링을 막는 실행 중 검사도 있다.
2. **executor 거절 때 DB claim을 회수한다.** 현재 worker는 `available`을 계산해 delivery를 먼저 `PROCESSING`으로 claim한 뒤 `submit()` 안에서 permit을 얻고 executor에 넣는다. 제출이 거절되면 메모리 permit만 돌려주고 예외를 던진다. 현재 claim token을 가진 delivery는 DB에서 `PROCESSING` 상태로 남아 lease가 만료될 때까지(기본 60초) 다시 잡히지 않을 수 있고, 반복문에서 뒤에 남은 claim도 제출되지 않는다. 실제 실행 슬롯을 먼저 예약하고, 그래도 제출이 거절되면 거절 건과 미제출 건을 claim token 조건으로 즉시 `PENDING`에 돌려놓는다. provider 호출 전의 큐 거절은 provider 실패 횟수에 더하지 않는다.
3. **지연 위치를 기록하고 3개 wave로 재시험한다.** 코드에 `notification.outbox.claim.lag`과 `notification.outbox.claim_to_attempt` timer는 이미 있다. 여기에 scheduler 예정 시각 대비 실제 시작 지연, executor 거절 수, provider 호출 시간, wave 최초 claim부터 마지막 `SENT`까지 시간을 남긴다. 같은 1,625건 wave를 5분 간격으로 3번 실행해 backlog가 누적되는지 확인한다. 제안 통과 기준은 큐 거절 0회, 각 wave가 다음 5분 실행 전에 끝나고 30초 이상 여유가 남는 것, API 실패 0건이다.
4. **측정 결과를 보고 worker 수나 DB 처리를 조정한다.** 지금은 worker thread 또는 queue 크기를 바로 늘리지 않는다. queue는 대기만 길게 만들 수 있고, 1 vCPU 환경에서 thread 수를 늘려도 CPU·DB 경합이 커질 수 있다. provider 시간이 길면 채널별 동시성·timeout을 조정하고, DB 처리 시간이 길면 per-delivery 완료 때 outbox row를 잠그고 active delivery 수를 세는 경로를 측정한 뒤 최적화한다.
5. **그 다음에 crawler 컨테이너 분리를 판단한다.** scheduler 분리는 한 JVM 안에서 scheduled job끼리 기다리는 문제를 줄인다. crawler의 OOM이나 JVM 장애가 API·알림 프로세스까지 멈추는 위험을 막으려면 별도 프로세스/컨테이너가 필요하다. 이번 실행은 API 실패·앱 OOM을 보이지 않아 그 장애 경계가 지금 꼭 필요하다는 증거는 아직 없다.

이 순서의 첫 변경은 scheduler 동시성 및 queue rejection 시 claim 회수다. 둘을 적용한 뒤 동일 자원 제한에서 반복 wave를 확인해야, 남은 처리 지연이 crawler 대기·worker queue·provider·DB 중 어디서 생기는지 판단할 수 있다.
