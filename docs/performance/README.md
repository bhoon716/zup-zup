## 대체 기준 검토 — 크롤링 완료 후 1분 안에 메일 전송

만약 “크롤링에 실제로 5분이 걸리고, 그 종료 뒤 1분”이라는 뜻이라면 별도 조건이다. 이번 시험에서 관측한 크롤러 실행시간은 5분이 아니므로 그 조건을 검증하지 않았다. 새 기준을 공식 합격 기준으로 쓸지는 별도 결정이 필요하며, 두 기준의 결과를 섞어 해석하지 않는다.

## 사용자 목표 해석 — 여석 발견 후 빠른 알림 (2026-09-29)

사용자는 여석이 생기면 알림을 빠르게 받는 것을 중요한 제품 목표로 보고 있다. 따라서 API P95는 보호용 지표로 두고, 다음 성능 판단의 중심은 여석 감지부터 메일 업체 접수까지의 알림 지연으로 둔다. 정확한 허용 시간은 아직 확정하지 않았다. 크롤러 종료 후 1분은 논의된 후보 기준이며 공식 SLO로 확정된 값은 아니다.

측정은 두 구간으로 나눈다.

1. **여석 발생 → 크롤러 감지:** 현재 크롤러는 5분 간격으로 예약되고 실제 실행은 약 21–35초였다. 여석이 직전 실행 직후 생기면 다음 실행까지 기다려야 하므로, 메일 전송만 빠르게 해도 실제 여석 발생부터의 대기 시간은 줄지 않는다.
2. **감지/알림 생성 → 메일 업체 접수:** 앞의 부하 시험에서는 크롤러가 끝난 뒤 전체 wave가 Mailpit에 도착하기까지 1,625건에서 약 3분 58초–4분 05초, 1,725건에서 약 4분 39초가 걸렸다. 따라서 “크롤러 종료 후 1분 내 전부 접수”를 목표로 채택한다면 현재 결과는 모두 미달이다.

메일 업체 접수 시각과 사용자의 실제 메일함 도착 시각은 구분한다. 다음 시험은 각 알림의 생성·접수 시각을 수집하고, API 지연·오류는 알림 처리 중에도 정상 사용이 가능한지 보는 guardrail로 함께 확인한다. 기존 5분 주기 30초 여유 통과 판정은 알림이 빠르다는 뜻이 아니라 다음 주기 전 backlog 위험이 낮았다는 뜻이다.

## 처리 지연의 현재 진단 — 원인 미확정 (2026-09-29)

### 확인된 사실

- 1,725건 실행은 314초 뒤 전부 처리되어 관측 처리량은 초당 약 5.5건이었다. 실제 크롤러는 34.9초 만에 끝났고, 전체 메일 도착은 그 뒤 약 4분 39초 후였다.
- worker executor 거절 경고는 없었다. 따라서 이번 실행의 지연은 이전 시험에서 보인 거절·claim 회수 문제로 설명되지 않는다.
- API 오류, 앱·DB 재시작, OOM은 없었다. 4분 34초 자원 표본에서 앱 CPU 평균은 약 23.7%, 최고 85.2%였고 MySQL 평균은 약 5.8%, 최고 30.2%였다. 이 표본은 지속적인 CPU 포화를 보여주지 않지만 짧은 경합을 배제하지도 않는다.
- 실제 메일 업체가 아니라 로컬 Mailpit을 사용했다. 운영 SMTP 업체의 응답시간·속도 제한은 이번 지연 원인으로 확인되지 않았고, 이번 시험으로 검증되지도 않았다.

### 코드에서 보이는 후보 원인

worker는 8개 thread로 최대 8건을 실제 처리하고 queue 32칸은 기다리는 작업을 담는다. 각 delivery는 별도 작업이며 처리 중 사용자·기기 정보 조회, 메일 전송, 발송 이력 저장, `SENT` 상태 반영이 차례로 수행된다. `SENT` 반영 때마다 delivery row뿐 아니라 부모 outbox row도 잠그고 해당 outbox의 미완료 건수를 다시 조회한다. 같은 outbox에 속한 여러 메일이 이 잠금에서 기다릴 가능성이 있어 확인할 가치가 높은 후보지만, 이번 실행에는 SQL·잠금 대기시간이 기록되지 않아 원인으로 확정할 수 없다.

PENDING outbox를 delivery로 펼치는 과정에도 사용자별 기존 delivery 확인 쿼리가 있다. 이번 wave에서 이 과정이 전체 지연에 얼마나 기여했는지는 계측하지 않았다. provider 호출시간도 코드에서 timer를 기록하지만 이번 원시 수집에는 포함되지 않았다. 따라서 현재 증거가 뒷받침하는 결론은 “알림을 완료하는 전체 처리량이 목표보다 낮았다”까지이며, DB 정산·사용자 조회·메일 전송 중 어느 하나가 주원인인지는 미확정이다.

### 원인을 가르는 다음 측정

다음 동일 부하에서 알림 생성→claim, claim→메일 전송 시작, provider 호출, provider 응답→DB `SENT` 반영의 시간을 각각 저장한다. 특히 outbox row 잠금 대기와 outbox별 완료 건수 조회시간을 확인한다. 그래야 worker 수를 늘리기 전에 느린 구간이 DB 정산인지, 사용자별 조회인지, SMTP 처리인지 구분할 수 있다.
