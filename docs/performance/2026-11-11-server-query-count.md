# 서버 반복 조회의 SQL 문장 수

- 기준은 `b9fdec75a` 위의 작업 트리에서 이번 리팩토링을 적용하기 직전 상태임.
- macOS arm64, Java 21.0.7, Hibernate와 로컬 H2에서 같은 합성 데이터를 사용함. 조회는 픽스처를 저장한 뒤 영속성 컨텍스트를 비우고 실행함.
- Hibernate `prepareStatementCount` 차이를 비교함. 각 경로는 호출 1회 기준이며, 발송 작업 생성만 트랜잭션 플러시의 쓰기 문장을 함께 포함함. 조회에 사용한 현재 사용자 ID는 테스트에서 고정함.

| 경로 | 입력 | 변경 전 | 변경 후 | 감소량 |
| --- | --- | ---: | ---: | ---: |
| 이모지 통계 | 이모지 3종, 반응 4개, 로그인 사용자 | 5 | 2 | 3회 (60%) |
| 교양 분류 | 대분류 2개, 중복 및 빈 세부 분류 포함 | 3 | 1 | 2회 (66.7%) |
| 문의 목록 | 문의 3건, 활성·삭제 답변, 별도 삭제 문의 | 5 | 2 | 3회 (60%) |
| 시간표 목록 | 시간표 2개, 빈 시간표 포함 | 2 | 1 | 1회 (50%) |
| 강좌 시간표 묶음 | 강좌 21개, 각각 수업 시간 1개 | 3 | 1 | 2회 (66.7%) |
| 관리자 발송 실패 목록 | 서로 다른 이벤트의 실패 작업 2건 | 4 | 2 | 2회 (50%) |
| 발송 작업 일괄 생성 | 이벤트 3건, 기존 발송 1건, 신규 발송 1건 | 16 | 9 | 7회 (43.8%) |

조회 목록과 페이지 총건수, 정렬, 삭제 답변 제외, 로그인 사용자의 이모지 표시를 같은 데이터로 검증함. 발송 작업 생성은 기존 작업을 재생성하지 않고, 새 작업은 대기 상태로 남기며, 구독자가 없는 이벤트는 완료 처리함.

```sh
apps/server/gradlew -p apps/server --offline test --tests '*ReadQueryCountTest'
```

강좌의 수업 시간과 관리자 발송 실패 목록의 이벤트 정보는 필요한 연관관계를 조회할 때 함께 읽음. 문의 목록과 시간표 목록은 화면에서 쓰는 답변 존재 여부와 강좌 개수만 DB에서 계산함. 발송 작업은 같은 배치의 수신자와 기기를 재사용하고, 사용자 조회의 IN 조건은 최대 1,000개씩 나눔. 초기 500개 상한은 MySQL의 1,000명 단일 이벤트에서 조회를 한 번씩 더 실행해 상한을 1,000개로 조정함.

연관 조회가 합쳐지면 SQL 문장 수가 줄어도 한 SQL이 가져오는 행 수는 늘 수 있음. 발송 배치도 배치 단위로 수신자와 기기를 보관함. 이 비교는 로컬 SQL 문장 수만 측정했으며, 운영 데이터에서 지연 시간이나 메모리 사용량의 변화를 측정한 결과는 없음.

MySQL 8.4에서 교양 분류의 대소문자·악센트 비교와 빈 세부 분류 처리를 별도로 확인함. 발송 검증은 구독자 100명과 1,000명에서 각각 1회 예열 후 이벤트 2건으로 실행함. 1,000명 조건의 업무 SQL은 500개씩 조회할 때 이벤트당 3,008회에서 1,000개씩 조회할 때 3,006회로 줄었음. 기존 발송 작업 및 비활성 채널 검증도 통과했음.
