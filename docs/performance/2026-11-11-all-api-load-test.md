## 병목과 검증 근거

### 1. 이름순 혼합 조회에서 DB 대기 증가

- 130 RPS까지 p95 49.54ms 이하와 미시작 0건을 확인했음. 220 RPS에서는 p95 2,672.72ms로 130 RPS 구간의 약 54배였으며, 실제 시도율 168.69 RPS에 머물렀음. 500 RPS에서는 실제 시도율이 155.53 RPS로 내려갔음. 이 부하 구성에서 포화 전환은 130~220 RPS 사이였으며, 구간 경계를 장시간 유지 시험으로 확정하는 범위는 아님.
- 자원 샘플 26개에서 MySQL CPU는 2코어 한도 부근에 도달했고, Hikari 활성 연결 10개와 최대 대기 189개가 관측됐음. Redis CPU와 메모리는 할당량에 여유가 있었음. 50 RPS 회복 구간에서는 기준선과 비슷한 지연이 돌아왔음.
- 좌석 이력 쿼리의 `EXPLAIN`은 추정 약 19.9만 행 전체 스캔과 filesort를 표시했음. 알림 이력도 약 8.6천 행 전체 스캔과 filesort를 표시했음. 이름순 기준 50 RPS에서 검색 p95 53.45ms와 좌석 이력 p95 53.18ms가 조회 중 가장 높았음. 두 이력 인덱스를 복구하는 실험은 별도로 필요함. [이력 실행 계획](/tmp/zupzup-api-load.6otN7d/read-explain.txt)

### 2. 인기순 찜 집계의 인덱스

- 느린 실제 SQL을 추출해 같은 데이터에서 실행 계획을 비교했음. 기존 `(user_id, course_key)` 유니크 인덱스는 `course_key` 단독 조건에서 `index` 전체 스캔으로 잡혔고, 추정 7,303개 인덱스 레코드를 훑었음. 테스트 DB에 `wishlists(course_key)`를 추가하자 `ref` 조회와 추정 1개 레코드로 바뀌었음.
- 같은 쿼리를 각 조건에서 3회 실행했음. 인덱스 없이 3회 모두 서버 SQL 제한 4초에 도달했고, 추가 후에는 0.13·0.13·0.14초에 완료했음. 이 시간에는 로컬 `docker exec` 왕복이 포함됨. 격리 인덱스를 적용한 인기순 혼합 40 RPS 시험에서 1,200건이 오류·미시작 없이 완료됐고, 검색 243건의 p95는 108.75ms였음.
- 초기 인기순 예열은 잘못된 테스트 값 때문에 500도 포함한 실패 사례임. 별도로 실제 SQL 10개와 160초 이상 실행, Hikari 대기, 같은 SQL의 인덱스 유무 실험으로 병목을 확인했음. 임시 인덱스는 실험 직후 제거했음. ### 3. 대표 시간표 전환

- 기본 대표 시간표와 다른 시간표를 가진 계정으로 단건 호출해 400을 재현했음. MySQL은 `1062`와 `timetables.uk_timetable_primary_user` 중복을 기록했고, 실패 후 기존 대표 상태는 유지됐음. 두 쓰기 구간에서도 740건 전부 같은 400이었음.
- 서비스는 기존 대표 해제와 새 대표 설정을 한 트랜잭션에서 변경함. 재현 결과는 DB가 제약을 검사할 때 두 상태 변경이 충돌하는 경우와 일치함. 기존 대표 해제를 먼저 DB에 반영하는 수정과 MySQL 동시성 회귀 테스트가 필요함. [단건 재현 결과](/tmp/zupzup-api-load.6otN7d/primary-reproduction.json)
