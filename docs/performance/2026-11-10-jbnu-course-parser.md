# 전북대 강의 응답 파서 성능 실험

2026-11-10에 UTF-8 Reader, Jackson 직접 InputStream, 기존 바이트 배열의 일괄 디코딩을 비교했음. 2026-11-11에 응답 시간을 우선해 Reader 변경과 실험용 회귀 테스트를 되돌렸음. 최종 파서는 `readAllBytes()` → `new String(..., UTF_8)` → `readTree(...)` 경로임. 실제 JUMP 호출 측정과 채택한 세션 재사용 변경은 [HTTP 실험 기록](2026-11-10-jump-http-stage-latency.md)에 정리했음.

## Reader 실험 변경 범위

- 기준본은 `b7441446b`임. 변경본은 `JbnuCourseParser.streamCourses()`의 UTF-8 Reader 실험본임.
- 기존에는 HTTP 클라이언트가 본문을 `byte[]`로 보관하고, 파서가 `readAllBytes()`와 `new String(...)`으로 전체 본문을 다시 만들었음. 변경본은 UTF-8 `InputStreamReader`를 Jackson에 전달함.
- 문자열과 스트림 입력은 같은 JSON 트리 검증과 DTO 변환을 거침. 정상 JSON 뒤의 읽기 오류를 감지하기 위해 남은 입력도 소비함. 스트림은 호출자가 닫음.

## 측정 조건

- MacBook Air M1, RAM 16 GiB, Amazon Corretto 21.0.7, G1 GC, `-Xms384m -Xmx384m`, 파싱 스레드 1개임.
- 저장소의 `mock/jump_course_response.json` 한 행을 사용해 고유 과목 코드를 부여한 합성 응답을 생성함. 기준본과 변경본에 같은 파일을 입력하고, 각 JVM에서 문자열 경로와 스트림 경로의 DTO 값 및 순서가 같은지 확인함.
- 파싱 1회는 메모리에 올려둔 바이트로 입력 스트림을 만들어 DTO 목록을 완성하는 구간임. HTTP, DB, 입력 파일 읽기 및 DTO 동등성 검사는 측정 구간 밖에 둠.
- 할당량은 파싱 스레드의 `ThreadMXBean` 누적 할당 바이트 차이임. 시간은 `System.nanoTime()`으로 측정하고 세 시행의 900개 표본을 합쳐 min·p50·p95·p99·max를 집계함. 백분위수는 nearest rank를 사용함.
- 힙은 별도 JVM에서 100회 연속 파싱하는 동안 약 1ms 간격으로 관측한 `MemoryMXBean`의 최대 사용량임. 시작점에 예열 결과를 해제하고 GC를 한 번 요청함. 힙 최댓값에는 아직 회수되지 않은 객체가 포함되며 짧은 피크는 샘플 사이에서 빠질 수 있음.
- 응답 크기·측정 방식마다 버전별 독립 JVM 3회, JVM당 예열 100회임. 실행 순서는 기준→변경, 변경→기준, 기준→변경임.

## 처리 시간과 HTTP 버퍼링 보조 실험

- 두 크기에서 할당량은 약 34% 줄었음. 관측 최대 힙은 1 MiB에서 33.60%, 8 MiB에서 15.37% 줄었음.
- 세 시행 모두 p50·p95·p99가 늘었음. 8 MiB에서 p50은 6.53 ms, p95는 11.93 ms, p99는 27.58 ms 늘었음. 1 MiB에서 변경본의 단일 최댓값 60.51 ms는 다른 두 시행의 최댓값 17.74 ms와 8.53 ms보다 컸음.
- 별도의 1 MiB JFR 실행에서 기준본의 메인 스레드 실행 표본 234개 중 13개가 `String.decodeUTF8_UTF16` 경로에 있었음. 변경본은 268개 중 65개가 `UTF_8.Decoder.decodeArrayLoop`에서 채집됐음. 디코딩 경로가 처리 시간 차이에 기여한다는 증거임. JFR 표본은 처리 시간 비교에서 제외했으며 개별 최장 표본의 원인은 확정하지 못했음.
- 실제 HTTP 클라이언트로 로컬 서버의 gzip 응답을 받아 변경본 파서로 읽는 보조 실험을 했음. 크기마다 15회 예열 뒤 30회 측정했음. HTTP와 파싱은 호출 스레드에서 구간을 분리했으며 HTTP 작업 스레드 할당량은 집계 범위 밖임.

## Jackson에 InputStream을 직접 전달하는 추가 실험

후보는 `STREAM_READER.readTree(responseStream)`으로 JSON을 읽고, 남은 바이트는 `OutputStream.nullOutputStream()`으로 소비함. 입력 자동 닫기는 계속 꺼 둠. 기준은 위에서 적용한 UTF-8 `InputStreamReader` 경로임. 후보 클래스는 별도 디렉터리에서 컴파일해 테스트와 벤치마크의 클래스패스 앞에 배치했음.

### 동작 비교

14가지 입력을 기존 일괄 디코딩, Reader 실험본, 직접 InputStream에 각각 넣었음. 기존 일괄 디코딩과 Reader 결과는 이 입력들에서 같았음.

| 입력 | 기존 일괄 디코딩 / Reader 실험본 | 직접 InputStream |
| --- | --- | --- |
| 정상 UTF-8 한글 | 같은 DTO | 같은 DTO |
| 빈 스트림·잘린 JSON | C002 | C002 |
| 빈 강의 배열 / JUMP 오류 응답 | 빈 목록 / C001 | 빈 목록 / C001 |
| 정상 JSON 뒤 추가 문자 | 같은 DTO | 같은 DTO |
| UTF-8 BOM, UTF-16LE BOM, BOM 없는 UTF-16BE, UTF-32BE BOM | C002 | 정상 DTO |
| 잘못된 UTF-8 시작·연속 바이트, 인코딩된 서로게이트 | U+FFFD로 치환한 DTO | C002 |
| overlong UTF-8 `C0 AF` | U+FFFD 두 글자로 치환한 DTO | `/`로 읽은 DTO |

파서·수집·HTTP·저장 테스트 56개는 두 방식에서 모두 통과했음. 스트림 소유권과 JSON 뒤 읽기 실패 시 C002도 이 테스트에 포함됨. 직접 InputStream은 기존과 인코딩 처리 결과가 달라 채택하지 않았음.

### 성능 비교

## 응답 시간 우선 대안과 예비 측정

HTTP 클라이언트가 압축 해제와 크기 확인을 끝내고 만든 `byte[]`를 UTF-8 문자열로 한 번에 디코딩하는 방식임. 기존 `new String(bytes, UTF_8)`과 `parseCourses(String, year, semester)` 경로를 유지하면서, 이미 읽은 배열을 스트림으로 감싼 뒤 파서에서 `readAllBytes()`로 복사하는 구간만 없앰. 실험은 제품 코드 변경 없이 수행했음.

기준은 기존 파서에 실제 운영과 같은 `BoundedInputStream(ByteArrayInputStream)` 조합을 넘긴 경우임. 후보는 같은 배열을 `new String(..., UTF_8)`에 직접 전달한 경우임. 동일한 합성 응답과 JDK 21·384 MiB 고정 힙·G1 GC를 사용했음. 방식별·크기별 JVM 3회를 교차 실행했고, JVM당 100회 예열 후 200회씩 측정했음. 전체 DTO 값·순서는 각 JVM에서 비교했음. 수치는 이미 받은 바이트부터 파싱 결과 생성까지이며 HTTP와 저장은 제외함. 이번 예비 실험은 처리 시간과 스레드 할당량을 측정했음.
